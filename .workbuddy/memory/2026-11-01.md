### 一、修掉的三处口径问题

**1. 情感/竞品场景里追加的词云走错了统计口径**

用户问「帮我分析一下评论的情感」，计划是 情感 → 词云（负评率 ≥5% 时追加）。
但 `_args` 只传"用户嘴上说的极性"，用户没提差评好评 → `polarity=None`
→ 工具退回全量频次排序 → 词云块显示 `质量 1792 / 苹果 1500 / 裤子 1131`。
在那两个答案里毫无价值：用户问"情感如何"，追问的自然是"不满意的在抱怨什么"。

修法：`intent in ('sentiment', 'competitor')` 且用户没指定极性时，默认传 `负向`。
**persona 不传** —— 画像要看全量，只统计差评会让"品质优先""囤货复购"
这类正向行为证据整体消失，画像只剩一半人。

**2. 词云块标题读的是"用户原话的极性"，不是"实际生效的极性"**

同一形状的坑换了层皮：数字已经是差评词云，标题却因为 `asked_polarity=None`
写成「里最常被提到的词」（连"差评"两个字都没有）。
改成读 `w['scope']['polarity']` —— 工具真正收到的那个值，只信它。

**3. 标题里"最突出的是"和 headline 复读**

块标题改为纯口径声明：`差评高频词（按区分度排序）` /
`全部评论高频词（按出现次数排序）`。`rank_by` 决定措辞，
因为两种口径回答的是不同问题，读者必须一眼看出眼前这堆词按什么排。

### 二、采集器块整块不渲染（本段最隐蔽的 bug）

**现象**：问「你的评论数据是从哪来的」，Agent 答了一句话，下面一片空白。

**根因**：`_absorb` 存进 facts 的是内层 `data`，而 `collector_status`
返回的 data 是 `{'collectors': rows, 'n_auto': 3}` —— **没有 `ok` 字段**。
`ok` 在外层 `ToolResult` 上。于是 `col.get('ok')` 恒为 `None`，整块表格永不渲染。
另外四个工具的 data 都由分析层产出、本来就带 ok，只有这个是手拼的、漏了。

**为什么 26 条断言全绿也没抓到**：它不会让任何数字变错，
只是"少显示"。这类假阴性纯粹靠人眼看截图才能发现。

**修法两层**：
- 工具侧：`data={'ok': True, ...}`，五个工具出口形状统一
- 断言侧：新增第 7 节「Agent 出口契约」，把 composer 里那些 `if` 的判据
  本身列成契约（`collector_status` 必须有 `ok/collectors/n_auto`）。
  反向验证过：把 `ok` 去掉再跑，断言立刻红。

### 三、顺带修的两个"参数收了不生效"

**`list_collectors()` 的 auto 只有布尔值** —— "半自动"在汇报里等于没解释。
补 `needs_human`（这一步要人做什么）和 `note`（为什么必须这样）。
其中 `imported` 的 needs_human 是「登录店铺后台点一次导出」，
note 是「登录态留在人手里，就是这条路径合规的全部理由」——
这两句是整份采集器说明里最该被引用的。

**CLI 的 `--dry` 是死参数** —— help 里有、从来没被读过。
用户照用不报错，于是会以为"预览过了"，而文件已经写进去了。
比"没这个功能"更糟，因为它让人失去警惕。
顺带发现 `run_collector` 把 `write` 传给了构造函数而不是 `run()`，
`--dry` 一传就炸 `CsvImportCollector() takes no arguments`。

**`REGISTRY` 键是 `import`、`name` 属性是 `imported`** —— 两套命名都对，
但用户看清单上写"平台后台导出导入"，很自然打 `--run imported`，得到"未知采集器"。
给 `run_collector` 做别名归一，两套都收。

### 四、前端三个新 block（最后一公里）

`Blocks.tsx` 的 `switch` 里原来没有 `wordcloud` / `persona` / `contrast`
三个 case，落到 `default: return null` —— **三块内容在界面上完全不显示**。

新增三个组件 + 对应 CSS（约 200 行）+ `types.ts` 五个接口。

设计上的三个决定：

1. **词云用横向条形，不用经典随机字号布局**。随机布局漂亮，但位置和大小
   都不对应可读的量，读者只能看出"哪个大"，看不出"大多少"也看不出排序。
   条形天然带顺序，还能同时挂频次和 lift。
   `lift` 列左边加虚线分隔，暗示"这是另一种量纲"，避免被读成"次数的一部分"。

2. **画像的 `cannot` 放进块内部，不进 caveats**。放 caveats 等于没写 ——
   那是页面底部折叠区，用户读到画像时已经形成印象了。
   这个清单的作用是**在印象形成的同时**拦住误读。

3. **`matched` 高亮**。让读者一眼看出"哦，是因为它提到了『回购』"，
   也能立刻发现"这句话里根本没有那个词"（如果真的错挂的话）。
   这比任何"我们做了校验"的说明都可信。

## v4.0 多页面工作台 · 完成并推送到 Gitee

用户要求「多设计几个功能页面，别只有一个 agent 问答页面」。做成 6 个功能页 + 问答页：
总览 / 归因 / 原因治理 / 评论洞察 / 竞品雷达 / 自检，加问答共 7 个入口。

### 一、架构决策：页面与 Agent 的分工

两条路径共用同一批底层函数（`DataHub` / `review_analytics`），但调用方式不同：
- 问答：Agent 动态决定查什么，按需深入
- 页面：固定查一组，一屏看全，不做动态决策

判据唯一性是硬约束：`pages.py` 的 `_diagnose_all()` 逐周调 `diagnose_week`，
绝不自己重写阈值。抄一份迟早分叉，分叉后页面和问答会给出不同答案且都不报错。

### 二、性能：评论页 37 秒 → 5.5 秒 → 0ms（缓存命中）

四个根因，全部与"重复计算"有关：

1. `load_lexicon()` **无缓存**，被 `score_text` 调 13,500 次 → 占总耗时 80%
   （单次解析 2.7ms，但没人意识到"词典是常量"）
2. 52 周循环各调一次 `analyze_sentiment`（重打分 + 8 维度全扫）
3. `word_freq()` 的极性筛选又抄了一遍打分逻辑，多跑 13,500 次 `score_text`（6 秒）
4. `tokenize()` 对同一批文本切两遍（目标组 + 对照组）

修法：拆 `score_frame()`（逐条打分 + `_SCORE_CACHE` 按 review_id）、
`_LEX_CACHE` 进程级缓存、`word_freq` 复用 `score_frame`、
`_TOK_CACHE`（键必须带 `drop_stop`/`min_len`，否则两种用法互相污染）、
维度扫描从 `for dim: apply()` 改成 `for review: for dim:` 单次遍历。

`score_text` 单条 0.92ms → 0.026ms（35×）。

### 四、hash 路由的两个坑

1. **`#/attribution/44` 渲染成第 52 周**：nav 回调里无条件 `setWeek(latest_week)`，
   把 hash 解析出的 44 吃掉了。改成 `hash 指定 > 用户已选 > 后端 default_week` 三级优先。
