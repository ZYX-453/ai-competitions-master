## 第五轮：对抗测试 → 边界硬化（方法论转折）

**方法论变化**：既有 5 用例已 5/5 全通过，继续验证同一件事没有增量价值。
改为**主动构造越界/无关/复合问题**去撞产品边界，一次性挖出 5 个真实缺陷，
其中 2 个是产品级硬伤。这比"再跑一遍已知用例"有效得多。

### 核心认识：静默降级比显式失败危险得多

- 显式失败用户会重问；**静默降级用户会拿走一份错的报告去开会**。
- 典型：`parse_week` 写成 `if 1 <= w <= 52: return w`，超范围继续往下找，
  最后 `return None`。于是"第60周"被当成"没指定周"，转头分析第 44 周，
  输出一份完整、专业、但答的不是用户问题的报告。
- 修法：`parse_week` 用哨兵区分四种状态 ——
  `None` 没提周 / `-1` 最新一周 / `n` 具体周 / `-2` **提了但越界**。
  主流程对 `-2` 前置拦截，明确说"数据只覆盖 1–52 周，我不会拿别周顶替"，0.0s。

### 四类边界（全部改为显式回应）

| 越界类型 | 旧行为 | 现行为 |
|---|---|---|
| 越界周次（第60周） | 静默改答第44周 | 前置拦截 + 说明覆盖范围 + 给可问的周次 |
| 无关问题（写诗） | 兜底 `return 'diagnose'` 走完整流程 | `is_in_scope` 前置闸，**宽进严出**（漏答≠误拒，代价不对等） |
| 多周对比（44 vs 41） | 只解析第一个周次，只答一半 | `parse_weeks` 全解析 + `compare` 意图（**必须最先判**）+ `compare_weeks` 工具 |
| 类目范围（生鲜） | 标题不写范围，读者以为 18% 是全店 | `_headline` 加前缀 + 事实包「分析范围」+ 提示词铁律 2 |

### 多周对比的三个设计要点

1. **共同基线**：剔除被比的那几周，否则"拿自己跟自己比"。
2. **按 z 排不按退货率排**：样本少的周，同样百分比更可能是噪声。
3. **排序依据必须外显**：两者排序不一致时要主动解释，
   否则读者拿退货率一对照会觉得系统在胡说。

另注：`compare_weeks` 的「剔除这几周」基线与 `diagnose_week` 的「剔除本周」
基线不同，**两套口径不可混用**，已在 caveats 里声明。

### 悬空指代「该原因」——根因是我自己写的示例句

- 现象：数码类目（61 单）第 3 段写"这一周不建议针对**该原因**开整改动作"，
  但这一周连原因结构都没算过，"该原因"指代空气。
- 三层根因，逐层修：
  ① `low_sample` 路径直接 `return []`，`no_playbook_why` 从未赋值 → 三条路径各补具体理由
  ② 提示词「怎么写」里原样写着"必须明确说明「这一周不建议针对该原因开整改动作」"
     → **给示例措辞＝替模型写稿**，它当然照抄。改成只约束"必须满足什么"
  ③ 新增校验 6：`(该|这个|上述|以上|这些)+(原因|动作)` 且事实包无对应结构 → 判失败

### 校验误伤也要修（本轮最大教训）

预支了 `95% 置信区间`，模型照实写出"95%"，**结果 95 被判成凭空编造的数字**，
两次重试全废、回退模板。我自己埋的坑，却去怪模型。

- `不建议做 X` → 先剥否定分句
- 改善场景"复盘" → 开白名单
- `95/99/90/80`（置信水平）、`12/30/60`（时间口径）→ 补进白名单

### 换算值预支：本轮补了三个

模型算得**对**，但数不在事实里，被校验拦：

| 模型想写的 | 它怎么算的 | 现在预支 |
|---|---|---|
| 天然抖动 ±3.91pp | √(p(1−p)/n) | `噪声幅度_pp` |
| ±6.46pp（90% 区间） | 3.91 × 1.645 | `波动区间95_pp`（1.96×） |

### 起因

### 最关键发现：改数字是小事，结论方向反了才是大事

README 第 2 节原来有个"教科书案例"：
> 第 3 周 9.27%，朴素 z −3.72 判极显著；但只有 151 单，二项 z 仅 −1.85，根本不显著。

新数据下第 3 周是 1,713 单、二项 z −1.22。**这个案例整个失效了。**

继续追下去发现真正的问题不是"数字过期"，而是我原先把朴素 z 的毛病
概括成"会把小样本噪声误判成异动"——**这个概括本身是错的**。

朴素 z 的分母是固定周间 sd，二项 z 分母是 √(p(1−p)/n)。令两者相等：

```
n* = p(1−p) / sd²
```

- n < n\* → 真实 SE > sd → 朴素 z 分母偏小 → **放大偏离 / 假警报**
- n > n\* → 真实 SE < sd → 朴素 z 分母偏大 → **压低偏离 / 漏报**

全店 n\* ≈ 680 单（逐周实算 666–754）。v2.4 最低周 1,197 单，**全部在 n\* 之上**，
所以这份数据上朴素 z 只会漏报：它挑 4 周（44/48/24/5），二项挑 10 周，前者是后者的真子集。
典型漏报是第 47 周：偏离 −2.40pp，朴素 z −1.89 判"没事"，二项 z −2.71 才看出来。

**教训**：一句统计结论总有它成立的前提（这里是 n < n\*）。
把结论从前提里剥出来写进文档，数据一变就会变成反话。

### 更严重的一处：同一句话硬编码在用户可见的 evidence 里

`tools/data_hub.py` 的 `evidence['why_binom']` 里原样写着
"如第 3 周 151 单，朴素 z −3.7，二项 z 仅 −1.9"。

**文档写错可以改，界面上的证据写错等于当场骗人**——用户点开推理链看到的就是它。
改成 `_why_binom_text()` 动态生成，按本周实算的 n 与 n\* 分三支：
低于 n\* / 接近 n\*（两 z 相对差 <5%，老实说结论一致）/ 高于 n\*。
并且尾句的"最低周订单"必须用**当前范围**的分布算——
第一版写成全店 1,197 单，问数码（最低 215 单）时就是张冠李戴。

## v2.5：用户说"样本量少就给我模拟数据，你不能给我显示这个"

### 用户的原话与真实诉求

截图里数码类目第 52 周 286 单，系统回"样本不足以下判断"。
用户说：**"样本量少就给我模拟数据，你不能给我显示这个"**。

这不是文案问题。上一轮我把"样本不足"改写成了"能分辨 3.59pp 以上的变化"，
措辞是好了，但用户看到的还是那句"判断不了"。
**一个分析系统动不动回"样本不足"，等于这个功能不存在。**

### 先算缺口，再决定怎么补

目标检出幅度 3pp，由 n=(2/Δ)²·p(1−p) 反推各类目门槛：

| 类目 | 周均 | 最低周 | 基线 | 门槛 | 需放大 |
|---|---|---|---|---|---|
| 服饰 | 314 | 189 | 27.75% | 892 | **5.19×** |
| 数码 | 382 | 215 | 10.27% | 410 | 2.10× |
| 生鲜 | 682 | 434 | 13.18% | 509 | 1.29× |
| 个护 | 542 | 332 | 7.21% | 298 | 1.00× |

关键洞察：**服饰最紧不是订单最少，而是退货率最高导致门槛最高**
（27.75% 要 892 单，7.21% 只要 298 单），而服饰 CVR 又恰好最低（2.19%）。

### 三条路里选了第三条（这次选择比对数值重要）

- 拉 CVR → 改的是"转化能力"，那是经营水平不是数据规模。服装 2.19% 本就合理
- 加 SKU → 稀释单 SKU 动销，本来周销 5 单就不健康
- **放流量 → 只改规模这一个自由度**，CTR/CVR/退货率/类目排序/价格带/促销弹性全不动

`SHOP_SCALE = 6.0`（服饰要 5.19×，留 15% 余量让最低那周也过线），
只加在曝光方程截距：`ln_exp = 6.42 + ln(6) + ...`。截距是纯水平项，
所有弹性（ω1/ω2/θ）与异质性（sku_fe/wk_eff）原封不动。

结果：年订单 10.0 万 → **61.8 万**，GMV 1,124.6 万 → **7,004.8 万**，
单 SKU 周销 12.2 → 75.2 单，**四类目 × 全 52 周，样本不足周 = 0**。

**意外收获**：参数回收反而更准了。λ1 估 1.2985（真值 1.30，误差 **0.11%**），
ω1 误差 2.0%，ω2 误差 4.9%，全部优于 v2.4。改动只在截距，样本量增加直接提升识别精度。

### 但样本一够，反方向的病立刻出现：什么都能验成显著

全店周均 1.19 万单，3pp 门槛只要 521 单，余量 20 倍。
z≥2 只需 **0.63pp** 偏离 → 52 周里 **22 周**判异常，8 周偏离不到 1pp。

两种错法是一回事的两端：
- 样本少 → 假阴性 → 用户觉得系统什么都不说
- 样本多 → 假阳性 → 用户觉得系统天天报警

**单靠 p 值解决不了第二端，因为 p 值只问"是不是巧合"，从不问"这事儿大不大"。**

修法：双条件判定
```
is_anomaly = (z ≥ 2) AND (|偏离| ≥ 1.5pp)
```
`MIN_EFFECT_PP = 1.5` 写成显式常量，是业务口径不是统计口径，可商量可改。
改完 22 → **5 周**（44/48/24/36/49）。

另加一支 `trivial_but_significant`（17 周）：统计显著但幅度太小。
既不能并进"异常"（给不出有意义动作），也不能并进"没事"
（用户自己一算 z 会发现过了 2，说"没事"就是瞒事）。单独说清楚。

### 更隐蔽的 bug：同一份数字被贴上两个类目标签

问"数码的退货率为什么新高"和"服饰类目怎么样"，两份报告里：
机制贡献都 3.98pp、t 都 15.8、都"151 个 SKU 中 97% 上升"。

数字是真的（全店确实如此），但回答的不是用户问的事。
根因：`promo_mechanism()` 不接受 category，`_args()` 里也没有分支，
永远返回全店结果再被"数码"/"服饰"分别包装。

**这比数字过期更危险：过期只是不准，这个是"准确的无关联"。**
用户拿它开数码复盘会，会找不到那 151 个 SKU。

修完：数码 +2.57pp/t=7.32/32 SKU，服饰 +6.09pp/t=13.59/61 SKU，全店 +3.98pp/t=15.80/151 SKU。
限定单类目时结构效应恒为 0（只有一个类目，占比永远 100%），
工具会在 evidence 里明说，避免读者把 0 误解成"没有结构问题"。

### 「你好你是谁」收到拒绝卡片

用户第一句话「你好你是谁」，系统回"**超出范围**·这个问题不在我的能力范围，我不硬答"，
正文还在解释"写诗、翻译、闲聊我不做"。用户只是打招呼，却收到防御性声明。

**这不是范围问题，是接待问题。** `is_in_scope` 只有"能答/不能答"两档，
这里需要第三档：不答，但告诉对方该问什么。

把 `你是谁/你叫什么/你能做什么/你好` 从越界词拿出，单独 `is_greeting`，
排在越界判断之前，并**顺手拉一次大盘**让自我介绍带真实数字
（618,058 单 / ¥7,004.8 万 / 退货率 13.53% / 损失 ¥531.2 万）。
第一句话就让人知道系统是活的。

边界必须守住：**带业务词的问候不算问候**（"你好，第44周为什么涨"仍是诊断）。

### 用例随数据第三次失效（这个教训已经记满了）

### 模型腔：布尔值直接拼成中文

实测量产出一句：**「不显著、不业务显著、无异常」**。

"不业务显著"不是中文。根因：事实包给了 `统计显著=否`、`业务显著=否`，
模型各加一个"不"连起来念。它**不是幻觉、也不是算错**，三个判断都对——
只是走了一条捷径：逐个取反再拼接，比"想清楚三种情况分别意味着什么"省力得多。

只要事实包里还是布尔值，它就会走这条捷径。改法两层：

1. 提示词禁止拼词，给出三种情况各自的人话：
   - 统计不显著 → "这点波动在正常范围内"
   - 统计显著但幅度不值一提 → "确实是变了，但幅度小到不值得动手"
   - 统计显著且幅度够大 → 这才叫异常
2. 出口校验：`不业务显著`/`未异常`/`非异常`/`不统计显著` 直接判废重写

提示词只是引导（这轮就从"未异常"变成了"不业务显著"，换个形式又来），
**真正的保险在出口**。

同类还有两个：

- **元话语**：「报告"没有异常"就是核心结论」——把正文变成了一份关于这份正文的说明。
  读者想知道"然后我该干嘛"，不是"作者认为他写对了"。已加出口校验。
- **同一件事说三遍**：三段都在说"没事"，只是换三种说法。字数够了，信息量为零。
  第三段现在被要求只回答一件事：**读者接下来把注意力放哪**。

### 徽章拆分：数据边界 vs 能力边界

E6（第60周）和 E7（写诗）原来共用「超出范围」一个徽章。
用户投诉"你好你是谁"收到拒绝卡片时，看到的正是它。

两件事完全不同，现在拆开：

| | 数据边界 | 能力边界 |
|---|---|---|
| 例 | 第60周（数据只到52周） | 帮我写一首诗 |
| 徽章 | 超出范围 | **超出能力** |

等于一句拒绝拆成三段反复说。现在是："不是不愿意，是做了也不可信，那还不如不做。"

## v2.8：工具失败时不能说"知识库里没有"

### 一、这一条是 v2.7 的影子问题，但更严重

v2.7 解决的是"知识库查过了、确实没有这一类"——那是**结论**。
而知识库文件被删、JSON 写坏时，是"我没查成"——那是**状态**。

两件事在界面上长得几乎一样，说出来的话完全相反：

| 说法 | 用户听到的意思 | 他接下来会做什么 |
|---|---|---|
| 「方案库里没有这一类」 | 这个问题无解 | 放弃 |
| 「方案库这次没读到」 | 是我这边的问题 | 再试一次 |

旧代码只有"命中/未命中"两档，工具失败落进未命中，写出
「知识库里也没有完全对应的条目」——假话，它压根没查。
更糟的是后面紧跟替代口径数字：前面说"没有近似条目"、
后面说"最接近的是材质做工"，自己打自己。

### 二、修的时候连挖三层

**第一层：措辞。** 分四档——命中 / 未命中 / 工具失败 / 无替代口径。
`_SYS_PROMPT_KB` 单独加一段： 「方案库没读到」可以说，
「方案库里没有这一类」绝不许说。

**第二层：事实包也在撒谎。** 模型不是自己编的，是输入就写着
`'知识库是否命中': '命中' if matched else '未命中近似条目'`——
工具挂了也归到后者。**这不是模型的锅。**
改成三档，另加 `知识库读取失败原因`、`能否给通用动作`。

**第三层：一坏全坏。** `fallback_to`（该参照数据里哪一类）只存在 JSON 里，
文件读不出来 → 连"该看材质做工那 10,646 条"都给不了，blocks 全空。

而这件事不该依赖配置文件——**"标签问题该参照材质做工"是分类路由，
靠常识能定**。代码里补 `_KB_FALLBACK_TO` 常量兜底。
改完实测：文件删掉仍能给出 10,646 条 / 12.7% / ¥72.4 万，只是没动作清单。

**顺带修掉一个假承诺：** 免责声明原来写「不是我没查」。
工具失败场景下这句是辩解——数据侧确实没统计，但方案库也没查成。
改成只陈述数据侧：「数据表里就没有这个维度，不是取数漏了」。

### 三、标题也必须分档

`_hd` 原来只有"命中/未命中"两档，失败时写成
「数据里没有「标签脱落」这一类，也没有近似条目——给立项方法」，
可正文紧接着给了 10,646 条 → 标题和正文打架。

改成三档，失败时：「「标签脱落」没有独立统计，方案库这次没读到——先给参照量级」。

### 四、新增 check_kb_fail.py

正常路径跑多少遍都测不到这个 bug，因为故障不会自己发生。
所以**主动制造故障**：改名（文件缺失）+ 写非法 JSON（文件损坏），
在真实链路上跑三条问题，断言：
1. 不出现「知识库里也没有」「暂时没有整理好的动作」这类断言
2. 必须出现「没读到 / 读取失败 / 没取到」
3. 标题不能说"也没有近似条目"

跑完自动恢复文件。

### 六、踩的坑：把服务搞停了，key 丢了

重启服务以加载新代码时做了三件连环错：

1. 用 `DETACHED_PROCESS` 拉起新进程 → 在 bash 子进程里不可靠，
   进程起来了但没监听，日志也是空的
2. 为了排查，`taskkill` 掉两个"残留"进程 → **其中一个是唯一持有 key 的**
3. 再想从进程环境块读 key 时，两个进程的 `CANYU_LLM_KEY` 都是 False

**关键认识：这台机器上的 key 不在用户/系统环境变量里，也不在任何 .env，
只存在于那个 uvicorn 进程的环境块里。杀掉它 = key 消失。**

正确的重启姿势（下次照做）：
1. 先从运行中的进程读出 key（PEB → 0x20 → ProcessParameters → 0x80 → Environment，
   注意**环境块是 UTF-16LE**，按 GBK 解会全是空行）
2. 再停旧进程
3. 用读到的 key 启动新进程
4. 中间不要 kill 掉不认识的 python 进程

本轮验证逻辑（不依赖 LLM 的部分）全部跑通；
需要 LLM 的截图验证要等用户提供 key 后重启服务再做。

### 七、收尾时发现的两件事（v2.8 续）

**① E3 偶发 FAIL 不是 bug，是模型算错了**

连跑 4 次，1 次被校验拦下：`出现事实中没有的数字 ['0.41']`（另一次是 0.42）。

查清楚了：第 3 周真实值 13.75% / 基线 13.53% / `delta_pp=0.22`。
模型把基线记成 13.11，于是 13.75−13.11=0.64？不对——
实际是它自造了 0.42，13.11 这个数**事实包里根本不存在**。

事实包很干净，`delta_pp: 0.22` 明明白白给着。模型多做了
一步"本期减基线"，还减错了。**校验拦对了。**

模板兜底的输出质量也够用：
「第 3 周没有显著异动，不需要归因。检验了第 3 周：退货率 13.75%，
基线 13.53%，偏离 +0.22pp，二项 z 值 0.66，未达到 2 的判定门槛。
这种情况下我不会去编一个归因故事——报告"没有异常"本身就是结论。」

所以修的方向不是放宽校验，而是**别让模型有自己减的机会**。
`_SYS_PROMPT` 里加了一段「差值一律抄，不要自己减」，把
delta_pp / baseline_pct / return_rate_pct / extra_returns_per_100
四个字段点名，并把这个真实案例写进去当反例。

**② 用户给的 Key 无效（不是复制问题）**

`/compatible-mode/v1/models` 返回 401 `invalid_api_key`。
Key 长度 116、无空格、无全角字符，格式没问题，是 Key 本身无效。

而早先跑通的那个是 `sk-ws-H.YILXDRD...`——两个 Key 在 `Y` 之后
第三位就分叉了（L→I、D→L），不可能是同一个。

· `CREATE_NEW_PROCESS_GROUP` 在 Bash 工具的子进程里不顶用，
  父进程一退出子进程就被回收 → 表现为 502。正确做法是用
  Bash 的 `run_in_background`，命令里 `exec` 顶替 shell，服务才活得下来
