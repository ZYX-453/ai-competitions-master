# 差评炼金炉 · 归因诊断 Agent

> 第一届中国 AI 管理实践挑战赛 ｜ 赛道一 ｜ 市场营销与客户洞察

一个能**自己决定查什么、查完再决定下一步**的退货归因系统。
不是套了壳的报表：它会推翻自己的假设，会在证据不足时直说，
会把"我算不出来"和"数据里没有"当成两件不同的事来讲。

## 三分钟跑起来

```bash
cd agent/backend

# Windows (cmd)
set CANYU_LLM_KEY=你的key
"C:\Program Files\Python311\python.exe" -m uvicorn main:app --port 8848

# macOS / Linux
export CANYU_LLM_KEY=你的key
python -m uvicorn main:app --port 8848
```

打开 <http://127.0.0.1:8848> 就是完整应用（前端产物已在仓库里，不用装 node）。

**没有 Key 也能跑。** 不设 `CANYU_LLM_KEY` 会走确定性模板，
结论、数字、判定全部一样，只是措辞没模型那么自然。界面右下角会标明当前是哪种模式。

Key 用阿里云百炼的（`sk-ws-` 开头）。换厂商设 `CANYU_LLM_BASE` + `CANYU_LLM_MODEL` 即可，代码不用动。

## 它跟"报表"差在哪

同一个问题「第 44 周为什么涨了」，两种系统的区别：

| | 报表 | 这个系统 |
|---|---|---|
| 回答 | 按原因列个占比表 | 先判是不是真异动（z 值 + 业务双门槛） |
| 遇到促销周 | 照旧归因到"破损变多" | 先拆机制与结构，发现是**促销改变了退货倾向**，不是质量变差 |
| 假设被推翻时 | 不会发生 | 抽样读原文后发现"尺码问题"其实是"同码不同大"，**推翻自己上一轮的结论** |
| 数据里没这一类 | 报错 / 空表 | 查本地知识库给通用方案，并明确标注"这是行业经验，不是本店数据" |
| 工具挂了 | 500 | 说"这次没读到"，而不是冒充"没有" |

最后两条是最近两轮才补上的，具体见 [agent/README.md](agent/README.md) 第 11、12 节。

## 界面：六个页面 + 一个问答

打开 http://127.0.0.1:8848 是一个多页面工作台。**页面和问答是两条不同的路径，共用同一批底层函数**：

| 页面 | 回答什么 |
|---|---|
| 总览 | 现在怎么样、哪里最疼（52 周曲线 + 判为异常的周 + 类目/原因排行） |
| 归因 | 这一周为什么涨了（双门槛判定 → 贡献度分解 → 构成对比 → 配对检验） |
| 原因治理 | 9 个原因各自**值不值得管**（按损失排，不按条数排） |
| 评论洞察 | 情感结构 · 抱怨点 · 用户画像 · 分周走势 |
| 竞品雷达 | 我们在同类里处在什么位置（含显著性检验与数据性质） |
| 自检 | 验了什么、在多大的数据上验的 |
| 问答 | 按需深入，让 Agent 自己决定查什么 |

**为什么不是"一个问答页加几个 Tab"**：问答是"我不知道答案长什么样，你替我去查"，
页面是"我知道想看什么，一次给我看够"。前者需要 Agent 动态决策，后者需要固定查询、
横向可比。硬塞在一起，结果就是页面上出现一堆下拉框让用户自己拼查询。

**数字只有一个来源**：页面上每个数都由后端算完再下发（连百分号都算好），
前端不许出现 `* 100` 之类的换算。这条边界是踩坑换来的——左栏曾经写死着
"年订单 64.7k / 退货率 14.6%"，数据重建到 61.8 万单 / 13.53% 后没人记得改前端，
于是页面上常驻着一个三个版本之前的数字。正文写错只在回答时出现，这个数字每一屏都在。

**判据也只有一个来源**：页面上"哪周异常"直接调 `diagnose_week`，
和 Agent 回答"第 10 周异常吗"是同一个函数。阈值不另抄一份——
抄了迟早分叉，而分叉之后页面和问答会给出不同答案，且都没报错。

## 数据从哪来

**两层来源，承担不同论证任务**，这一点是整份材料能不能站住的关键：

| 层 | 内容 | 用来证明什么 |
|---|---|---|
| 真实文本 | 2.15 万条电商评论（监控 13,500 + 训练 8,000） | 归因能力——模型面对的是人写的脏话、错别字、情绪 |
| 模拟面板 | 158 SKU × 52 周，含两级传导真值 | 方法可靠——因为**知道真值**，才能验证"算出来的因果对不对" |
| 竞品语料 | 4 个竞品 × 各 1,040 条，标定后生成 | 竞品对比的**方法可验证**——不是行业实测数字 |

模拟数据不是能力不足的妥协，是刻意设计：真实数据没有反事实，
你永远无法证明「发现了促销机制」这个结论是对的。详细的 DGP 设计和
参数回收检验见 [reports/README.md](reports/README.md)。

> ⚠️ 仓库里的 `data/processed/*.csv` 被 `.gitignore` 排除（最大的 9.9MB）。
> 需要数据请跑 `python scripts/build_dataset.py`（种子固定，产出完全一致）。

### 关于"自动爬取评论"

需求里最直接的理解就是写个爬虫去抓竞品评论。**这个项目不实现它**，理由不是做不出来：

| 理由 | 说明 |
|---|---|
| 违约 | 平台服务条款明确禁止，商家账号一旦被抓到，连带店铺受影响 |
| 寿命以周计 | 反爬一改版就失效。建立在它上面的分析，每几周就要重写采集层 |
| 样本天然有偏 | 平台只展示前 N 页、默认"推荐排序"，抓到的不是全部评论，而是平台愿意给你看的那部分 |

替代方案是**可插拔采集器**，把"能自动"和"必须有人"分清：

| 渠道 | 自动化 | 要人做什么 |
|---|---|---|
| 公开学术语料采样 | 全自动 | 不需要人 |
| 平台后台导出 → inbox → 自动导入 | 半自动 | 登录后台点一次导出 |
| 官方开放平台 API | 全自动（需资质） | 一次性申请应用 + 店铺授权 |
| 人工粘贴 | 无 | 全部 |

关键在第 2 行：**登录态留在人手里，就是这条路径合规的全部理由。**
机器要"自动登录"，就越过了那条线。

问 Agent「你的评论数据是从哪来的」会直接答出这张表——不藏在文档里。

```bash
# 看清单 / 预演能导入多少条 / 真的导入
python -m tools.collectors --list
python -m tools.collectors --scan --dry
python -m tools.collectors --scan
```

## 评论分析四件套

除了退货归因，Agent 还能直接回答评论层的问题。这四个模块的共同约束是：
**不许读标签**。

`corpus.csv` 里物理上没有 `label` 列——不是靠约定说"别用"，是它根本不在。
所以"准确率 95%"是真的判出来的，不是和标准答案对了一遍。

**仓库里有两个带真值的文件，它们不是分析输入，请注意区分**：

| 文件 | 为什么在里面 | 谁能读它 |
|---|---|---|
| `data/processed/reviews_competitor.csv` | 竞品语料的**构建素材**，`scripts/build_review_corpus.py` 读它拆成公开列 + 真值列 | 只有构建脚本 |
| `data/review_pool/_corpus_truth.csv` | 上面那步拆出来的真值，`check_*.py` 算准确率时用 | 只有验收脚本（已在 `.gitignore`） |

运行时链路（`main.py` → `pages.py` → `tools/review_tools.corpus()`）**只读 `corpus.csv`**，
且 `corpus()` 读进来第一件事就是把 `label`/`cause_l1`/`cause_l2` 删掉——
即使将来有人往 corpus 里补了真值，下游也看不见。

| 能力 | 问法示例 | 关键设计 |
|---|---|---|
| 情感分析 | 帮我分析一下评论的情感 | 词典 + 否定窗口 + 转折压制；星级只做兜底且单独计数 |
| 词云 | 差评都在说什么 | 按 **log2 lift** 排序，不是按频次 |
| 用户画像 | 用户画像是什么样的 | 只统计语言证据，每条结论挂原话，并明写"回答不了什么" |
| 竞品对比 | 我们和竞品比怎么样 | 两比例 z 检验，不显著的差异不写进结论 |

**词云为什么不用频次**：差评里出现最多的词是"苹果 182 次""蒙牛 130 次"——
它们是本店在卖的生鲜 SKU，在好评里一样多。频次高只说明这个 SKU 卖得多，
不说明它是抱怨点。改用 `log2(差评出现率 ÷ 好评出现率)` 之后，
商品名自动沉底，Top10 变成：坑人 / 差劲 / 失败 / 发霉 / 一星 / 不透气。

**画像为什么不预测人群**：评论里没有年龄、性别、收入。
任何画像里出现这三项都是编的，所以代码里直接把这三项列进 `cannot`，
并且这个东西显示在画像块**内部**——不是脚注，不是折叠区。

### 验收

```bash
python agent/backend/check_review_analytics.py    # 31 条断言
```

覆盖：22 条踩坑句的极性判定、全量准确率、词云可回溯性、画像原话与信号的一致性、
竞品排序与 DGP 真值的 Spearman 相关、以及**Agent 出口契约**（block 字段能不能被前端读到）。

最后一类断言是补上的教训：分析层全对、界面上却一片空白——
因为 `collector_status` 返回的 data 里少了一个 `ok` 字段，
`col.get('ok')` 恒为 `None`，整块采集器表格永远不渲染。
这类错不会让任何数字变错，所以前 26 条断言全绿。

## 怎么核对（不用读代码）

```bash
cd agent/backend

python run_all.py            # 8 条行为用例：走对工具了吗、徽章对吗、数字编了吗
python check_complaints.py   # 12 条措辞用例：用户投诉过的那几句话回来了吗
python check_kb_fail.py      # 3 条故障用例：把知识库文件改坏，看它说不说假话
python check_review_analytics.py  # 31 条评论分析用例（含出口契约）
```

四套测的是四件不同的事，缺一不可：

- `run_all` 测**行为**——但测不出措辞。用户投诉的"样本量不足"发生在文案上，行为完全正常。
- `check_complaints` 测**说了什么**——把用户原话逐条重放，全文搜禁用语。
- `check_kb_fail` 测**坏了会怎样**——正常路径跑多少遍都测不到，因为故障不会自己发生。
- `check_review_analytics` 测**分析对不对 + 出口能不能被前端读到**——
  最后一类是补课：前 26 条全绿而过，界面上采集器表格却是空的。

最后一步是真的截图看。代码改了 ≠ 屏幕上没有。

## 已知局限

写在代码里，也写在这里：

1. **两类归因混在一个指标上**——数量传导和结构传导在面板上是同一个退货率，
   需要额外拆解才能分清。目前靠 z 值和促销机制校验，不是根本解法。
2. **知识库只有 8 类原因**——覆盖服饰/家居常见问题，生鲜的冷链、临期没做。
3. **模型偶尔算错减法**——实测过一次 13.75−13.53 写成 0.42。现在提示词强制
   "差值一律抄 `delta_pp`，不要自己减"，数字校验也会拦，但这是概率性防护。
4. **单店单周期**——没有跨店铺对比，也没有时间序列预测。
5. **竞品语料是模拟的**——4 个竞品各 1,040 条，按标定参数生成而非实时抓取。
   界面和导出里每行都标了「种子批次」，就是为了不让这些百分点被当成行业实测。
   它能验证分析链路（排序与真值 Spearman ρ=1.00），不能用来引用行业数字。
6. **画像不含人群属性**——评论里没有年龄/性别/收入，所以画像只有"说了什么"，
   没有"是谁"。这不是暂缺，是数据本身就不支持，界面上写在画像块内部。
7. **词云在无极性场景会显示商品名**——按频次排序时"质量""苹果"必然靠前。
   块标题会标明「按出现次数排序」，摘要里也会说清这一组没有做区分度校正。
   要看抱怨点必须限定差评。
