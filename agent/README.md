# 差评炼金炉 · 归因诊断 Agent

> 把「这周差评为什么涨了」变成一条**带证据、可核对**的归因链。

## 一、怎么跑起来

**先装依赖**（只需一次，Python 3.10+）：

```bash
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt     # Windows
# .venv/bin/pip install -r requirements.txt       # macOS / Linux
```

依赖只有五个：`fastapi`、`uvicorn`、`pandas`、`numpy`、`jieba`。
`matplotlib` 不在里面——只有重画 `reports/figs` 那 10 张图时才需要。

**最省事的方式：双击 `start.bat`**（Windows）。它会自动定位 Python、按需构建前端、然后启动服务，完成后打开 http://127.0.0.1:8848 即可。

命令行：

```bash
# Windows
start.bat

# macOS / Linux / Git Bash
./start.sh

# 或者手动启后端（前端已构建好的前提下）
cd agent/backend && python main.py
# http://127.0.0.1:8848
```

> `start.sh` 会按 `项目根/.venv` → `工作区根/.venv` → `Python311` → `PATH` 的顺序找 Python，
> 找到后先做一次 `import fastapi, uvicorn, pandas, numpy, jieba` 自检。
> 缺依赖会当场说"缺哪个、怎么装"，而不是等 uvicorn 抛一句 `ModuleNotFoundError`。
> 端口被占也会直接报出来，可用 `PORT=8849 bash start.sh` 换端口。

> 后端同时托管 API 与前端静态产物，**单端口**即可访问完整应用，不需要开两个服务。

> ⚠️ **Git Bash 里不要用 `set` 设 Key**。Bash 的 `set` 是设 shell 选项/位置参数，
> `set CANYU_LLM_KEY=xxx` 不会创建环境变量——服务照常启动、端口正常、界面能开，
> 但读不到 Key，静默走模板模式。**这种"看着成功其实没成功"最费时间**。
> Git Bash 必须用 `export`（见下）。

## 二、为什么这是一个 Agent，而不是套了壳的报表

判断标准只有一条：**下一步做什么，是不是由上一步的结果决定的。**

本系统在真实数据上跑出过五条完全不同的执行路径（见 `/api/eval`，可一键复跑）：

| 提问 | 实际路径 | 为什么这样走 |
|---|---|---|
| 第44周退货率为什么涨了 | overview → diagnose → promo_mechanism → attribution → loss → samples → playbook → value（8 步） | 检出异常，且该周带促销标记，必须先验证是不是促销机制 |
| 最新一周差评有异常吗 | overview → diagnose → **diagnose(44)** → …（9 步） | 最新周 z=−0.69 不显著，自动重定向到真正异常的第 44 周 |
| 第3周为什么异常 | overview → diagnose（2 步，停） | 10,274 单样本充足，但 z=+0.66 不显著，**直说这周不是异常周** |
| 第49周怎么回事 | overview → diagnose → trend | z=−5.10 显著**下降**，是好事，不套用归因模板 |
| 补偿补多少最划算 | compensation_curve → value | 走权衡分析路径，不求归因 |

五条路径共用同一套工具、同一份数据。**换一个问题，路径就变**——这是与流水线最本质的区别。

## 三、它做对了什么（这几条是可以被质疑、也可以被核对的）

### 1. 主动推翻了一个"看起来很合理"的因果故事

看到「双11 退货率涨了」，最自然的解释是"爆单导致履约崩盘、破损变多"。
系统没有接受这个直觉，而是做了三重检验：

| 检验 | 结果 | 结论 |
|---|---|---|
| 订单结构是否偏移 | 结构效应 **−0.31pp**，仅占涨幅 7% | 不是选品或流量结构问题 |
| 同 SKU 配对比较 | 150 个 SKU 中 **98%** 自身退货倾向上升，均值 **+3.93pp**，**t = 17.72** | 机制确实存在 |
| 是否降价 / 推低质商品 | 降价 SKU 占 **0%**，质量均值反而略升 | 排除"低价低质"解释 |

结论：**促销这个动作本身改变了退货倾向**，治理方向是下单预期管理，而不是去查供应链。

如果换成"破损变多了"这个直觉答案，会指向完全错误的动作（去换包材、罚承运商），钱花下去退货率不会动。

### 2. 换掉了一套会算错符号的检验

这里最初用的算法是"周间标准差"：拿每周退货率算个标准差，再把本周偏离除以它。看起来没问题，而且大多数周确实算得对——错的只在两头。

**真正的问题不是"朴素 z 总是把噪声放大"，而是它的偏误方向会随样本量翻转，而使用者看不出自己正站在哪一边。**

朴素 z 的分母是周间标准差 `sd`（一个固定值），而真实抽样误差是 `√(p(1−p)/n)`（随 n 收缩）。令两者相等，得到分界点：

```
n* = p(1−p) / sd²
```

| 该周样本量 | 真实抽样误差 | 朴素 z 的分母 | 后果 |
|---|---|---|---|
| n < n\* | 大于 sd | **偏小** | 偏离被放大 → **假警报** |
| n > n\* | 小于 sd | **偏大** | 偏离被压低 → **漏报** |

全店基线 13.53%、周间 sd 1.02pp 时，n\* ≈ **1,115 单**。（n\* 随基线小幅浮动，逐周实算会在这个量级上下。）

这个数字很要紧：**当前数据里最低的一周也有 7,548 单，是分界点的 6.8 倍。**也就是说，在这份数据上朴素 z 根本不会虚报——它只会漏报。

实际扫描 52 周的结果：

```
朴素 z 判显著（|z|≥2）：           3 周 —— 第 44、48、24 周
二项 z 判显著（|z|≥2 且 n 达门槛）：  5 周（再加第 36、49 周）
前者是后者的真子集
```

被朴素 z 漏掉的是第 36 周（+1.77pp，朴素 z 约 1.7、二项 z 6.42）和第 49 周（−1.84pp）。
下面第 7 节会讲到，最终判定还要再加一条业务幅度门槛，所以这 5 周里又只留下 4 个"值得动手"的。

所以口径统一换成二项 z：

```
z = (本周退货率 − 基准率) / √(p(1−p)/n)
```

分母里有 n。样本量一进分母，缩放关系就对了。同时门槛按各类目基线反推（见第 6 节），不再写死一个数。

> **这里必须记一笔错。** 第一版文档把这件事写成"朴素 z 会把小样本周的抽样噪声误判为异动（第 3 周 151 单，朴素 z −3.7，二项 z 仅 −1.9）"。那个例子在 v2.3 数据上确实成立——151 单远低于 680 的分界点。但补完样本量之后，第 3 周变成万单级、二项 z +0.66，**结论方向整个反了**。我照着旧结论去核对时，差点把一句说反的话当成"已知事实"保留下来。
>
> 更要命的是，这段话当时**硬编码在 `evidence.why_binom` 里**——那是界面上推理链点开就能看到的证据。文档写错可以改，界面上的证据写错等于当场骗人。现在这段文案改成按本周实际的 n 与 n\* 动态生成，并且区分三种情形（低于 n\* / 接近 n\* / 高于 n\*）。

### 3. 该说"不知道"的时候真的说了

这条现在要换个说法讲，因为数据补完之后，"样本不足"的样本变少了。

**先说结论：系统仍然拒绝硬凑归因，但判断"能不能下结论"用的不是拍脑袋的门槛，而是这个样本量物理上能分辨多大的变化。**

以数码类目第 52 周为例（286 单，是四类目里最低的）：

```
数码第 52 周：286 单
  基线退货率 10.28%
  判定门槛 410 单（按基线反推，目标为 3pp 检出幅度）
  可分辨幅度 3.59pp —— 低于这个数的变化落在噪声里
  本周实际变化 −0.49pp → 不构成结论
```

系统的答复不是"样本不足"，而是：

> 这一周不需要开整改动作。理由很具体：286 单的样本量，只能看清 3.59 个百分点以上的变动，而实际变化只有 −0.49 个百分点。

第 49 周则是另一种情形——9,042 单，**样本完全够**，偏离 −1.84pp、z = −5.10 显著下降，判定为**改善**，只拉一段趋势看是否持续，不做归因。不是问题就不该套归因模板。

### 4. 知道自己不该答什么（对抗测试挖出来的四类边界）

这四条不是在"已知用例"里发现的，而是**故意拿越界问题去撞**才暴露的。
其中前两条是产品级硬伤，共同点是：**它不报错，只是安静地答错。**

| 你问 | 旧行为（错） | 现在 |
|---|---|---|
| 第 60 周退货率为什么涨了 | **当作"没指定周次"，转头分析第 44 周**，给出一份完整但答非所问的报告 | `parse_week` 返回 `-2` 哨兵 → 前置拦截：「数据只覆盖第 1–52 周，第 60 周没有订单记录。我不会拿别的一周来顶替」，0.0s 返回 |
| 帮我写一首诗 | `classify_intent` 末尾无条件 `return 'diagnose'` → 走完整诊断流程，输出三段退货率分析 | `is_in_scope` 前置闸：命中业务词放行 / 命中强越界词拒绝 / 其余放行（**宽进严出**，漏答与误拒代价不对等） |
| 第44周和第41周哪个更严重 | 只解析第一个周次 44，其余当作没问，只答一半 | `parse_weeks` 取全部周次 + `compare` 意图（**必须最先判**）+ `compare_weeks` 工具，共同基线、按 z 排序、排序依据外显 |
| 生鲜类目怎么样 | 答成「生鲜第44周退货率异常升高」，标题不写范围，读者以为 18% 是全店数字 | `_headline` 加类目前缀；事实包加「分析范围」字段；提示词铁律 2 要求首段交代范围 |

**静默降级比显式失败危险得多**：显式失败用户会重问，静默降级用户会**拿走一份错的报告去开会**。

多周对比还额外解决了一个统计问题——**排序依据必须说清楚**：

```
按 z 值排（不是按退货率排）   ← v2.4 数据
第44周  17.04%  偏离 +3.64pp  z = 16.13  样本 22,769 单  → 显著上升
第24周              z = 10.07  样本 19,153 单  → 显著上升（促销周）
第49周              z = -5.10  样本  9,042 单  → 显著下降（改善）
第 3周  13.75%  偏离 +0.22pp  z =  0.66  样本 10,274 单  → 在噪声内
```

退货率最高不等于问题最大：样本少的周，同样的百分比更可能是噪声。
所以正文必须主动交代"为什么这么排序"，否则读者拿退货率一对照，会觉得系统在胡说。

### 5. "一直在说第 44 周"是怎么解决的

这是上线后最刺眼的问题：不管问什么，答案最后都指向第 44 周（双11 促销周）。

**追下去发现是三层问题叠在一起，前两层在数据、第三层在逻辑：**

| 层 | 现象 | 根因 | 修法 |
|---|---|---|---|
| 数据 | 前 9 周订单量曾只有 79→737 单，全在判定门槛以下 | `launch = randint(1, 22)` 让 158 个 SKU 分散在 1–21 周上新，前几周只有 6 个 SKU 在架 | 79% 的 SKU 第 1 周即在架，其余分散上新（保留爬坡形态，但不再把样本量打到门槛以下）。修后前 9 周 1.3–2.1 万单，全周期最低 7,548 单 |
| 数据 | 数码类目曾全周期周均仅 64 单，**永远**到不了门槛 | 数码 CVR=0.019 偏低，34 个 SKU×低转化 = 结构性低样本 | CVR 提到 0.078（3C 配件决策链短，仍在合理区间），修后周均 2,372 单、最低 1,395 单；客单价仍是四类目最高 |
| 逻辑 | 问哪个类目都跳到第 44 周 | `_scan_anomaly()` **不接受类目参数**，永远扫全店；全店唯一站得住的异常只有 44 周 | 加 `category` 参数：问数码就只在数码里找，没有就老实说没有 |
| 逻辑 | 问第 3 周也答第 44 周 | 只要"不异常"就无条件重定向 | 加 `week_pinned_by_user`：**用户报了周号就不许换题**，重定向只用于「最新一周/大盘」这类不绑定具体周的问法 |

修完之后，同一句话的回答从"第 44 周怎么回事"变成：

> **HEAD: 第3周退货率未显著异常，无需归因**
> 第3周退货率 13.75%，较基线 13.53% 上升 0.22pp；z = +0.66，未达 |z|≥2 门槛；
> 样本量 10,274 单远超最低要求，**判断依据充分可靠**。
> 这一周**本来就不是异常周**，不存在需要归因的问题——报告"无异常"就是核心结论。
> 真正显著异动发生在第 44 周，**与本次分析无关**。

第 44 周被降级成一句附注，而不是主旨。

一个细节值得记：`"第 52 周"` 和 `"最新一周"` 最终都解析到 52，
但重定向许可完全不同 —— 前者是点名要看这周，后者只是问"现在有什么问题"。
最初没区分，导致「最新一周差评有异常吗」再也走不到重定向，答案永远停在"这周没问题"。

### 6. "样本不足"改成"能看清多大的变化"

原本遇到小样本只会说「样本量不足以支撑任何归因，因此不派动作」。
用户听完只会换个问法再问一遍，得到的还是同一句。

**改法是把"不能看什么"换成"能看什么"**：用 `n = (2/Δ)²·p(1−p)` 反推，
告诉用户这个样本量能分辨多大的偏离。

```
数码类目第 52 周：286 单
  判定门槛 410 单（按该类目 10.28% 基线反推，目标为可分辨 3pp）
  可分辨幅度 3.59pp —— 低于这个数的变化，本来就不该开会讨论
  本周实际变化 -0.49pp → 落在噪声里
```

同时**门槛不再写死 300 单**。旧写法有个隐含偏见：由公式反推，
300 单在退货率 27.75%（服饰）时只能分辨 4.8pp，在 7.2%（个护）时能分辨 3.1pp ——
同一个门槛对高退货率类目更宽松、对低退货率类目更严格，而且从不告诉用户这件事。
现在门槛按各类目基线浮动，在目标检出幅度上对四个类目是**一致**的：

| 类目 | 基线退货率 | 判定门槛 | 旧固定门槛 |
|---|---|---|---|
| 服饰 | 27.80% | 893 单 | 300 |
| 生鲜 | 13.14% | 508 单 | 300 |
| 数码 | 10.28% | 410 单 | 300 |
| 个护 | 7.25% | 299 单 | 300 |

另加一条 `suspicious_but_small`：偏离已超过可分辨幅度、但样本仍不够判定时，
明确写成"疑似异动、但样本不足以下结论"，而不是笼统归到"没问题"里。

### 7. 把样本补够之后，冒出了反方向的病：什么都显著

上一节解决的是"样本太少看不出"。补完样本之后，它的孪生兄弟立刻出现了。

**先看缺口有多大。** 目标检出幅度 3pp 下，按 `n = (2/Δ)²·p(1−p)` 反推各类目的判定门槛：

| 类目 | 周均单 | 最低周 | 基线退货率 | 判定门槛 | 需放大 |
|---|---|---|---|---|---|
| 服饰 | 314 | 189 | 27.75% | 892 | **5.19×** |
| 数码 | 382 | 215 | 10.27% | 410 | 2.10× |
| 生鲜 | 682 | 434 | 13.18% | 509 | 1.29× |
| 个护 | 542 | 332 | 7.21% | 298 | 1.00× |

服饰最紧，**不是因为订单最少，而是因为它退货率最高、门槛也最高**（27.75% 要 892 单，
7.21% 只要 298 单）；而服饰 CVR 恰好又是四类目最低（2.19%）。两个因素叠在一起，
于是"服饰类目第 52 周 244 单，样本不足以下判断"变成了默认答复。

**修法的选择比数值更重要。** 有三条路：拉 CVR、加 SKU、放流量。

- 拉 CVR 改的是"转化能力"，那是经营水平，不是数据规模。服装 2.19% 本身合理
  （货架式浏览、决策链长），硬拉到 10% 才叫真失真。
- 加 SKU 会稀释单 SKU 动销——本来每 SKU 周销 5 单就已经不健康了。
- **放流量只改规模这一个自由度**：CTR、CVR、退货率、类目排序、价格带、促销弹性全不动。

选了第三条，`SHOP_SCALE = 6.0`（最紧的服饰要 5.19×，留 15% 余量让四季波动里最低那周也过线），
只加在曝光方程的截距上：`ln_exp = 6.42 + ln(6) + …`。截距是纯水平项，
加常数等于所有人的曝光同乘 6，而 ω1、ω2、θ 这些弹性与 sku_fe、wk_eff 的异质性原封不动。

结果：年订单 10.0 万 → **61.8 万**，GMV 1,124.6 万 → **7,004.8 万**，单 SKU 周销 12.2 → 75.2 单。
**四个类目 × 全部 52 周，样本不足周数 = 0。**

> 顺带验证了一件事：放大流量后参数回收反而更准了。λ1 估计 1.2985（真值 1.30，误差 **0.11%**），
> ω1 误差 2.0%，ω2 误差 4.9%，都优于上一版。因为改动只在截距，而样本量增加直接提升了识别精度。

**但样本一够，新的错法立刻出现：什么都能验成显著。**

全店周均 1.19 万单，3pp 门槛只要 521 单，余量 20 倍。此时 z ≥ 2 只需要 **0.63pp** 的偏离。
52 周里有 **22 周**判"显著异常"，其中 8 周偏离不到 1pp——统计上完全站得住，
运营上毫无意义。一个 13.5% 的退货率上下浮 0.6pp，不值得开复盘会。

两种错法其实是一回事的两端：

| 样本 | 症状 | 用户感受 |
|---|---|---|
| 太少 | 假阴性，真实异动淹没在噪声里 | 这系统什么都不说 |
| 太多 | 假阳性，日常抖动被验成显著 | 这系统天天报警 |

单靠 p 值解决不了第二端，因为 **p 值只问"是不是巧合"，从不问"这事儿大不大"**。

所以判定改成**双条件**：

```
is_anomaly = (z ≥ 2)  AND  (|偏离| ≥ 1.5pp)
             统计显著          业务上值得管
```

`MIN_EFFECT_PP = 1.5` 是业务口径，不是统计口径，写成显式常量就是为了让它可商量、可改，
而不是藏在某个人对"显著"的默认理解里。改完：显著周 22 → **5**，
且留下的都是大偏离（第 44 周 +3.64pp、第 48 周 +2.98pp、第 24 周 +2.48pp 三个促销周，
加第 36 周 +1.77pp、第 49 周 −1.84pp）。

还有一支不能省：**统计显著但幅度不值一提**（`trivial_but_significant`，17 周）。
它既不能并进"异常"（给不出有意义的动作），也不能并进"没事"——
用户自己一算 z 会发现确实过了 2，那时说"没事"就是瞒事。所以单独说：

> 第 52 周偏离 −0.98pp，z = −2.84，**统计上确实显著**——不是巧合。
> 但公司定的动作触发线是 1.5pp，这个幅度只到它的三分之二，
> 属于"能测出来、但不值得动手"的那一类。

### 8. 同一份数字被贴上两个类目的标签

数据补够之后紧接着暴露的，是一个更隐蔽的问题。

问「数码的退货率为什么新高」和问「服饰类目怎么样」，两份报告里：
机制贡献都是 **3.98pp**、配对 t 都是 **15.8**、都是"**151 个 SKU** 中 97% 上升"。

数字本身是真的——全店确实如此。但它回答的不是用户问的那件事。
根因是 `promo_mechanism()` **不接受 `category` 参数**，`_args()` 里也没有对应分支，
于是永远返回全店结果，再用"数码"/"服饰"这两个词分别包装一遍。

**这比数字过期更危险**：过期只是不准，这个是"准确的无关联"。
用户拿它去开数码的复盘会，会发现全场找不到那 151 个 SKU。

修完之后两组数字才真正分开：

| 范围 | 实际涨幅 | 机制贡献 | 配对 SKU | t 值 |
|---|---|---|---|---|
| 数码 | +2.46pp | +2.57pp | 32 | 7.32 |
| 服饰 | +7.34pp | +6.09pp | 61 | 13.59 |
| 全店 | +3.28pp | +3.98pp | 151 | 15.80 |

限定单一类目时，"结构效应"在定义上恒为 0（只有一个类目，占比永远 100%），
这不是缺陷而是口径使然——类目内部的涨跌不可能由类目构成变化解释。
所以工具会在 `evidence` 里明说这一点，避免读者把 0 误解成"没有结构问题"。

### 9. "你好你是谁"不该收到一张拒绝卡片

用户第一句话是「你好你是谁」，系统回的是：

> **超出范围** · 这个问题不在我的能力范围，我不硬答
> ……写诗、翻译、闲聊这类事我不做——勉强答出来只会让你误以为我什么都懂。

用户只是打了个招呼，却收到一段防御性声明，而且完全不知道这家店的退货率是多少。

**这不是范围问题，是接待问题。** `is_in_scope` 只有"能答/不能答"两档，
而这里需要第三档：不答，但告诉对方该问什么。

所以把 `你是谁`/`你叫什么`/`你能做什么`/`你好` 从越界词里拿出来，单独走 `is_greeting`。
`is_in_scope` 仍返回 True（它不是越界），问候分支排在它前面，并且**顺手拉一次大盘**，
让自我介绍带上真实数字：

> 先说手头的数据：这家店近 52 周 **618,058 单**、GMV **¥7,004.8 万**、
> 整体退货率 **13.53%**，全年退货损失约 **¥531.2 万**。这些数我都能拆到类目、拆到周、拆到具体原因。

第一句话就让人知道这个系统是活的、有数据的、能问出东西的——这比任何功能列表都有说服力。

有一个边界必须守住：**带业务词的问候不算问候**。「你好，第44周为什么涨」仍然是诊断问题，
不能因为句首有"你好"就走自我介绍。

### 10. 「尺码版型不符怎么解决」返回了第 44 周报告

用户问「尺码版型不符这个问题该怎么解决」，系统回了一整份「第 44 周为什么涨」——
6/6 步推理链完整、数字全对、结论自洽，但**没有一句话在讲尺码问题怎么解决**。
「尺码版型不符」只在原因结构表里露了一面（12.5%、484 条）。

这种错比数字算错更隐蔽：每一处都站得住，唯独答的不是他问的事。

**四层缺陷叠在一起，缺一层都不至于答错：**

| 层 | 缺陷 | 后果 |
|---|---|---|
| 意图分类 | 关键词表只收「怎么办/怎么做」，没收「怎么解决」 | 判成 `diagnose` |
| 工具规划 | `action` 序列第一枪固定是 `diagnose_week` | 话题被拉到第 44 周 |
| 参数传递 | `action_playbook` 只认 P1/P2 代码，收到中文名就返回 `ok=False` | playbook 从未产出过 |
| 数据检索 | `review_samples` 用中文名去筛 `cause_l2`（存的是 P1/P2） | 差评原文从未出现 |

第三、四条最阴——**它们不报错，只安静返回失败**。上层拿到空 playbook，
最后写出一句「无事实支撑」，而链路上每个工具都显示"已调用"。

**修法不是改文案，是加一条独立路径。** 因为这两类问题需要的证据完全不同：

|  | 周度异动 | 单原因治理 |
|---|---|---|
| 核心问题 | 这一周发生了什么 | 这个毛病有多重、该做什么 |
| 证据 | 基线、z 值、促销拆解 | 条数、损失、差评原话、动作手册 |
| 与周次关系 | 强 | **无关**（尺码问题不是某一周才有的） |

新增工具链 `reason_profile → review_samples → action_playbook`，
`reason_profile` 按"原因"组织而不是按"周"——这是此前缺失的视角：
所有工具都是按周组织的，没有一个是按原因组织的。

**看完真实原文，结论被推翻了。** 原以为尺码退货 = 尺码表不清楚，
原文里却是：

> 「买两条30码，就发来一条31码，大一码叫人怎么穿，还有再买一条30码和之前的30码大了点，**同码的裤子，居然不一样大**」

这是生产公差/批次管理，**加尺码选择器治不好**。所以结论段从"第一条最见效"
改成了"别照着这个顺序做"，并把优先级倒过来：先查批次、再压一致性、最后才补选择器。

这个改动引出两个数据细节，都反直觉：

| 发现 | 数字 | 含义 |
|---|---|---|
| 98.4% 集中在服饰 | 10,238 / 10,802 条，占该类目退货 **34%** | 生鲜仅 2.0%，不该并列 |
| 单均损失只有全店 58% | ¥37.01 vs ¥63.51，可二次销售 81.5% | 退得多但每单不贵，亏运费不亏货值 |
| 近 12 周在收窄 | −0.64pp | 不该报红、不该过度投入 |

**三处踩过的坑，都属于"证据被自己切掉"：**

1. `_args` 里 `review_samples` 写死 `limit: 5`，而"同码不同大"那条排在第 7 条 —— 证据根本没进事实包。
   修法不只是调大数字：取样从 `head(limit)` 改成等距抽样，因为行序没有任何业务含义。
2. 引语按 `t[:58] + '…'` 硬切，"不一样大"正好落在第 59 个字之后 —— 证据在最关键处断了。
   改成先定位证据词再开窗口，且证据词**按信息量排序**（"不一样大"优先于"大一码"）。
3. 叙述写死了"这两条抱怨的是同码不同大"，但排序后挑中的第二条恰恰是「L号都那么大」——
   一句话否掉了自己刚引的证据。改成按实际挑中的原文分组，再决定说什么。

### 11. 用户问的原因，数据里根本没有这一类

原因结构表只有九个取值。用户问「标签脱落怎么解决」，一个都对不上。

旧行为：`action_playbook` 返回"未收录原因" → 整份回答退化成拒绝。
用户明明有这个问题，却被告知"你这功能没用"。

**三种做法，只有一种对：**

| 做法 | 结果 |
|---|---|
| 说"未收录原因" | 用户觉得这功能没用，而他的问题真实存在 |
| 编一套数字（"标签问题占 8%"） | 造假，一追问就崩 |
| **说清边界 + 给通用做法 + 用最接近的真实数据做参照** | 用户拿到手能动手 |

所以加了本地知识库 `data/reason_kb.json`（8 类原因，每类含征兆、动作、责任方、KPI、易混淆点），
以及工具 `reason_kb`。路径是 `reason_kb → reason_profile`（后者按 `fallback_to` 查替代口径）。

**最难的不是接线，是"别把两种可信度混着说"。**

知识库的动作是行业经验，替代口径是本店真实数据。写成
「标签问题占退货 12.7%」——那个数其实是材质做工的，标签一条都没统计过。
运营拿这句去汇报，就是在会上说错数。

所以做了三件事：

1. 返回值带 `source_tier`，事实包分成「知识库兜底」和「替代口径数据」两块，物理隔离
2. 专用提示词 `_SYS_PROMPT_KB`（不能复用周度诊断那套——它会去找不存在的"促销机制"字段，找不到就编）
3. 出口加一道 `_verify_kb_numbers`：替代数字出现时，同一段必须有"参照/不是/不代表"这类限定词

第四件事是踩出来的：`_verify_llm_output` 的校验 4 规定"没有 playbook 就不许提动作"，
而知识库路径本来就没有 playbook，模型一写"建议先做批次留样"立刻被判失败，
两次重试全废、回退模板——**而模板里的动作恰恰也是知识库给的**。
改成：知识库场景拿知识库的动作文本当白名单比对，编造动作照样拦得住。

**还有三个措辞错误，都是同一个根因——把"你说的""我归到的类""数据里的类"三个概念混用：**

| 错法 | 为什么错 |
|---|---|
| 「数据里没有『标签/吊牌问题』，按最接近的『标签/吊牌问题』给方案」 | 用户原话和知识库类名用了同一个变量，自己跟自己比 |
| 「归到『标签/吊牌问题』——归到材质做工看」 | 引用了 `fallback_reason`，但它讲的是 `fallback_to`，两个类名打架 |
| 「已被纳入『材质做工问题』统一统计」＋「可作量级参照」 | 前面说已并入、后面说只是参照，自相矛盾 |

现在三个名字分开存：`user_reason_text`（用户原话）、`kb_name`（知识库类名）、
`stand_in`（数据里最接近的类）。`_extract_reason_phrase` 从**问句里**抠原话，
不是在别名表里挑最长的——否则用户说"赠品没送"会被削成"赠品"。

### 12. 工具挂了的时候，不能说"知识库里没有"

这一条是第 11 节的影子问题，但它比第 11 节更严重。

第 11 节说的是"知识库查过了、确实没有这一类"，那是**结论**。
而知识库文件被删、JSON 写坏时，是"我没查成"——那是**状态**。
两件事在界面上长得几乎一样，说出来的话却是相反的：

| 说法 | 用户听到的意思 | 他接下来会做什么 |
|---|---|---|
| 「方案库里没有这一类」 | 这个问题无解 | 放弃 |
| 「方案库这次没读到」 | 是我这边的问题 | 再试一次 |

旧代码只有"命中/未命中"两档，工具失败落进未命中，于是写出
「知识库里也没有完全对应的条目」——**假话，它压根没查**。
更糟的是后面紧接着给出了替代口径数字，前面说"没有近似条目"、
后面说"最接近的是材质做工"，自己打自己。

**修的时候连着挖出三层问题：**

**第一层：措辞。** 分成四档——命中 / 未命中 / 工具失败 / 连替代口径都没有。
提示词里单独加一段：「方案库没读到」可以说，「方案库里没有这一类」绝不许说。

**第二层：事实包也在撒谎。** 模型不是自己编的，是我给它的输入就写着
`'知识库是否命中': '命中' if matched else '未命中近似条目'`——工具挂了也归到后者。
这不是模型的锅。改成三档，另加 `知识库读取失败原因` 和 `能否给通用动作` 两个字段。

**第三层：一坏全坏。** `fallback_to`（"该参照数据里哪一类"）只存在知识库 JSON 里，
文件一读不出来，连"该看材质做工那 10,646 条"都给不出来了，整份回答只剩
一句"没读到"，`blocks` 全空。

而这件事本来不该依赖配置文件——**"标签问题该参照材质做工"是分类路由，靠常识能定**。
所以在代码里补了一份 `_KB_FALLBACK_TO` 常量兜底，文件读不出来时用它。
改完实测：文件删掉的情况下依然能给出 10,646 条、12.7%、¥72.4 万这组参照，
只是没有动作清单。

**一个顺带修掉的假承诺：** 免责声明原来写「那些数字不存在，不是我没查」。
在工具失败场景下这句是辩解——数据侧确实没统计，但方案库也没查成。
改成只陈述数据侧的事实：「数据表里就没有这个维度，不是取数漏了」。

专门写了 `check_kb_fail.py`，用**注入故障**的方式跑真实链路
（把文件改名、往里写非法 JSON），检查三件事：
不出现假话、必须承认"没读到"、标题不能说"没有近似条目"。

## 四、界面上几个"看起来能用、其实是错的"细节

这些是逐个截图放大核对后才发现的。列出来不是为了说做了什么，而是它们都会**让结论骗人**。

| 问题 | 表象 | 实际危害 | 怎么改的 |
|---|---|---|---|
| 补偿曲线按数组下标等距画 | 七个档位看起来间隔均匀 | 档位是 0/5/10/15/20/30/50，**¥30→¥50 跨度是 ¥0→¥5 的四倍，却被画成一样宽**。于是"利润在 ¥30 见顶、到 ¥50 断崖"这个最关键的结论被抹平了 | x 轴改成按真实档位映射 |
| SVG 圆点被横向拉伸 | 折线上像粘着几块扁补丁 | `preserveAspectRatio="none"` 把 viewBox 横向放大 9 倍，`<circle>` 变成椭圆；调 `r` 无效（是几何形变，不是描边粗细） | 数据点改用 HTML `div + border-radius` |
| 均值参考线几乎不可见 | 放大截图才发现在 | 参考线的作用就是"一眼看出当前值相对中枢在哪"，看不见等于白画 | 描边加粗到 1px、透明度提到 0.75 |
| 图内标注「均值 14.22%」 | 加了之后曲线起点被底色遮断 | 标注底色遮罩把折线切断，像渲染 bug | 数值挪回卡片说明行，图内只留线——这也是专业图表的惯例 |
| 涨幅拆解条内浮着孤立数字 | 绿色条中间一个 "3.9" | 丢了单位、丢了精度，还和图例重复 | 单段不标；多段标类目名而不是裸数字 |

## 四之二、评论分析四件套：六个"看起来很对"的错

这一节是 v3.1 加的。四个模块（情感 / 词云 / 画像 / 竞品对比）从一开始就跑得通、
数字也像回事——**问题全部出在"像回事"上**。下面每一条都是先看到结果觉得没问题、
后来去读原句才发现错的地方。

### 1. 词云：按频次排会让商品名霸榜

差评词云的第一版 Top3 是 **苹果 182 / 蒙牛 130 / 裤子 113**。
它们是本店在卖的生鲜和服饰 SKU——在好评里出现的次数一样多。
频次高只说明这个 SKU 卖得多，**和"用户在抱怨什么"完全无关**。

第一反应是加停用词表。失败：语料横跨 4 个类目，商品名有几万个，列不完。

真正的解法是换统计量：

```
lift = log2( 这个词在差评里的出现率 / 在好评里的出现率 )
```

商品名的 lift≈0，自动沉底；"坑人""发霉""不透气"这些只在差评里出现的，lift 冲到 7~8。
改完 Top10 变成：坑人 / 差劲 / 失败 / 发霉 / 一星 / 不透气 / 无良 / 受不了。

**代价是没有对照组就没有 lift。** 所以全量统计时必须退回频次排序，
并且明确标 `rank_by='count'`，标题写「全部评论高频词（按出现次数排序）」——
否则读者会把"质量 1792 次"读成"抱怨最多的是质量"。

### 2. 词云：`polarity` 参数收了，但从来没被读过

调用方传 `polarity='负向'` 以为只统计差评，实际拿到全量词频。
不报错、不崩、只是数字悄悄错掉——前端会显示"差评高频词：质量 128 次"，
而这 128 次大半来自好评的"质量不错"。

修的时候又踩了第二个坑：第一版用 `_rating_prior(0)` 做兜底，恒为 0，
等于把"星级兜底"这条路径整个关掉，且关得很安静——差评里"东西收到了"
这类无情感词的评论全部被判中性、从负向集合消失。

正确做法：**极性按整条评论筛，再统计词**。不在词级别判正负，
因为同一个词在不同句子里正负可以相反。

### 3. 画像：原话和它挂靠的信号完全对不上

这一条最严重。`囤货/复购` 挂的原话是：

> 「要想能打电话，看清楚版本再买，唉。很是无语！」

这句话里没有任何"复购"的意思，它是**劝人别买**。

根因是一行看着很自然的代码：

```python
sub = pd.concat([neg_q.head(2), pos_q.head(1)])   # 先拼
...
for _, r in sub.head(3).iterrows():                # 再取前三条
```

`concat` 之后，行序和"命中哪个词"就脱钩了。拿到的不是"命中这个词的那几条"，
而是"这一组里的某几条"。

**这不是显示问题，是证据造假。** 模块头写着"每一条画像结论都要挂着触发它的原话"，
挂错的原话比不挂更糟——它让结论看起来有据，实际是随便找了一句贴上去。

修法两步：
1. `sub = df[mask].copy()` 之后**立刻**算 `_hit`，后续所有筛选都带着这一列；
2. 每条 quote 补 `matched` 字段，前端据此高亮命中词，读者可以自己核对。

顺带写了一条断言：`画像 quote 的 matched 可在句内定位`。反向注入旧 bug 会立刻红。

### 4. 画像：「不会再回购了」被算成复购 + 主动推荐

```
超级小的火龙果，无良的商家不会再回购了
  → 囤货/复购 +1
  → 主动推荐 +1
```

`any(k in t for k in kws)` 不考虑否定。这跟情感分析里"好评被否定句翻转"
是同一个病根，只是换了个模块重现。

修法是加一个 4 字否定窗口：

```python
def _signal_hit(text, kws):
    for k in kws:
        idx = text.find(k)
        while idx >= 0:
            before = text[max(0, idx-4):idx]
            if not any(neg in before for neg in _NEG_BEFORE):
                return k
            idx = text.find(k, idx+1)
    return ''
```

同时清理了两个词表错误：
- **`再买` 必须删**。它是"不会再买"的命中源，方向完全相反。
- **`比较` 必须删**。「屏幕上有一个亮点，好在比较靠边」被记成"比价型"——
  这里"比较"纯粹是程度副词。它在语料里出现上千次，把这一类撑到 841 条。
  修完 841 → 23 条。

### 5. 竞品：数码类目里出现了"合身"和"布料"

```
数码类目评论：「按尺码表买的，上身正合身」
数码类目评论：「材质厚实，洗了一次没变形」
```

这些文本还进了语料池，在竞品对比里表现为「对标在数码类目更常提尺码/布料」。
分析层没错——**是生成层把不同品类的语言混在了一起**。

根因有三层，缺一层都修不干净：

| 层 | 问题 | 修法 |
|---|---|---|
| ① 维度是否适用 | `DIM_CAT_GATE` 只登记了"破损"一条，尺码/材质没门控 | 补全 4 条门控 |
| ② 适用后用什么词 | `{fab}` 槽位用全局词表（料子/面料/布料），数码会生成"手机壳的面料起球" | 新增 `FAB_WORDS`，按类目取词 |
| ③ 维度内部也要拆 | "破损"里混着「生鲜收到还是冰的」这类生鲜专用句 | 拆成「破损/变质/污损」+「变质/新鲜度」两套模板 |

**只做第 ① 层的结果是"数码店在夸外壳做工"——门控放行了，槽位没换。**

### 6. 竞品：本店独有词是"苹果"和"蒙牛"

跨类目对比时，`log_ratio` 最高的两个词是 苹果 6.83 / 蒙牛 5.61。
它们确实是本店独有——因为竞品 B 不卖生鲜。

但这表达的不是经营差异，**是两家店的选品不同**。

修法：特征词对比限定在同一类目内；未指定类目时自动选两家都有、样本最多的那个，
并在返回里写明 `compare_scope='数码类目内'`。
修后数码对比 = 屏幕/系统/功能 vs 边角/撞痕，这才是有话可说的差异。

### 7. 采集器表格整块不渲染（最隐蔽的一个）

问「你的评论数据是从哪来的」，Agent 答了一句话，**下面一片空白**。

原因：

```python
# _absorb 里存的是内层 data
f['collectors'] = d          # d = {'collectors': rows, 'n_auto': 3}
...
# compose 里判断有没有结果
if col and col.get('ok'):    # 恒为 None
```

`ok` 在**外层** `ToolResult` 上，内层 data 里没有。另外四个工具的 data
都由分析层产出、本来就带 `ok`，只有 `collector_status` 是人手拼的、漏了。

这类错的可怕之处：**它不会让任何数字变错**。
26 条断言全绿，数据审计全过，只有界面上少一块。
所以专门补了一节「Agent 出口契约」断言，把每个工具 data 里必须有的特征键
列成契约——这些键就是 composer 里那些 `if` 的判据本身。

同一批还修了两个：
- `list_collectors()` 只返回 `auto: bool`，"半自动"三个字在汇报里等于没解释。
  补 `needs_human`（这一步要人做什么）和 `note`（为什么必须这样）。
- CLI 的 `--dry` 是个**死参数**：声明了、help 里有、从来没被读过。
  用户照用不报错，于是会以为"预览过了"——而文件已经写进去了。
  这比"没这个功能"更糟，因为它让人失去警惕。

## 四之三、为什么"自动爬取"这件事没做

需求里最直接的理解就是写爬虫抓竞品评论。**没做，而且不是做不出来。**

三条理由写在 `tools/collectors.py` 模块头：

1. **违约**——平台服务条款明确禁止。商家账号被抓到，连带店铺受影响。
2. **反爬对抗使代码寿命以周计**——建立在它上面的分析，每几周要重写采集层。
   这不是工程能力问题，是把系统的地基放在别人随时会改的东西上。
3. **样本天然有偏**——平台只展示前 N 页、默认"推荐排序"。
   抓到的不是"全部评论"，是"平台愿意给你看的那部分"。
   用它算负评率，算出来的是这个筛选机制的产物，不是真实口碑。

替代方案是**可插拔采集器框架**，`PlatformScraperCollector` 保留为空类，
并在类注释里写明不实现的理由——**空类比删掉它更诚实**：
删掉之后，看代码的人会以为"只是还没做"。

五个渠道里最关键的是第 2 个：

| 渠道 | 自动化 | 要人做什么 |
|---|---|---|
| 公开学术语料采样 | 全自动 | 不需要人 |
| 平台后台导出 → inbox → 自动导入 | 半自动 | 登录后台点一次导出 |
| 官方开放平台 API | 全自动（需资质） | 一次性申请应用 + 店铺授权 |
| 人工粘贴 | 无 | 全部 |
| 平台页面抓取 | **不实现** | — |

**登录态留在人手里，就是这条路径合规的全部理由。** 机器要"自动登录"，就越过那条线。

这个立场也写进了 Agent 的推理独白里，问「你能自动爬取评论吗」它会主动交代
哪个渠道不做、以及为什么——不是藏在文档里等人去翻。

---

还有三处是**逻辑**而非视觉的：

- **"大盘怎么样"答成"你问的那一周其实正常"**。用户根本没问哪一周——重定向文案没区分意图。现在大盘问题改成"整体看，最该关注的是第 44 周"，并在正文首段交代"我扫了全部周次、按二项 z 挑出偏离最大的那周"。
- **"最新一周"解析不出周次**。系统内部按当前周跑，结论却说"你问的那一周"，既不说是哪一周，也不摆那周的数字。现在 `最新一周/最近一周/这周/本周` 都解析成真实末周（用 `latest_week`，不硬编码 52）。
- **样本不足时仍输出"类目贡献分解"表**。结论说"我不下判断"，下面却摆着精确到两位小数的贡献值，等于嘴上说不知道、手上却在算账。现在不判异常时降级为"各类目退货率对照（未做归因）"，明确不带贡献列。

### 4.5 左栏那两个数是写死的，而且停在三个版本之前

这一处是**真截图才发现的**，光看后端日志永远看不到。

界面左上角"数据底盘"四格，长期是：

```tsx
<div className="stat-v">{(64659 / 1000).toFixed(1)}<small>k</small></div>   // 年订单
<div className="stat-v">14.6<small>%</small></div>                          // 退货率
```

这两个数是 JSX 里写死的字面量。数据从 v2.3 重建到 v2.5（61.8 万单、13.53%）的过程中，
后端每一处都跟着改了，前端这两格没人想起。于是页面上常驻着一个**三个版本之前**的数字。

为什么这比正文写错更严重：

| | 正文出错 | 左栏出错 |
|---|---|---|
| 出现频率 | 只在回答那一屏 | **每一屏都在** |
| 读者印象 | "这句好像不太对" | "这是系统的基本盘" |
| 发现难度 | 对比同类数字即可 | 除非同时记住真实值，否则发现不了 |

修法是让它走 `/api/health`，由后端算好下发。但改的过程中我自己又制造了两个新错，而且都是截图抓出来的：

1. **`return_rate` 是小数（0.1353），前端直接 `toFixed(2)` → 显示 `0.14%`。**
   比原来的写死值更糟：写死值只是旧，这个是错的。
2. **`Math.round(618058 / 10000)` → `62`。** 61.8 被进位成 62，一位小数就这么丢了。

两处都加了注释说明为什么必须这么写。这类错误的共同点是：**TypeScript 完全不会报错**——
`toFixed` 对 `number` 合法，`Math.round` 也合法，语义错了但类型全对。

第三个同类问题是**表格底下的注释**：

```
本周被判定为样本不足或非异常，因此只列原始差异，不计算对整体的贡献。
```

这句话把"样本不足"和"非异常"合并成一个判断。但它们是两件完全不同的事：

- 样本不足 → **我看不清**（这是我的问题）
- 非异常 → **确实没事**（这是数据的事实）

合并的后果是白丢一次可信度：明明样本充足、确实没异常，却说成"样本不足"，
用户会以为系统又在找借口——而他投诉的正是这句话。现在按 `enough_sample` 分两支生成。

> **教训**：改文案不能只搜正文。要搜所有会显示给用户的字符串——
> `summary`、`caveats`、`headline`、`badge.label`，以及每个 block 的 `note`。
> 我第一轮只改了正文和 caveats，表格注释原封不动留给用户看。

## 四之四、注释说得对，代码做得不对：重定向为什么会静默失效

这一节记的是**全项目最难查的一类 bug**。它不报错、不告警、不产生任何异常日志，
答案还很有说服力——只是答的不是用户问的那件事。

### 现象

`run_all.py` 的 E2 是「最新一周差评有异常吗」。期望徽章「已重定向」
（最新一周正常 → 自动移到真正异常的第 44 周），实际返回「无异常」。
连跑三次完全一致——**确定性 bug，不是模型随机性**。

### 根因：哨兵值在被用之前就被抹掉了

`parse_week()` 用 `-1` 表示「最新一周」。这个值和「第 52 周」最终落到同一周，
但业务含义完全不同：

| 用户说法 | 解析 | 业务含义 | 该不该换题 |
|---|---|---|---|
| 「第52周怎么样」 | `52` | 点名了某一周 | **不许**换题 |
| 「最新一周怎么样」 | `-1` | 只是说"看看现在" | **可以**追下去 |

主流程是这样处理这个哨兵的：

```python
w = week or parse_week(q)          # 这里拿到 -1
if w == -1:
    w = int(hub.latest_week)       # ← 抹掉了，变成 52
...
state['facts']['week_pinned_by_user'] = (w is not None and w > 0)   # ← 此时恒为 True
```

替换发生在算 `_plan` 之前、而判断写在 state 初始化之后，中间隔了两百多行。
等到判断那一行时，`-1` 已经不存在了，`w > 0` 永远成立——
**「最新一周」被当成了「用户点名第 52 周」，重定向许可被关掉。**

而且这个 bug 特别擅长伪装：第 52 周当时是 `偏离 -0.98pp / z = -2.84`，
过了 z 门槛但不到 1.5pp 的业务幅度线，正好落进 `trivial_but_significant` 分支。
那条分支里有专门为 E2 写的重定向逻辑（连注释都点名了 E2），
但入口处的 `_pinned_t` 已经是 True，`if not _pinned_t:` 直接跳过，
于是 `return ['trend']`——去看 52 周的走势了。

于是三层全部"正常工作"：解析层给了 -1 没错，替换成 52 没错，
trivia 判定没错，走势工具也没错。**没有一处报错，只是答案答错了。**

### 最刺眼的地方

留这段注释的人（也是我）写得很清楚：

```python
# w > 0 等价于"用户报出了一个具体周号"：
#   None → 没提；-1 → "最新一周"（允许追下去）；-2 → 越界（早前已拦下）
state['facts']['week_pinned_by_user'] = (w is not None and w > 0)
```

注释描述的行为是对的，代码在那一行也是"对的"——
错的是它读的变量早就不是注释假设的那个值了。

> **这类 bug 不可能靠读代码发现。** 读到注释会信，读到那一行判断也觉得合理，
> 必须把 `-1` 的整个生命周期串起来看：谁产生、谁替换、谁消费。
> 只要中间有一处替换，后面所有基于哨兵的判断都作废。

### 修法：留一份未被污染的副本

```python
w_asked = parse_week(q) if week is None else week   # 保留哨兵语义
w = w_asked
if w == -1:
    w = int(hub.latest_week)                        # 只改 w，不动 w_asked
...
state['facts']['week_pinned_by_user'] = (w_asked is not None and w_asked > 0)
```

`asked_week` 仍然存替换后的 52（文案要说"第 52 周（你问的那一周）"），
**两个变量的职责分开：`w` 是"要分析的周"，`w_asked` 是"用户怎么问的"。**

### 回归：七种问法必须同时成立

修完只测 E2 是不够的——很容易修好一条、弄坏另一条。七种问法一起跑：

| 问法 | `parse_week` | 徽章 | 行为 |
|---|---|---|---|
| 第52周怎么样 | 52 | 无异常 | 只答 52，不换题 ✓ |
| 最新一周怎么样 | -1 | 已重定向 | 移到 44 ✓ |
| 大盘怎么样 | None | 已重定向 | 移到 44 ✓ |
| 第3周为什么异常 | 3 | 无异常 | 直说这周不是异常周 ✓ |
| 第三十周的数据指标有问题吗 | 30 | 无异常 | 中文数字解析 ✓ |
| 这周怎么样 | -1 | 已重定向 | 移到 44 ✓ |
| 最近一周差评有什么问题 | -1 | 已重定向 | 移到 44 ✓ |

关键是第 1 行和第 2 行必须**分开成立**：都是 52 周，一个不许换题、一个必须换题。
修 bug 时只顾让第 2 行变绿，很容易把第 1 行一起改坏——那等于把"答非所问"换个方向又犯一次。

修完 `run_all.py` **8/8 通过、模板兜底 0**，这是项目到目前为止的最好状态。

> **一句话总结**：哨兵值、占位符、临时标记这类"有特殊含义的值"，
> 一旦被替换，就没法再拿它判断"用户原本怎么说的"。
> 判断"用户意图"的变量和"实际要处理的对象"必须是两个变量，不能共用。

## 四之五、三个只有"真的看一眼屏幕"才能发现的 bug

这一节记的是同一次核对里连着挖出来的三个问题。它们的共同点是：
**所有自动化测试都通过，代码逻辑也自洽，只有把界面渲染出来看才会暴露。**

起因很朴素——按项目自己的规矩「代码改了 ≠ 屏幕上没有」，改完重定向逻辑后跑了一次
截图脚本。结果四张图全部警告「未在 90s 内进入稳定态」，而截出来的图**看着挺正常**。

### 一、截图脚本从加多页面工作台那天起就失效了

| 版本 | URL | 实际截到 |
|---|---|---|
| 旧 | `/?q=标签脱落...&pace=0` | **总览页**（一张完整、漂亮、但不是这一题的页面） |
| 新 | `/?q=标签脱落...&pace=0#/chat` | 问答页 ✓ |

`App.tsx` 的 `parseHash()` 决定渲染哪个页面，没有 hash 就默认 `dashboard`。
而 `?q=` 的自动提问逻辑写在 `ChatPage` 的 `useEffect` 里——**页面都没挂载，它当然不执行**。

所以脚本等的是"回答区域的 `done` 标签"，可那个页面根本没有回答区域，
只能等满 90 秒超时，然后在总览页上截一张图。

> **最阴的地方**：图不报错、不缺块、配色正常。如果不核对"这张图是不是我问的那道题"，
> 会以为截图流程一直是好的。而实际上从 v4.0 引入 hash 路由起，它就没work过。

### 二、稳定态判据用的选择器属于另一个页面

修完 URL 之后，问答页出来了，但仍然超时。`badge=True`（回答渲染了）、`chip=''`。

因为判据写的是 `.rail-right .chip`，而问答页的右栏类名是 **`.chat-rr`**：

| 区域 | 工作台页 | 问答页 |
|---|---|---|
| 左栏 | `.rail-left` | `.chat-rail` |
| 主区 | `main` | `.chat-stage` |
| 右栏 | `.rail-right` | `.chat-rr` |

`.rail-left / .rail-right` 是 six 个功能页面用的骨架，问答页是独立的 `chat-shell`。
于是 `chip` 永远查不到 → 判定条件永远不成立 → 每张图都等满 90s →
最后截在"正在用 qwen-plus 组织结论"这一帧。

**同一类错误在量取截图高度时也犯了一次**：`Math.max(...q('.rail-left'), q('.rail-right'))`
在问答页上全是 0，于是高度退回兜底的 945px，正文下面全被切掉。
现在是两组类名都量、取最大值。

### 三、固定答复路径的 `done` 事件用了另一个字段名

前两个修完，截图上出现一行：

```
— 步 · NaN s
```

`ChatPage.tsx` 读的是 `done.elapsed_ms` 和 `done.tool_calls`（`types.ts` 里也是这两个）。
但 `done` 事件在全项目有五处 `yield`，其中**四条是提前返回的固定答复**
（越界周次 / 空问题 / 问候 / 超出能力），字段写成了 `'ms'`，也没有 `tool_calls`：

| 路径 | 旧字段 | 结果 |
|---|---|---|
| 正常诊断（1 处） | `elapsed_ms` + `tool_calls` | ✓ |
| 越界周次 | `ms` | `NaN s` |
| 空问题 | `ms` | `NaN s` |
| 问候 | `ms` | `— 步 · NaN s` |
| 超出能力 | `ms` | `NaN s` |

**这四条正是用户最先看到的那几条**：第一句「你好你是谁」、问了个不存在的周、
问了个业务外的问题。也就是说，评委第一次点开这个产品，右上角挂着的就是这个 `NaN`。

改成统一字段后：`0 步 · 0.0s`。

### 这一节真正想说的

三个 bug 有两个共同特征：

1. **它们都不在"业务逻辑"里**，而在页面路由、CSS 类名、事件字段这些"接线"位置。
   单元测试测工具函数测不到，断言测业务结论也测不到。
2. **它们都伪装成正常**。总分页看着完整、超时了照样出图、`NaN` 也只是一小段灰字。

所以「最后一步是真的截图看」这句话，重点不在"截图"，在**"看"**——
不是截完就算完，是要拿用例清单逐条对：这张图里问的是不是我那题、
数字有没有出现 `NaN`/`undefined`/`—`、正文有没有被切断。

> 顺带记一个判据的教训：**别用类名跨页面复用同一个判据。**
> 页面骨架换过一次（v4.0 多页面工作台），判据没跟着换，
> 于是"永远等不到"和"永远等得到"看起来一样都是超时。
> 现在两个类名都试，任一命中即可，页面改版也不会静默失效。

## 四之六、总览页改成了 BI 看板：四次把"图"做错的过程

总览页原来是四个互相独立的区块：KPI 格、52 周曲线、类目表、原因表、异常周表。
数字都对，但有一个具体的读图障碍：**看到"服饰 28.33%"，没法立刻知道
"服饰的钱主要花在哪个原因上"** —— 得切到原因治理页再选一遍。

改成了可联动看板：点一个类目，KPI、曲线、原因结构、异常周全跟着切。
下面记的是这个过程中做错的四次，每一次都"看起来能跑"。

### 一、上色键用错：dev_pp 让服饰整行深红

热力图第一版按"偏离本类目基线的百分点"上色。跑出来服饰整行深红、
数码几乎无色。当时以为是 bug，查了数据才明白是**设计错了**：

| 类目 | 基线 | 周间 dev_pp 范围 |
|---|---|---|
| 服饰 | 28.36% | −3.71 ~ +8.83 |
| 数码 | 10.28% | −2.39 ~ +3.32 |

服饰基线高，周间波动天然就大，±3pp 是它的常态；数码 ±3pp 已经很异常。
**同一把尺子量不同尺度的类目，读者看到的其实是"类目退货率不同"这个废话，
而不是"哪一周出事了"。**

改成按**二项 z** 上色。z 已经按各自基线率与样本量归一，跨类目可比
（实测各类目 |z| 中位数 1.17–1.60，分布确实对齐了）。
顺带一个好处：z 和双门槛判定的第一条同源，不会出现"图很红但判定说没事"。

### 二、选中类目后，其他三个类目变成 0.00%

联动上线后截图发现：点"服饰"，类目对比里个护/数码/生鲜 全变成 `0.00%`。

根因一句话：`by_category` 那个循环用的是**已按类目过滤过**的表。
选中服饰时，其他三个类目在过滤后的表里查不到任何行 → `orders=0` →
退货率算成 0。

```python
cat_week = hub._cat_week
if category:
    cat_week = cat_week[cat_week['biz_category'] == category]   # ← 过滤
...
for c in hub.categories:
    g = cat_week[cat_week['biz_category'] == c]                  # ← 用了过滤后的
```

`by_category` 是**切换器**，它必须在任何范围下都完整 —— 否则用户没有
切回去的入口。修法是留一份未过滤的 `cat_week_all` 给它用。

> **这条最值得记的地方不是修法，是它有多安静。**
> 页面上显示的是 `0.00%` 而不是报错、不是空白。
> `0%` 看起来像"这个类目没退货"，比显示 `—` 更危险 —— 读者会信。

已经固化成断言（`check_review_analytics.py` 第 8 节）：
选中任一类目后，其他类目的 `orders` 与 `return_rate` 必须**逐字节不变**。
反向验证过——把 `cat_week_all` 改回 `cat_week`，断言立刻红。

### 三、前端和服务端字段名对不上，整页白屏

换色阶时后端把 `scale_pp` 改成了 `scale_z`，但**服务没重启**（uvicorn 没开 `--reload`）。
前端读 `d.heatmap.scale_z` 得到 `undefined`，紧接着 `.toFixed(1)` 崩掉：

```
TypeError: Cannot read properties of undefined (reading 'toFixed')
```

React 的错误边界把整棵树卸载了 —— 截图出来是**一张纯黑图**，
判据里 `root 内容长度: 0`。而且它不报"字段缺失"，只报一个 toFixed。

> 教训：**改字段名的时候，前后端要一起动、服务要重启**。
> 全项目五处 `done` 事件那次也是同一类问题（用 `'ms'` vs `'elapsed_ms'`）。
> 现在这类问题有一个统一兜底办法：所有下发字段都写在 `lib/pages.ts` 的
> interface 里，`tsc --noEmit` 能在**编译期**抓到"读了一个不存在的字段"。
> 但**抓不到"后端没发"** —— 所以字段改名后必须重启并重新截图。

### 四、`?category=服饰` 被忽略：看板状态不可寻址

Dashboard 的 `scope` 一开始是 `useState(null)`，不读 URL。
后果有三个，都很日常：

- 截图脚本传 `?category=服饰`，页面照旧显示全店（**截图和被测对象不是一回事**）
- 评委想分享"服饰这一屏"，发出去的链接打开是全店
- 刷新一下联动状态就没了

改成从 `window.location.search` 读初值，切换时 `history.replaceState` 同步回去。
ChatPage 早就用 `?q=` 做深链（现场演示预先打开问题），看板这边漏了同一件事 ——
**BI 看板的状态本来就该是可寻址的**，"你去看服饰那一屏"是评审现场最常说的话。

### 顺带修掉的一个校验误伤（跟看板无关）

跑回归时 E5 偶发失败：`出现事实中没有的数字 ['25', '35']`。
追下去发现是千分位剥离的正则收尾用了 `\b`：

```python
re.sub(r'(?<=\d),(?=\d{3}\b)', '', body)     # 旧
re.sub(r'(?<=\d),(?=\d{3}(?!\d))', '', body) # 新
```

Python3 的 `\b` 是 Unicode 感知的，**汉字算 word 字符**，所以「1,355单」里
`5` 和 `单` 之间没有词边界 → 前瞻失败 → 逗号没去掉 → 拆成 `1` 和 `355`
→ 355 被判成编数 → 模型输出作废、回退模板。

实测：「1,355 单」能过（后面是空格），「1,355单」不能过。
而模型写中文时**通常不加空格**，所以这条几乎次次命中。
换成 `(?!\d)`：只要求"后面不是数字"，与语言无关。

修完 E5 从 3/5 提到 4/5（剩下那 1 次是模型真编了数字，校验拦得对）。

### 这一节的结论

四次错误里有三次**不产生任何错误数字**：
上色键错了（图在骗人）、字段名错了（整页白屏）、URL 不支持（截错对象）。
它们全部由"看截图"发现，没有一条是断言先报出来的。

所以第 8 节的那 9 条看板断言（尤其是"切换范围时 by_category 不被动过"
这条逐字节比对的）是补在事后 —— **先被截图抓出来，再写成断言防复发**。
顺序不能反：断言只能守住你已经想到的事。

## 四之七、评论页的"文字墙"：40 个词各挂一句原话，页面 3,659px

总览页改完之后顺手截了其余五页，**只有评论洞察页还是纯粹的静态列表**。
它当时的样子：40 个词，每个词下面挂一句原话，整页高 **3,659px**，
其中词云那一块独占 3,000px 以上。

### 问题不是"不好看"，是三个具体的读图障碍

1. **滚到中途就忘了开头。** 读者想知道"抱怨集中在哪"，得把 40 行都读完
   才敢下结论，而读完前 15 行时已经把前 5 行的印象冲掉了。
2. **两个量纲挤在一列。** 差评栏按 `log2 lift` 排序（这是它存在的理由），
   但右边只有次数。读者看到"坑人 17 次"排在"质量 1,792 次"前面，
   第一反应是"排错了" —— 其实这一栏根本没按次数排。
3. **原话只挂第一句。** 后端每个词给最多 3 句，界面只显示 1 句。
   想多看一句的人没有任何入口。

### 改法：条形 + 悬停 + 折叠，三个层次各管一件事

| 层 | 解决什么 | 实现 |
|---|---|---|
| 条形 | 一眼看出"抱怨集中在哪" | `HBars`，条长按**当前排序口径**归一 |
| 悬停浮层 | 随口验证"这个词是不是被误切出来的" | 第一句原话 + 命中词高亮 |
| 折叠区 | 逐条核对全部原话 | `<details>`，默认收起，网格排布 |

**关键的一处决策：条长归一分母要跟着排序口径走。**

```tsx
pct: wcIsLift ? Math.pow(2, w.lift) : w.count      // 不是固定用 count
max: Math.max(...wcShown.map(w => wcIsLift ? 2**w.lift : w.count), 1)
```

一开始图省事写了 `pct: w.count` + `max: maxCount`，结果差评栏
条长和排序完全对不上（"坑人"只有 17 次却排在 1,792 次的"质量"前面，
条却短得看不见）。**排序键和长度键必须是同一个量纲**，否则图在自相矛盾。

**第二个决策：默认只显示 12 个。**

40 个词全列出来，读者记不住；12 个足够看清"抱怨集中在哪几个点"，
剩下的给"24 / 全部"两档。切到"全部"时页面仍然很长，但那是**读者主动选的**，
不是默认塞给他的。

### 一个顺手确认过的疑似 bug（不是 bug）

改完发现"全部"那一栏只有 20 个词，而"差评"栏有 30 个。
第一反应是前端截断了。查了后端才确认：两栏的候选池本来就不同 ——
差评的样本少（1,348 条）、词更分散，所以 Top-40 里能留下的候选更少；
而全部评论用词集中，去重后只有 20 个词进得了榜单。**界面没有说谎。**

> 但这件事值得记下来：**当两个列表长度不同时，第一反应应该是查数据，
> 而不是查代码。** 这次是虚惊，下一次可能就不是 —— 而"先怀疑前端截断"
> 会让人去改一个根本没问题的地方。

### 这一轮新增的 5 条断言（第 9 节）

改完之后，词云块对前端有两个强依赖：`count`（全部栏的主值）和
`lift`（差评栏的主值和排序键）。任何一个没下发，页面不会报错，
只会出现一条 0 长的条或一个"—"。所以固化成断言：

- 两栏都有数据
- 按区分度那栏每个词带 `lift`
- 全部词栏每个词带 `count`
- 每个词都能回溯到原话
- 差评词按 lift **降序**下发（前端不重排，直接按数组顺序画）

最后一条尤其重要：**排序口径只有一份**（在后端）。
前端如果再排一次，两处迟早分叉。

## 四之八、v4 视觉重构：从青绿驾驶舱到纯灰阶

用户的要求是两句话：「配色不好看，整体弄成黑白灰，用颜色深浅区分不同元素」
「界面呆板，要灵动、圆润，鼠标放上去要有反馈」。

### 一、为什么敢做纯灰阶

一、**灰阶的信息密度更高。** 四个语义色同时出现时，读者要先记住
"红=坏、琥珀=待定、青=好"，才能开始读数据；灰阶把这一层认知成本省掉了——
亮就是重，暗就是轻，不需要学习。
二、**彩色界面很难避免"像模板"。** 青绿 + 深蓝几乎是所有 AI 产品的默认皮肤。
去掉色相之后，剩下的只能靠间距、字重、对齐、层级撑住，
而这些恰恰是"专业工具感"的真正来源。
三、**投影仪友好。** 评审常投屏，多色在低质量投影上会糊成一团灰，
而灰阶本来就是灰，怎么投都不失真。

### 二、但语义色不能全砍

这是整套改造里最重要的一个判断。全灰会丢信息：

- **热力图**的红/青承载"偏离方向"。全灰之后只剩"偏得多不多"，
  分不出"恶化"还是"改善"——而这恰恰是归因诊断的结论本身。
- **KPI 的退货损失**必须有警示感，否则运营扫一眼会当成普通指标略过。

所以保留语义色，但做三件事让它不破坏灰阶：

| 手段 | 做法 | 效果 |
|---|---|---|
| **去饱和** | 饱和红 `#f2555a` → `灰红 #c26663` | 明度降、灰度提，不抢视线 |
| **压面积** | 只出现在数字、圆点、1px 描边上，绝不铺底色块 | 208 格热力图不再是一块砖红 |
| **换通道** | 条形改"亮度分级"、走势线改"线型差异" | 大小和方向不再依赖色相 |

其中"换通道"是关键：**条形的大小本来就不该用颜色表达。**
改造前所有原因条都是红的——一整片红，既没有区分度（每根都一样），
又让灰阶当场破功。改成三档灰（>66% 亮、>33% 中、其余暗）之后，
最亮的那根 = 数值最大 = 最该看的那一项，**不需要图例**。

### 三、灵动感从哪来：三层反馈，分时触发

只做变色 = 死板；只做位移 = 廉价；三个一起 = "面板被触碰"的物理感。
关键是**不要同时发生**：

```
0ms    颜色/亮度立刻响应   ← 大脑认为"我按到了"
40ms   位移跟上            ← 体现质量感，太快会飘
120ms  阴影铺开            ← 最慢，负责"浮起来了"的余韵
```

全部 100ms 同时完成的话，看起来像整体平移了一下，反而没有层次。

幅度必须小：位移上限 2px、缩放上限 1.08、阴影最多两级。
超过这个量，专业工具就开始像消费级 App 的按钮动画。

具体覆盖了 16 类元素（卡片、KPI、按钮、表格行、条形、热力格、
分段控件、胶囊、侧栏项、标签、品牌标、折叠区、tooltip…），
并且**统一在 CSS 的一节里**——动效最容易失控，三个地方写成三种时长，
界面就会"有的地方活、有的地方死"。集中之后，想调手感只改 4 个变量。

### 四、圆润化：哪些放大、哪些不动

2642 行 CSS 里散着 42 处写死的 `border-radius`。没有逐个改原定义，
而是在末尾加了一节覆盖——好处是想调"圆到什么程度"只改一处，
想退回硬朗风格删掉整节即可。

**分寸在"哪些不动"**：

| 放大 | 不动 |
|---|---|
| 卡片 8→14px、按钮 5→9px、标签→胶囊 | 图例方块 2px、热力格 2px、细条 4px |
| 这些是"面"，会被注视和点击 | 这些是"刻度"，一放大就失去精度感 |

### 五、过程中修掉的四个问题

| 问题 | 现象 | 根因 |
|---|---|---|
| 条形全长一样 | 每根都是红条，看不出差异 | tone 写死 `'bad'`，与数值无关 |
| 热力图一片砖红 | 208 格铺满暖色，画面脏 | 满色不透明度 0.77 太高 |
| 走势图负评线消失 | 改灰后太暗，小图上几乎看不见 | 亮度 150 太低，提到 196 |
| **表格行指示条完全不显示** | hover 时左侧竖条没有出现 | **`tr` 不支持 `position: relative`** |

最后一条是这次最有价值的发现：

```css
/* 无效：table-row 的定位上下文不被浏览器支持 */
.pg-table tr.clickable::before { position: absolute; ... }

/* 有效：改成 td 的 inset 阴影，不占位、不影响列宽 */
.pg-table tr.clickable:hover td:first-child {
  box-shadow: inset 2px 0 0 0 var(--fg);
}
```

`tr` 的 `display: table-row` 是特殊类型，绝对定位子元素会脱离到
最近的非 table 定位祖先——伪元素直接跑到表格外面去了。
**这种错在代码里看着完全合理，只有实测才发现它一次都没生效过。**

### 六、无障碍兜底（不是可选项）

```css
@media (prefers-reduced-motion: reduce) { /* 全部降级为"只变色不位移" */ }
```

系统级开了"减少动画"的用户（前庭功能障碍、偏头痛患者）会因为
视差、缩放、脉冲而生理不适。这一条不是锦上添花，是必须有的出口。

另外焦点环统一成白色双环：灰阶界面里浏览器默认的蓝色焦点环
是唯一的彩色，非常突兀；而且很多组件被 `outline: none` 干掉了，
键盘用户会彻底失去位置感。

### 七、验证方式

配色和动效都不能靠"看着还行"验收，所以做了三层检查：

1. **读计算样式**（不是读像素，避免图片缩放误差）：
   背景 `rgb(11,11,12)` 纯中性 · 条形三档灰 · 热力格饱和度极低 ·
   圆角 14/9/999px 全部生效
2. **模拟真实鼠标事件**（`Input.dispatchMouseEvent`，不是加 `:hover` 类）：
   卡片/按钮/胶囊/侧栏/条形/热力格 6 项悬停全部检测到样式变化
3. **全站对比度审计**（`check_contrast.py`）—— 见下一节。

第 2 步是必须的——`:hover` 伪类能测样式，但测不到"这个元素到底在不在鼠标下面"。

## 四之九、灰阶化最容易翻车的地方：文字看不清

### 一、问题不是"丑"，是"看不见"

改完灰阶之后截图看着挺好。但把四个语义色一起降饱和时，
**文字和它自己的底色是同一个变量**——底色减了饱和，字色也跟着减，
于是标签、单位、说明这些小字先看不清了。

第一次跑对比度审计，**6 个功能页共 74 处不达标**，全都是同一类：

```
2.88 (需 4.5)  10.5px  rgb(90,90,97) on rgb(11,11,12)
                .pg-foot
                「口径：全部类目 · 显著性用双侧两比例 z 检验，不是看谁的数字大小」
```

这句话读者**必须**能读清——它就是"这个结论是怎么判的"。看不清它，
整页数字的可信度就无从判断。它不是装饰文字。

### 二、这类问题为什么必须靠机器查

| 特点 | 后果 |
|---|---|
| 截图缩到 1000px 显示时，人眼会自动补足对比度 | 肉眼审查**看不出来** |
| 74 处分散在 6 个页面、几十个类名上 | 手工逐个查不现实 |
| 每次调 `:root` 色阶，所有引用处一起变 | 手工调过的地方，下次改配色又会复发 |

所以写成了 `check_contrast.py`，进验收清单，改配色就跑一遍。

### 三、判据

WCAG 2.1 AA：

| 字号 | 要求 |
|---|---|
| 正文（< 18.5px，或 < 14px 且非加粗） | ≥ **4.5** |
| 大字（≥ 18.5px，或 ≥ 14px 且加粗） | ≥ **3.0** |

只算"直接含文字节点"的元素，否则同一个问题会被祖先和后代各报一次。

### 四、改法：不是简单调亮一个变量

第一反应是"把 `--fg-4` 调亮"，但那样四档文字会糊成一档，层级就没了。
实际做了三件事：

**1. 整条阶梯上移，但保持级差**

```
           改前        改后      在 --bg 上的对比度
--fg      #f2f2f3    #f2f2f3    17.6
--fg-2    #b4b4b9    #c2c2c8    11.1
--fg-3    #83838a    #9c9ca4     7.2
--fg-4    #5a5a61    #86868f     5.0   ← 原来只有 2.88
--fg-5    #3d3d43    #56565e     3.4   ← 只用于占位/刻度，WCAG 豁免
```

相邻两级的亮度比都在 1.4 倍上下，层级仍然分得开。
**是整体抬亮，不是把四档压成一档。**

`--fg-4` 后来还微调了一次（#80808a → #86868f）—— 因为 `--panel-2`
比 `--bg` 亮一级，同样的字在更亮的底上只剩 4.24，差 0.26。
**"差一点点"最容易被放过，但它恰恰是最常见的正文说明。**

**2. 语义色要分"当底用"和"当字用"两个版本**

```css
--bad:    #c26663;   /* 当底色块：够用，不刺眼 */
--bad-fg: #e0a8a4;   /* 当文字：亮 40%，否则压在自己的 --bad-dim 上只有 2.68 */
```

这是灰阶化最容易漏的一类：底色和字色共用一个变量，
降饱和时一起降，字就先死了。

**3. 局部覆写，不动全局**

浮层（`--raise`）比卡片亮一级，同样的 `--fg-4` 在那里只剩 4.45。
为这 0.05 去抬高全局变量会让全站标签一起变亮、层级糊掉，
所以在 `.bi-tip-row.dim` 上局部覆写成 `#8f8f98`。

**4. 不要用 `opacity` 做"弱化"**

排序指示符 `↕` 原来写 `opacity: .5`，实测对比度 **1.84** ——
等于把"这列可排序"这个唯一的提示彻底抹掉。
弱化应该用颜色，不是透明度：**透明度会连可读性一起削掉。**

### 五、两个审计脚本自身踩的坑（值得记）

审计脚本如果算错，比不审更糟 —— 它会让你去修一个不存在的问题。

**坑 1：渐变底读不到。**
`getComputedStyle().backgroundColor` 对渐变返回 `transparent`，
真实底色在 `backgroundImage` 里。品牌标是"白渐变底 + 深色字"，
不处理就被算成"深底 + 深字"，报 1.04 的假警报。

**坑 2：渐变不能简单取 RGB 平均。**
修了坑 1 之后改用算术平均，结果
`linear-gradient(transparent, rgba(255,255,255,.06))` 这种
顶部装饰高光被算成 `rgb(128,128,128)` —— 一个根本不存在的"中灰底"，
问答页因此报了 5 处假警报。

**正确做法是 alpha 加权**：按 alpha 求加权色，再取平均 alpha 作为这层遮盖度。
装饰渐变的 RGB 是亮的但 alpha 接近 0，忽略 alpha 就会把它当实色。

> **教训**：审出来的问题要能解释"为什么这里会看不清"。
> 解释不通的，先怀疑脚本，不要急着改样式。

### 六、验收

```
python check_contrast.py            # 全部
python check_contrast.py pages      # 6 个功能页
python check_contrast.py chat       # 问答页（欢迎态 + 真实回答后）
python check_contrast.py states     # 14 种交互态
```

结果：

```
6 个功能页             0 处不达标
问答页 欢迎态/回答后     0 处
14 种交互态             0 处
```

**为什么单列"交互态"**：v4 新增了十几种 hover / 选中样式，而状态样式
只在鼠标放上去时存在 —— 静态审计一次都碰不到。
一个元素平时 8.0 的对比度，悬停时背景提亮了、字色没变，
可能瞬间掉到 3.0。

脚本里"跳过"会显式打出来（`[跳过] 元素不存在或不可见`），
因为**跳过不等于通过** —— 选择器写错会被当成"没有这个问题"。

## 四之十、键盘焦点：一个被 `box-shadow: none` 吃掉的环

### 一、问题

v4 的焦点环第一版是这样写的：

```css
:focus { outline: none; }
:focus-visible {
  outline: none;
  box-shadow: 0 0 0 2px var(--bg), 0 0 0 4px rgba(255,255,255,.55);
}
```

想法是"双环"：内圈取页面底色打底（保证在浅色块上也看得见），
外圈白色（保证在深底上看得见）。看起来很稳。

但实测 Tab 到**第 1 个元素**——侧栏当前选中的「总览」——环完全消失。

### 二、根因：CSS 优先级

```
:focus-visible         → 特异性 0,1,0
.sidenav-item.on       → 特异性 0,2,0   ← 更高
```

我在交互层为了让新的 `::before` 渐变竖条生效，写了：

```css
.sidenav-item.on { box-shadow: none; }   /* 清掉旧版用 box-shadow 画的左侧条 */
```

这一条把焦点环也一起清掉了。而**"当前选中项"恰恰是最需要知道
"键盘焦点在不在它上面"的状态** —— 它的背景已经是 `--panel-2`，
比别的项亮，没有环根本分不出"选中"和"聚焦"。

### 三、改法：换通道，不换值

```css
:focus-visible {
  outline: 2px solid rgba(255, 255, 255, .78);
  outline-offset: 2px;
  border-radius: inherit;
}
```

三个理由：

| 改法 | 理由 |
|---|---|
| `box-shadow` → `outline` | outline 是独立通道，**不会被任何 box-shadow 覆盖** |
| 加 `outline-offset: 2px` | 环落在元素**外侧**，外侧永远是页面深底，所以不再需要"内圈深色打底"那一层 |
| `border-radius: inherit` | 环的光角跟随元素圆角，符合 v4 的圆润风格 |

**教训**：用 `box-shadow` 做焦点环，等于把可见性托付给
"没有任何其他规则也在动 box-shadow"。而这句话在真实项目里几乎不成立 ——
阴影是最高频的装饰属性（卡片、按钮、选中态、内高光都在用）。
**可见性不该和装饰性共用同一个 CSS 属性。**

### 四、同一个坑还埋了一处

`.composer textarea { outline: none; }` —— 特异性 0,1,1，同样高于
`:focus-visible` 的 0,1,0。这条更隐蔽，因为它**本来就是多余的**
（`:focus { outline: none }` 已经清掉了），纯属历史残留。
删掉之后输入框的聚焦反馈来自两处叠加：自己的白环 + 父容器
`.composer:focus-within` 的边框提亮，在深底上非常明确。

### 五、检测器本身也踩了坑：8 步走不到输入框

第一版脚本在问答页只走 8 步，而实际顺序是：

```
7 个侧栏项 → 6 个推荐问题按钮 → ... → textarea（第 23 步）
```

8 步时脚本报"全部 OK"，但**最该测的 textarea 一次都没走到**。

改成按元素类型判停（Tab 到出现 `TEXTAREA` 且它已通过检查为止，
硬上限 40 步防死循环），并加一条：

```python
if need and not hit:
    print(f"★ {max_steps} 步内没走到 {need} —— 检测器未覆盖目标元素")
    total_bad += 1        # 没覆盖到 = 失败，不是通过
```

> **检测器的覆盖面本身就是判据的一部分。**
> "没报错"和"没问题"之间，隔着一个"我到底测到了没有"。

### 六、判据：有环 != 看得见

`hasOutline` 为 true 只说明存在一个 outline，4% 白也算。
所以加了量化判据：**焦点环对比度 ≥ 3:1**（WCAG 2.1 对非文字元素的要求）。
环落在元素外侧，压的是页面底色，直接按 `--bg` 算即可。

反向验证过：临时把环调成 `rgba(255,255,255,.04)`，
脚本立刻报 **39 处**（环对比 1.08）；恢复 `.78` 后 —— 39 处变 0 处，
每处实测 **11.92**。

### 七、顺带验了另外两件事

**降动效降级**（`prefers-reduced-motion: reduce`）

用 CDP 的 `Emulation.setEmulatedMedia` 模拟系统设置，实测：

```
[基准] .pg-card transition=0.320  .bi-heat-c=0.220  .sidenav-item=0.220
[降级] 全部 transition=0.00001   animation=0.00001
[降级] 悬停前后 transform 都是 none（位移被正确撤销）
```

关键是**降级后悬停不能还有位移** —— 只把时长改成 0 是不够的，
`transform: translateY(-1px)` 仍然是终值，会瞬间跳过去。
v4 的降级块里显式写了 `transform: none !important`，实测生效。

**窄屏**：1280 / 1366 两档，`scrollWidth == viewport`，无横向溢出。
这两档是评审最可能用的笔记本分辨率，而之前所有截图都是 1440px。

### 八、验收

```bash
python check_a11y.py
```

```
键盘焦点（总览 16 步 + 问答 23 步，含 TEXTAREA）   0 处不可见
焦点环对比度                                      11.92（需 3.0）
降动效降级                                        0 处未降级
窄屏 1280 / 1366                                  0 个溢出
交互可达性（17 个可点元素）                        0 处问题
```

焦点环的实际观感也截图核过（数值只证明可见，不证明得体）：
白环 + 2px + 圆角跟随，在侧栏项和按钮上都紧贴外侧、不割裂、不侵占相邻元素。

## 四之十一、"点不到"比"看不清"更严重

第 4 节验的是**看得见**，这一节验的是**点得到**。
一个元素可以对比度满分、焦点环漂亮，却因为是个裸 `<div onClick>`
而永远进不了 Tab 序列 —— 键盘用户根本到不了它面前。
这不是"体验差一点"，是**功能缺失**。

### 一、两处可点却不可聚焦

```tsx
// ① 折线图上的异常周圆点（全图唯一的交互点）
<g className="pg-dot-g" onClick={() => onPick(s.week)}>

// ② 条形图的行（点了切类目 / 跳原因治理）
<div className="bi-bar-row" onClick={it.onClick}>
```

两者都靠 `onClick` 挂行为，但 `<g>` 和 `<div>` 默认**既不可聚焦也不响应回车**。
鼠标用户点得到，键盘用户只能看着。

修法是三件套，缺一不可：

```tsx
role="button"
tabIndex={0}
onKeyDown={(e) => {
  if (e.key === 'Enter' || e.key === ' ') {
    e.preventDefault()      // ← 关键，见下
    onPick(s.week)
  }
}}
```

**`preventDefault` 不是可选的**：空格键在浏览器里的默认行为是滚动页面。
不拦的话，用户按空格 → 页面往下跳一段 → 看起来像"点了但没反应"，
而且焦点跟着跑出视口。这个 bug 只在键盘上出现，鼠标用户永远遇不到。

### 二、只有真的可点时才进 Tab 序列

条形行里既有可点的（类目、原因），也有纯展示的（异常周表的静态行）。
一律挂 `tabIndex` 会让 Tab 在很多无意义的地方停住，反而更烦：

```tsx
role={it.onClick ? 'button' : undefined}
tabIndex={it.onClick ? 0 : undefined}
```

> **可访问性不是"给所有东西都加上属性"，是让每个属性都对。**
> 乱加 tabIndex 和不加，对键盘用户是同一类伤害。

### 三、还有一个"瞬间跳变"

圆点原来的 hover 是：

```css
.pg-dot-g:hover circle:nth-child(2) { r: 4.4; }   /* 没有任何过渡 */
```

鼠标一放上去，圆点**突然变大**。而周围所有元素（卡片、按钮、条形、热力格）
都是 160–320ms 的平滑过渡。这种"一个地方硬跳"的手感比完全不做反馈更难受 ——
用户会以为掉帧了。

这也正好违反了我自己在交互层开头写的原则：
> "三个地方写成三种时长，界面就会有的地方活、有的地方死。"

补上过渡后还要验一件事：**`transition` 作用在 SVG 几何属性（`r`）上
是不是真的在插值。** 写了不代表生效 —— 浏览器完全可能把它当未知属性
静默忽略，不报任何错。

判据只有一个：hover 后**立刻**读（50ms，远小于 180ms），值应当还在中间。

```
静止 r=3.4   +50ms r=4.6873   +650ms r=5      ← 在插值，过渡真生效
```

如果是瞬间跳变，`+50ms` 会直接等于 `5`。

### 四、hover 和 focus 必须是同一套反馈

```css
.pg-dot-g:hover > circle:nth-child(2),
.pg-dot-g:focus-visible > circle:nth-child(2) {
  r: 5;
  stroke-width: 2.2;
}
```

**同一个元素不该有两种样子**：
鼠标放上去变大变粗，键盘聚焦时却什么都不变，等于告诉键盘用户
"这个反馈不是给你的"。两条选择器写在一起，是这个承诺在代码里的形态。

另外给聚焦态的透明热区圆加了一点柔光（`rgba(255,255,255,.10)`）：
SVG 的 `<g>` 上，全局 outline 画在**包围盒**外侧（约 18×18 的矩形），
对圆形略显方正。柔光让它在形状上也说得通。
但**没有抹掉 outline** —— 上一节刚说过焦点环不该被任何规则吃掉，
柔光是修饰，两者叠加而不是替换。

### 五、为什么不写自动化点击测试

这一节的四项（可聚焦 / 在插值 / 回车触发 / 空格不滚页）
全部用 CDP 真实派发事件验的，不是读代码猜的：

```
[1] 17 个可点元素    tabIndex=0  role=button          全 OK
[2] 半径过渡         r 3.4 → 4.6873 → 5              在插值
[3] 聚焦 + 回车      #/dashboard → #/attribution/24   跳转成功
[4] 空格            scrollY 0 → 0                     没滚
```

第 2、4 项是纯运行时行为，**读源码完全看不出来**：
`transition: r` 写了但没生效、`preventDefault` 漏了，
两者在 TypeScript 层面都是 0 错误。

## 四之十二、用读屏的人，看到的是「空页面」

前面十一节全部是**视觉和触觉**层面的：看得见、点得到、过渡平滑。
这一节是**听觉**层面的。对用读屏软件的人来说，
前面所有工作**一点都传不过去**。

### 一、最严重的：问答页没有 live region

实测全项目 `aria-live` 出现次数：**0**。

问答页是这套系统的核心。用户提问 → 后端流式返回 → 推理链逐步展开 →
结论卡渲染出来。整个过程对屏幕阅读器是**完全静默**的：
所有内容都是视觉增量插入，辅助技术捕捉不到任何变化。
用户按了回车，然后什么都不会发生。

### 二、但也不能直接给流式容器加

第一反应是把 `aria-live` 挂到 `.stage-scroll` 上。这是反模式：

```
流式输出每个 token 都在变更
→ 整块作为 live region
→ 读屏每来几个字播报一次
→ 变成听觉轰炸，用户只能强行打断
```

比不播报更糟。正确做法是**完成时播报一次摘要**：

```tsx
{/* 视觉隐藏的独立 live region，只在 done 后填内容 */}
<div className="sr-only" aria-live="polite" aria-atomic="true">
  {lastTurn?.done && lastTurn.answer
    ? `${lastTurn.question}。回答：${lastTurn.answer.headline}`
    : ''}
</div>
```

三个选择都有理由：

| 属性 | 为什么 |
|---|---|
| `aria-live="polite"` | 不打断用户当前正在听的内容，排队播报。`assertive` 会强行插话，适合错误告警，不适合正常回答 |
| `aria-atomic="true"` | 每次变化重读**整个区域**，而不是只读增量片段 |
| 内容取自 `headline` | 后端已经组装好的一句话结论。塞整篇正文（300+ 字）会让读屏念半分钟 |

生成过程中不填内容 —— 进度由 `.stage-scroll` 的 `aria-busy` 表达，
读屏自己会报"忙碌"。用户不需要听"正在查询、正在计算"这种逐条播报。

实测走完一次真实问答：

```
提问前   aria-live = ''            aria-busy = 'false'
生成中   aria-busy 变 true ✓
完成后   aria-live = '第44周为什么涨了。回答：第44周退货率上涨3.64个
                     百分点，主因是促销机制本身抬高退货倾向'   （46 字）
```

**46 字是刻意控制的**：含问题 + 一句话结论，不念表格数字。

### 三、`sr-only` 不能用 `display:none`

这是最容易做错的地方。写无障碍最经典的错误是：

```css
.sr-only { display: none; }        /* ✗ 读屏完全跳过，等于没做 */
.sr-only { visibility: hidden; }   /* ✗ 同上 */
```

两者都会让元素从**无障碍树**里彻底消失。代码里明明写着 `aria-live`，
检查起来还觉得挺规范，实际一点用都没有。

正确写法是把元素挤出视口但保留在树上：

```css
.sr-only {
  position: absolute;
  width: 1px; height: 1px;
  margin: -1px; padding: 0;
  overflow: hidden;
  clip: rect(0, 0, 0, 0);
  clip-path: inset(50%);
  white-space: nowrap;
  border: 0;
}
```

所以验收判据必须是**「`display` 不是 `none`、`visibility` 不是 `hidden`、且尺寸 ≤ 4px」** ——
只看"有没有 aria-live 属性"会把上面两种错误写法判为通过：

```
OK  mode=polite atomic=true display=block visibility=visible 尺寸=1×1
```

（没用 `left: -9999px` 的老写法：RTL 布局下方向会反，而且父元素有
`overflow` 或 `transform` 时会留下一条可滚动区域。）

### 四、表格：7 个 th，0 个 scope

```
tables: 1   th: 7   thScoped: 0
```

视觉上这些表很好读；听觉上是一串**没有标签的数字**：
读屏只能报"第 3 列，28.33"，说不出"退货率 28.33%"。

补 `scope="col"` 后，读屏会把列名和每个单元格关联起来。
可排序表头还要 `aria-sort`：

```tsx
<th scope="col"
    aria-sort={c.sortVal
      ? (sort?.key === c.key ? (sort.dir === 'asc' ? 'ascending' : 'descending') : 'none')
      : undefined}
    tabIndex={c.sortVal ? 0 : undefined}
    onKeyDown={...}>
```

两个细节：

**① 可排序列必须显式给三态之一**（`ascending` / `descending` / `none`）。
只给当前排序列设、其他列不设，读屏会把"没属性"和"不可排序"混在一起，
用户听完列名不知道这列能不能点。

**② `th` 不能改成 `role="button"`。** 那会**丢掉 `columnheader` 语义** ——
读屏不再把这格当表头，单元格的列名又没了。
正确做法是保留表头语义 + 单独补 `tabIndex` / `onKeyDown`。

批量补齐时用正则扫全部 `.tsx`（逐个手写必然漏）。
**六页实测 79 个 th，79 个带 scope**：

```
dashboard 7 · attribution 23 · reasons 19 · reviews 4 · competitors 14 · eval 12
```

（一开始我在文档里写的是 58 —— 那是按源码里 `<th` 的出现次数估的，
而 React 展开 `map` 之后实际渲染更多。**这种数必须跑一遍再写。**）

### 五、触控目标：46×23 差 1px

WCAG 2.2 SC 2.5.8（AA）要求交互目标至少 **24×24 CSS px**。实测：

```
.bi-seg-i     39×20   ✗
.bi-scope-i   46×23   ✗   ← 高度差 1px
.pg-dot-g     20×18   ✗
```

**没有加 padding。** 加 padding 会把按钮撑高，一排 7 个分段按钮
会从"轻量切换器"变成"一排厚标签" —— 这是拿可访问性当借口破坏设计。

用透明伪元素把**命中区**撑开，视觉尺寸一点不变：

```css
.bi-seg-i::after, .bi-scope-i::after {
  content: '';
  position: absolute;
  left: 0; right: 0;
  top: 50%;
  height: max(100%, 24px);
  transform: translateY(-50%);
  background: transparent;   /* 透明，但不加 pointer-events: none */
}
```

**`pointer-events` 这一行是成败关键**：加了 `none` 尺寸变大但点击穿透，
等于白做。实测必须真点一下：

```
点击前选中态 = 1000100   目标 = 变化
点击后选中态 = 0100100   ← 切换成功
```

命中层高度读到 `24px`、`pointer-events=auto`、按钮真的有响应。

### 六、圆点：宁可尺寸不达标，也不能点错

折线图 52 周，viewBox 宽 1000，周间距约 **18.7 单位**（实测热区 20px）。
把热区撑到 24px 会让相邻两周的命中区重叠 → 点 W23 跳到 W24。

**这是 SC 2.5.8 的 spacing 例外明确允许的情形**：目标密集到无法同时满足时，
只要替代路径存在即可。圆点的替代路径已经做了（上一节）：
键盘 Tab 可达 + Enter 触发 + 完整 `aria-label`。

> 可访问性不是"把所有指标刷成绿的"。
> 尺寸和准确率冲突时，**选准确率**，然后把替代路径补上。

### 七、输入框：placeholder 不是 label

`placeholder` 在用户开始输入后立即消失。读屏用户回到输入框时
听不到"这是什么框"。

```tsx
<label className="sr-only" htmlFor="chat-input">输入你的业务问题</label>
<textarea id="chat-input" aria-describedby="chat-hint" ... />
```

`aria-describedby` 指向 `.hint-row`（"Enter 发送 · Shift+Enter 换行"），
但**那个 id 原来不存在** —— 是我写 `aria-describedby` 时才补上的。
一条指向空 id 的描述等于死链接，读屏不会报错，只是什么都不读。
所以验收里查了 `describedExists`：

```
describedBy: chat-hint   describedExists: True
```

## 四之十三、高对比度模式：一整页数据消失了

Windows 的「高对比度」会触发 CSS 的 `forced-colors: active`，
浏览器**强制覆盖** `background` / `background-image` / `color` /
`fill` / `stroke`，把页面换成用户选定的配色（通常白底黑字）。

而 v4 的整套设计是「用亮度区分元素」：

```
条形    = background: linear-gradient(三级灰)
热力格  = background: rgba(...)
折线    = stroke: var(--accent)      ← 白
```

### 一、实测后果：不是变丑，是变空白

用 CDP 的 `Emulation.setEmulatedMedia` 模拟，截图核对：

| 元素 | 正常 | 高对比度 | 后果 |
|---|---|---|---|
| 折线 | `rgb(242,242,243)` | `rgb(242,242,243)` | **白线画在白底上 —— 整条线消失** |
| 条形 | 3 档灰渐变 | `backgroundImage: none` | 三档全合并，只剩虚线轮廓 |
| 热力格 | 94 种可区分色 | **全部 `rgb(0,0,0)`** | **208 格数据全丢** |
| 页面底 | `#0b0b0c` | `rgb(255,255,255)` | 深色主题被整个翻转 |

文字还能读（变黑），**但所有图表变成空白**。
这不是「高对比度模式不好看」，是这个模式下产品不可用。

### 二、第一版修法是错的：`forced-color-adjust: none`

最容易想到的办法是关掉适配：

```css
@media (forced-colors: active) {
  .bi-heat-c { forced-color-adjust: none; }
}
```

方向反了。用户开高对比度**正是因为看不见浅灰**；
保住浅灰等于在白底上画一片浅灰 —— 比不修更糟。

而且实测它连"保住半透明"都做不到：

```
读回 backgroundColor: rgb(0, 0, 0)   ← 系统色，rgba 的 alpha 被抹掉了
opacity: 1
```

`forced-color-adjust: none` 保的是「颜色值不被替换」，
但 `forced-colors` 替换 `background-color` 时会把 alpha 一起吃掉。
**所以靠 `rgba()` 的透明度表达深浅，在这个模式下从根上不成立。**

### 三、正确做法：把「强度」从颜色里拆出来

`forced-colors` **不会覆盖 `opacity`**。所以它是那个模式下
唯一还能编码「程度」的通道。

于是把热力格的颜色拆成两个变量：

```tsx
style={{
  '--heat-bg': color(c.z),        // 正常模式：带 alpha 的 rgba
  '--heat-op': String(strength(c.z)),  // 高对比模式：0.02 ~ 0.46
}}
```

```css
/* 正常模式：用颜色自己的 alpha */
.bi-heat-c { background: var(--heat-bg, transparent); }

/* 高对比模式：换成系统色 + opacity 承载深浅 */
@media (forced-colors: active) {
  .bi-heat-c { background: transparent !important; }
  .bi-heat-c::before {
    content: '';
    position: absolute; inset: 0;
    background: CanvasText;
    opacity: var(--heat-op, 0.3);
  }
}
```

三个细节都有原因：

| 细节 | 为什么 |
|---|---|
| 色块画在 `::before` 上 | 如果把 `opacity` 加在格子本身，会连异常周的 `outline` 一起变淡 —— 恰好削弱最该看见的标记 |
| `strength()` 与 `color()` 数值同源 | 否则正常模式和高对比模式会画出两种强度，等于两张不同的图 |
| 用 `Canvas` / `CanvasText` / `GrayText` / `Highlight` | 系统色由用户的主题决定，白底黑字和黑底黄字都能正确对比。写死 `#000` 在黑底主题上就瞎了 |

折线同理，`stroke` 写在内联属性上，普通选择器压不住，要 `!important`：

```css
@media (forced-colors: active) {
  .pg-chart-svg path[stroke] { stroke: CanvasText !important; }
}
```

### 四、条形图：三档灰没了，但数据没丢

修后实测 `barDistinct: 3 → 1`，13 根条同色。**这是对的**——
系统色只有一个前景色，三档灰在这里必然被抹平。

但条形的**长度**仍然编码数值，只要条可见，信息就在。
实测宽度 `[303, 142, 110, 77]`，与 28.33% / 13.27% / 10.26% / 7.17% 一致。

> **一个图表如果只靠颜色深浅传信息，它在高对比模式下必然失效；
> 如果能靠长度/位置传信息，配色被覆盖也还读得出来。**
> 这不是为高对比度做的妥协，而是好图表本来就该有的冗余。

热力矩阵没有长度可用，所以它是唯一"只能靠拆出 opacity 才救得回来"的图。

```
普通格  --heat-bg: rgba(220,238,233,0.145)  outline: 透明

```

**这一节最值得记的一点**：开关在用户系统里，不在产品里。
作者自己永远不会触发它，所以它永远不会被发现 ——
除非有人专门去模拟一次。

## 四之十四、52 个点里只有 5 个能碰

总览页那张「52 周退货率」走势图，改造前只有一个交互点：
异常周的红色圆点，点它跳归因。

看起来挺合理 —— 异常才是重点。但实测一遍就发现不对：

```
52 个数据点
  ├── 5 个异常周  → 可悬停、可点击、可 Tab 聚焦
  └── 47 个正常周 → 鼠标划过毫无反应，纯图形
```

### 为什么这是问题，不只是"不够花哨"

读者站在这张图前面，真正想问的往往是：

- 「W17 那个小鼓包到底是多少？」→ 正常周，点不了
- 「这周比基线高还是低？」→ 正常周，读不到
- 「为什么 W30 看着挺高却不算异常？」→ 想进去看两条判据各差多少，进不去

而**旁边紧挨着的热力矩阵，208 个格子每一格都能读、都能点**。
同一屏里两种交互语言：一张图什么都能碰，一张图基本碰不到。

### 改法：整条线都可读

原则是「鼠标在哪，就读哪一周」，而不是「只有被判定为重要的地方才响应」。

```
鼠标在图上任意位置 → 吸附到最近一周 → 准星 + 浮层读数
点击任意一周       → 进该周判定页（正常周也进，回答"为什么它不算异常"）
异常周圆点         → 保留 Tab 聚焦，方向键在异常周之间跳
```

### 五个实现决定，每个都有原因

**① 按 x 反算最近周，不给每周画透明矩形**

52 个矩形 = 52 个 DOM 节点 + 52 套事件，而且宽度 19px 的矩形之间
必然留 1–2px 缝隙（取整误差），鼠标划过会「闪一下又没了」。
用 `clientX` 反算索引，热区是连续的一整条，不存在漏格。

**② 索引必须按 svg 的 `getBoundingClientRect` 换算，不能用 clientX 直接算**

`viewBox="0 0 1000 220"` + `preserveAspectRatio="none"`，实际宽度随窗口变。
实测 1410px 视口下 svg 宽 1122px，**1 个 CSS 像素 ≠ 1 个 viewBox 单位**，
直接用 clientX 会越往右偏得越多（图幅 1000 vs 实际 1122，右端差 12%）。

**③ 点击事件挂在容器上，不挂在圆点上**

原来圆点上有 `onClick`。改造后容器也响应点击，如果不清掉圆点那个，
**点在红点上会触发两次 `onPick`** —— 一次点击跳两次页，带过渡的路由里看得见闪烁。
两者算出的周次相同，重复纯属多余，所以圆点上只留 `onFocus/onBlur/onKeyDown`。

**④ 浮层要会翻面**

图只有 220px 高，浮层约 150px。默认「右下 14px」会正好压住光标右侧那段折线
——而那一段恰恰是读者接着要看的走势。改成按光标在图中的上下半区决定翻转方向：

```tsx
const above = e.clientY > box.top + box.height * 0.55
show(e, tipFor(series[i]), above)
```

翻到上方时用 `translateY(-100%)` 自己往上撑，而不是写死一个高度：
内容行数会变，写死高度会在换行时把浮层压扁，或者露出一截空白。

**⑤ 准星不加过渡**

跟随类元素一旦对位置做 transition 就会「追」着鼠标跑，看起来像掉帧。
这和热力格 tooltip 的「跟随而不滞后」是同一条理由：
它是读数辅助，不是动画，越即时越好。

### 顺带修的：浮层盖住数据的通用问题

`useTip()` 原来只有「右下 14px」一种摆法。加了一个可选参数 `above`，
不传时行为完全不变 —— 热力图的 tooltip 不受影响（已实测确认仍在右下）。

### 验证：截图看不出来的东西，只能靠断言

这个 bug 的特征是**图长得完好，只是不响应**。所以测试不能看截图，必须真的动鼠标：

```
[5] 走势图：整条线是否可读（不再只有异常周）
    OK   悬停非异常周 → 浮层: 第 6 周 / 准星 x=127.5 / 光标点 rgb(242, 242, 243)
    OK   移出图外 → 浮层 False / 准星 False
    OK   点击非异常周 → #/dashboard → #/attribution/6
```

另外用 CDP `captureScreenshot` 的 `clip + scale` 放大 3.4 倍核对准星渲染，
确认 1px 虚线在灰色带上真的看得见（实际 `stroke: rgba(255,255,255,.28)`，
`dasharray: 2px 3px`，落在格子中央不遮挡折线）。

### 高对比度模式：新增的两处也补了

准星和光标点是新增元素，默认的 `rgba(255,255,255,.28)` 在白底主题下直接消失
——正是那个模式最不能接受的。补进原有的 `@media (forced-colors: active)` 块：

```css
.pg-cross      { stroke: CanvasText !important; }
.pg-cursor-dot { fill: CanvasText !important; stroke: Canvas !important; }
```

### 写测试时踩的两个坑（比功能本身更值得记）

**坑一：`js()` 出错时返回的是 `{"__error__": ...}`，一个 truthy 的 dict**

我的浏览器封装在页面 JS 抛异常时返回这个字典。于是：

```python
geo = br.ctl.js(...) or {}
if geo:                    # ← 出错时这里也是 True
    geo["norm"]            # ← KeyError: 'norm'
```

`KeyError` 看起来像"测试脚本写错了"，掩盖了真正的原因「页面里那段 JS 崩了」。
现在先判 `"__error__" in geo` 再判内容，两种失败分开报。

**坑二：靠上一步的残留状态做前置条件，改一次用例顺序就全崩**

第 4 节测「空格键不滚页」，用例本身是 `preventDefault()` + `onPick()` ——
滚动确实被拦住了，**但页面已经跳到归因页了**。
第 5 节我原以为 `history.back()` 能兜住，结果 `wait_until('.pg-dot-g')`
被**旧页面**的元素立刻满足，紧接着 `querySelector('.pg-chart-svg')` 拿到 null。

修法不是再加一个 `sleep`，而是让第 5 节自己负责自己的前置条件：

```python
br.ctl.js("location.hash = '#/dashboard'")
arrived = br.ctl.wait_until(
    "(() => { const s = document.querySelector('.pg-chart-svg');"
    " return !!s && s.getBoundingClientRect().width > 100; })()", 30)
```

两个细节：等待条件要挑**只有目标页才有**的元素；还要判宽度 ——
元素存在但尺寸为 0（还在布局）时算出来的坐标全是 0，测试会"通过"但什么都没验。

### 教训（续）

33. **"只有重点可交互"通常是个借口**。判断一段数据重不重要是读者的事，
    不是作者的事。让所有点都能读，代价是一段坐标反算，收益是 47 个不再沉默的周。
34. **`preserveAspectRatio="none"` 的图，坐标必须从 rect 换算**，
    clientX 直接减 left 是错的，而且错得随窗口宽度变化，很难在截图里看出来。
35. **不要在两处挂同一个事件**。容器和圆点都响应点击 = 一次点击走两遍，
    带过渡的路由会闪。
36. **跟随类视觉（准星、光标点）一律不加过渡**。要的是即时，不是平滑。
37. **测试的前置条件要自己建立**，不能依赖上一条用例留下的状态。
    这类"碰巧正确"的测试，改一次顺序就会集体失效。
38. **错误返回值如果是 truthy 的容器，判错会变成看似无关的 KeyError**。
    `{"__error__": ...}` 这种设计要在用之前先分流。

### 四之十四、52 周曲线：从"读一个点"到"框一段区间"

#### 加之前的状态

v4.6 已经把整条线做成可读的：悬停出准星和浮层、点任意一周进判定页。
但这只能回答**单点问题**（"W26 是多少"），回答不了最常被问的那类问题：

> 下半年是不是整体变差了？这段里哪几周要解释？

前者是区间问题。而原来看区间只能靠眼睛在 52 个点上估，
或者把浮层从 W27 一周一周划到 W52 —— 划 25 次，中途一松手就全丢。

#### 现在能做什么

```
拖选一段   → 选区外的曲线压暗，选中段浮出来
           → 图下方出摘要：跨度 / 均值 / 比基线 / 趋势 / 退货订单 / 异常周 / 峰谷
           → 下方热力矩阵同步高亮对应列
点红点/任意一周 → 进该周判定页（原有行为不变）
近13/26/52 周 → 一键选区（键盘和触屏的唯一入口）
Esc        → 退出选区
```

联动是这次最值钱的一处：**"这一周整体偏高，是哪几个类目撑起来的"**
必须两张图一起看才答得出来。原来只能人肉在 208 个格子里找那一列。

#### 为什么趋势用最小二乘，不用"末周 − 首周"

均值只回答"这段整体偏高还是偏低"，**回答不了方向** ——
一个 +3pp 然后 −3pp 的段落，和一个平稳段落，均值一模一样。

但趋势也不能用首尾两点：首尾各是一个单周观测，
**挑中一个异常周就能把结论整个反转**（W49 恰好是个低谷，拿它当终点会得出"在改善"）。
回归用上区间内全部点，单周噪声被平均掉。

实测 W15–W39（25 周）：均值 13.28%、比基线 −0.11pp 看着很平，
但趋势是 **+0.27pp/10周 恶化**。这两个数不矛盾 —— 均值说的是水平，趋势说的是方向。

周数 < 4 时不出趋势：三个点连一条线都能算出 slope>0，
给出的精确数字全是噪声，**那比不给更糟**。

#### 三个踩到的坑

**坑一：快捷按钮的点击被容器吃掉**

按钮在图表容器内部，点击会冒泡到容器的 `onClick`。容器的逻辑是
"点到图外空白 = 清空选区"，于是：

```
点「近 26 周」→ 选区建立了 → 冒泡 → idxAt 算出坐标在图外 → 清空
```

选中瞬间就消失，看起来像按钮没接上。更糟的是摘要条里的「清除」：
清掉选区后继续冒泡，**顺带跳进了某一周的判定页**。

修法不是给每个按钮加 `stopPropagation`（以后再加按钮还得记得加一次），
而是在容器里按事件来源排除：

```tsx
if ((e.target as HTMLElement).closest('.pg-selbar, .pg-selgo')) return
```

**坑二：`--bg` 压暗等于没压**

遮罩一开始复用了 `--bg`。实测几乎看不出来 ——
卡片是 `#151517`，`--bg` 是 `#0b0b0c`，**只差 10 级亮度**。
另立 `--scrim: rgba(0,0,0,.58)` 才看得出"这块被排除了"。
复用语义不同的颜色变量，是这类"改了但没效果"的常见来源。

**坑三：高对比度下 `box-shadow` 会被整条丢弃**

联动高亮原本用 `box-shadow: inset 0 0 0 1.5px`。正常模式没问题，
HC 下读回来是 **`boxShadow: "none"`** —— 加 `!important` 也留不住，
因为 `forced-colors` 是在计算值层面清掉它的，和选择器优先级无关。

换成 `::after` + `border` 才活下来。但接着发现**新的撞车**：

| | outline | 联动边框 |
|---|---|---|
| 纯异常周 | `2px solid` 黑 | 无 |
| 异常+联动 | `2px solid` 黑 | `2px solid` 黑 |

颜色全被抹成黑，两者长得一样，含义却相反（"数据异常" vs "你正在看这列"）。
HC 下还能自由支配的只剩**线型**：

```
异常周 = 实线   （要紧的事，用最实心的语言）
联动   = 虚线   （临时的，随鼠标走，不该看起来同样权威）
```

表头不能用颜色区分（`color` 也会被强制成 `CanvasText`），改用下划线。

遮罩在 HC 下则**必须整个关掉**：它的作用是压低对比，
而高对比度用户要的正是最高对比 —— 半透明黑幕恰恰在帮倒忙。
选区本身改用 `Highlight` 系统色描边，边界照样清楚。

#### 验收

`check_a11y.py` 新增第 6 节，五条断言：

```
OK   拖选 W11–W31 → 摘要: 第 11–31 周 21 周 均值 13.24% 比基线 -0.15pp 趋势 ↓ 改善 -0.14pp/10周
     拖动中有框=True 松手后虚线=None 遮罩宽度=[199, 430]
OK   热力图联动 84 格（21 周 × 4 行 = 应 84）
OK   松手不误触跳页 → #/dashboard
OK   Esc 清除 → 摘要 False / 框 False / 联动残留 0
OK   快捷选区 3 个按钮（高 24px）→ 第 27–52 周 / 联动 104 格
```

格数要精确到 84 而不是"大于 0"：数字对不上说明传给热力图的周次错了，
而"有几格亮着"这个粗判会放过差一到两周的错误。

#### 补做的两件事（第一版漏的）

**一、触屏根本拖不动**

第一版只绑了 `onMouseDown/Move` + `window.mouseup`。
桌面自动化 5 条全过，**触屏一条都不行**（`box=False / bar=False`）。

原因：移动浏览器会把 touch 合成为鼠标事件，但前提是浏览器判定这段手势
"不是滚动"。图只有 220px 高、手指滑动又多带垂直分量，**合成事件根本没来**。
而桌面自动化派发的是 `dispatchMouseEvent`，压根测不出这个缺口。

修法：

```css
.pg-chart { touch-action: pan-y; }   /* 上下滚你管，左右拖我管 */
```

```tsx
onTouchStart → 只记锚点，不开始框选   （还分不清想滚还是想框）
onTouchMove  → dx≥8 且 dx>dy 才算拖拽，然后 preventDefault
onTouchEnd   → 复用鼠标那套 selCommit
```

三个细节：

- **8px 的观察期**：手指按下去时，想滚页面和想框选区长得一模一样。
- **dx>dy 才拦**：提前 `preventDefault` 会连带禁掉纵向滚动，
  用户会觉得"手指在这块图上失灵"。
- **`touch-action: pan-y` 而不是 `none`**：图上纵向滚动是正常需求。
  另外这条在 Chrome 里会**抑制合成鼠标事件**，和 JS 里的 `preventDefault`
  是同一件事的两道保险。
- 触屏拖完浏览器仍会补发一次 `click`（tap 语义），
  用一个 600ms 的时间戳挡掉，不能复用 `draggedRef` ——
  它在 mouseup 后一个宏任务就清了，而合成 click 要晚 300ms。

实测：

```
OK 触屏横拖 → 框 True / 第 15–38 周 / 联动 96 格 / 未误跳 #/dashboard
OK 触屏纵滑 → scrollTop 120 → 235 · 没误触框选 False/False
```

**二、发现一条一直在假通过的测试**

给触屏补用例时顺手怀疑了第 4 节「空格键不滚页」，一查果然是假的：

```python
br.ctl.js("window.scrollTo(0, 240)")   # ← 对这个页面毫无作用
y0 = br.ctl.js("window.scrollY")       # ← 恒为 0
...
ok = y0 == y1                          # ← 0 == 0，永远成立
```

**滚动容器是 `.app-scroll`（`overflow-y: auto`），不是 window。**
`window.scrollTo` 对它无效，所以 `y0` 和 `y1` 都是 0 ——
这条断言跑了不知道多少轮，一次都没真正执行过。

改成读 `.app-scroll` 之后，测出 `scrollTop 200 → 0`，看着像"滚回顶部了"。
但再查发现：**空格是双重语义** —— 既 `preventDefault()` 防滚屏，
又 `onPick()` 跳到归因页；一跳页，新页面的 scrollTop 自然是 0。

用位置差来判，怎么写都会把"滚动了"和"换页了"混在一起。所以直接判因果：

```js
document.addEventListener('keydown', (e) => {
  if (e.code === 'Space') window.__sp = e.defaultPrevented
}, false)
```

监听挂 `document`：React 把事件委托到 `#root`，`#root` 是 body 的子节点，
冒泡顺序保证 document 的监听在 React handler 之后执行，读到的是最终值。

```
OK 空格 defaultPrevented=True（拦住 = 浏览器不滚）· 起点 scrollTop 200
```

代码本身是对的，**错的是测法** —— 但它给出的绿灯骗了整轮验收。

### 教训（续）

39. **悬停能回答"是多少"，回答不了"在变好还是变坏"**。后者需要区间和斜率。
40. **趋势要用回归，不要用首尾两点**。首尾是两个单周观测，一个异常周就能翻转结论。
41. **样本太少时宁可不给结论**。3 个点算出来的斜率看着精确，全是噪声。
42. **容器级的事件处理要把"内部按钮"排除掉**，否则按钮语义会被容器语义覆盖。
43. **复用语义不同的 CSS 变量，会造成"改了但没效果"**。
    压暗要用比卡片更深的色，`--bg` 不够深。
44. **`forced-colors` 会丢弃 `box-shadow`，`!important` 也救不了**。用 border 替代。
45. **HC 下颜色全被抹平后，还能用的通道是线型、下划线、位置**。
    两个含义不同的标记不能共用同一个形状。
46. **遮罩类效果在 HC 下要关掉**。它压低对比，而那个模式要的正是最高对比。
47. **桌面自动化测不出触屏问题**。`dispatchMouseEvent` 和真实手指是两条路径，
    必须显式开 `setTouchEmulationEnabled` 并派发 touch 事件。
48. **`touch-action: pan-y` 比 `preventDefault` 更早生效**，
    它决定浏览器要不要把这段手势交给 JS，两层都要做。
49. **判断"能不能滚"，先确认滚动容器是谁**。
    `window.scrollY` 在 `overflow:auto` 的子容器布局里永远是 0。
50. **恒真的断言比没有断言更危险**。`0 == 0` 这种通过率 100% 的用例，
    会把真问题一起盖住。每个断言都该问一句"它在什么情况下会失败"。
51. **一个键承载两种语义时，不要用"结果状态"判断其中一种**。
    空格既防滚屏又触发跳转，只能用 `defaultPrevented` 这类因果证据。

## 四之十五、"看着能交互，其实不能"比静态更糟

评论页的「分周情感走势」是全站最后一张静态图。它的毛病不是"没做交互"，
而是**复用了 `.pg-chart` 类，于是继承了 `cursor: crosshair`**：

```
鼠标移上去 → 十字光标（暗示"这里可以框选"）
按下拖动   → 什么都没发生（组件里 0 个事件）
```

这比一张看起来就静态的图更糟：**用户会以为是自己没点对，而不是这里没有功能。**
一个人反复在图上拖三次、以为是浏览器卡了，然后放弃 —— 整个过程他都不会来问。

### 做了什么

按趋势图（四之十四）那套语汇复刻，不新造交互：

| 操作 | 得到什么 | 回答什么问题 |
|---|---|---|
| 悬停 | 单周负评/正评、样本、**抽样误差 ±x.x pp** | 这一周的 12% 是真的吗 |
| 拖选 | 区间负评均值、**趋势斜率**、峰谷、样本合计 | 这一段在变好还是变坏 |
| 快捷按钮 | 近 4 / 13 / 全部 | 键盘和触屏怎么拿区间结论 |
| Esc | 清选区 | — |

### 三个不显然的决定

**一、把抽样误差放进浮层**

负评率 = 命中数 / 样本数。同样写着 "12%"，
样本 40 条的周和样本 2000 条的周，95% 置信区间半宽差 7 倍：

```
n=274  → ±3.6pp    "样本中等，±2pp 以内的变化不必当真"
n=2000 → ±1.3pp    "样本充足，这一周的百分比可以直接用"
n=30   → ±10pp     "样本偏少，周间涨跌主要来自抽样波动"
```

没有这个数，读者会把 W31 的 12% 和 W32 的 9% 读成"降了 3pp"，
而样本少的时候这个差完全落在噪声里。
顺带解释了图例那句"每周样本 < 30 条不画"——**不是省事，是 ±10pp 的柱子画出来全是尖刺**。

**二、删掉原生 `<title>`**

原来每个圆点挂了 `<title>`。加了自绘浮层之后，
悬停会**同时弹出两层提示**，屏幕上同一个数字报两遍，而且原生那层样式不可控。
现在查 `document.querySelectorAll('.pg-chart-svg title').length === 0`。

**三、点少的时候，让数字自己承认不可靠**

实测「近 4 周」给出 `-13.98pp/10周` —— 精确到小数点后两位，看着非常权威。
但 4 个点里挑中一个噪声大的周，斜率能翻几倍甚至换符号，**这个精度是假的**。

这正是我在教训 41 里写过的那条，然后自己又犯了一次。
加了一句 `点少，仅看方向`（n < 6 时显示），并且把这个场景写成了验收项：

```
[5] 点太少时，趋势要自己承认不可靠
    OK 近 4 周带「点少，仅看方向」提示 ✓
```

> 一条经验：**写进 README 的教训，不会自动变成代码里的约束。**
> 除非它同时是一条会失败的测试。

### 验收（check_a11y 新增第 7 节，13 项）

```
[1] 悬停读数        浮层有值 · 负评10.22+正评88.69=98.91%（应≈100）· 准星 · title 残留 0
[2] 拖选区间        摘要含均值/趋势/样本 · 框留在图上 · 快捷区让位
[3] Esc 清除        摘要和框都清掉
[4] 快捷选区        3 个按钮 · 可聚焦 · 点击出结果
[5] 假精度防护      近 4 周带「点少，仅看方向」
评论走势图问题：0 处
```

判据特意不写"有没有浮层"，而是**数字对不对**：
负评率 + 正评率 ≈ 100（两类互斥），抽样误差 > 0（样本量真的参与了计算）。
只验"浮层出现了"的话，浮层里写死一个 `12%` 也能过。

### 教训（续）

52. **复用交互样式类，等于承诺了交互**。`.pg-chart` 带 `cursor: crosshair`
    和 `touch-action: pan-y`，静态图用它就成了"能拖但拖不动"。
    要么给静态图换类，要么把交互补上。
53. **浮动提示只能有一层**。原生 `<title>` 和自绘浮层会同时出现。
54. **百分比类指标必须带样本量或误差**。同一个数字，可信度能差 7 倍。
55. **写进文档的教训不会自动变成代码约束** —— 除非它同时是会失败的测试。

## 四之十六、图表形式要跟着数据形状选，不是跟着"好看"选

归因页两块卡各补/修了一个视图。判断依据不是"多一张图更丰富"，
而是**现有图表在回答哪个问题上漏了一半**。

### 一、新增「本周vs基准」哑铃图

原来那四张各有盲区：

| 图 | 回答 | 漏掉 |
|---|---|---|
| 贡献瀑布 | 各节怎么加总成总差额 | 看不出谁的绝对水平高 |
| 订单占比（环形） | 盘子怎么分 | 与退货率无关 |
| 差距（发散条） | 差多少 | **丢掉绝对水平** |
| 规模×差距（斜率） | 两个排名是否错位 | 数值不在同一把尺上 |

发散条那个漏洞最要命：

```
类目 A  12% → 20%   差距 +8pp
类目 B  30% → 38%   差距 +8pp
```

发散条画出来**一模一样**，但 B 才是真麻烦 —— 它本来就高，这周又往上走。
表格里有全部数字，可 4 行 × 7 列没人会逐行做减法。

哑铃图把两件事拆成两个视觉通道：

```
点的横向位置 = 本来多高（共用一把尺，可跨行比）
两点的距离   = 这周差了多少（就是发散条画的那个量）
```

实测第 44 周正好是这两种情况的对照：服饰 `28.0% → 36.8%`（本来就最高，还跳了 8.8pp）
vs 数码 `18.6% → 20.5%`（居中，涨得也少）。只看差距排序两条都是"要查"；
看哑铃图，优先级一目了然。

设计上还有两条：

- **点的大小按订单量开方缩放**（面积正比于规模）。
  线性映射下 8450 单的点会比 3929 单的大一倍多，视觉上过于夸张。
- **基准点空心、本周点实心**。形状差是给色弱读者的第二通道，
  颜色（涨红跌绿）只是第一通道。

### 二、修「规模×差距」点不中

`Slope` 两端都是 `<button>`，有 hover、有 `onFocus` 浮层、有 `aria-label` ——
**就是没有 `onClick`**。而卡片说明写着：

> 点选一个类目可钉住，切视图和明细都会保留。

说明与实现不一致。用户点两次，以为是浏览器卡了，然后放弃。
补上 `onPick` 后两端都触发同一个选择（在读者眼里它们本来就是同一个东西），
并加了 `is-pick` 样式把"钉住"和"悬停"分开 —— 两者语义不同，不能共用 `on`。

### 三、修两个渲染缺陷

**树图小格子的文字被从中间截断**

`.bi-tree-c` 是 `overflow: hidden`，而一个格子要塞三行（原因名 / 金额 / 条数），
合计约 50px。按金额分配面积后，末尾小格只有 30~40px 高，
于是"1.8万"只露上半截 —— 看起来像渲染坏了，而不是"这里放不下"。

用容器查询按格子高度逐级降级：

```css
.bi-tree-c { container-type: size; }
@container (max-height: 52px) { .bi-tree-cs { display: none; } }  /* 去掉第三行 */
@container (max-height: 40px) { .bi-tree-cv { display: none; } }  /* 只留原因名 */
```

两级都是"少显示一行"，不是"截断一行"——半行字比没有更糟。

顺带一个坑：`@container` 只能命中容器的**后代**，
在里面写 `.bi-tree-c { justify-content: center }` 不报错也不生效，
得用子元素的 `margin-block: auto` 达到同样效果。

**象限图的角标和轴标叠在一起**

`.bi-q-q` 这个类**原来没有任何 CSS 规则** —— 四个象限名只靠内联的
`right/top/bottom/left` 勉强落在角上，字号和颜色全是继承来的。
左下角的"损失小"和画布外紧贴的"可再售率"垂直只差 8px、字号都是 9px，
实测读起来是三行糊在一起的字。
补上 `.bi-q-q` 的定位/字号/颜色，底角上移 6px，轴标签 margin 从 6px 加到 12px。

### 验收（check_a11y 新增第 8 节，19 项）

```
[涨在哪] 6 个视图    瀑布/本周vs基准/占比/差距/规模×差距/明细 —— 全部有图形
[卖的东西变了吗] 5 个视图   份额/损失×可再售/条数×金额/归属树/明细
[钉住]   斜率图点「服饰」→ 2 个节点同时亮；切到明细仍高亮 1 行
[布局]   两个分段控件右边界 1363 ≤ 卡片右 1378，未溢出
归因页视图问题：0 处
```

两处判据特意写得很具体：

- **不能只数 `svg` 里的元素**。本项目这 7 张图有两种实现 ——
  Donut/DualRing/Slope 用 SVG，Waterfall/Diverging/Quadrant/Treemap 用 HTML+CSS。
  第一版只查 `svg path, rect, ...`，四张 HTML 图全被判"空白"，其实渲染得好好的。
  判据要同时看 SVG 图形和 HTML 子元素。
- **"钉住"要跨视图验**。只验点完当场有没有高亮是不够的 ——
  卡片承诺的是"切视图和明细都会保留"，那就必须切过去再看。

### 教训（续）

78. **相同差值 ≠ 相同严重程度**。只要图里只画差值，就必然混淆
    "本来就高"和"这周才冲上去"。至少要有一个通道表达绝对水平。
79. **有 hover/focus 但没有 click，是最难被发现的缺失** ——
    它看起来"像能点"（光标变了、浮层弹了），点了却没反应，
    用户会归因于自己操作不对。按钮的完整语义是"能聚焦 + 能激活"。
80. **`overflow: hidden` 会从中间切掉一行字**，看起来像渲染 bug。
    矮容器里要显式降级显示级数，而不是让它自己截。
81. **`@container` 不能给容器自身写样式**（写了不报错、不生效）。
    顺带：一个元素有 className 不等于它有 CSS 规则，可能是纯靠内联样式存活。
82. **验证"渲染出来了"不能只看一种实现**。同一个页面里 SVG 和 HTML 图混用，
    只按 SVG 查会漏判一半。

## 四之十六A、表格不是唯一的答案：四张图各管一个问题

归因页原来两个模块都是纯表格。表格没错，但它只回答"这个数是多少"，
回答不了"这些数之间是什么关系"——而**分解、构成、方向、取舍**
恰恰都是关系。

按数据形态选了四种形状，每一张都对应一个只能用它回答的问题：

| 模块 | 图 | 回答的问题 | 为什么非它不可 |
|---|---|---|---|
| 类目贡献 | **瀑布** | 各节加起来等于全店 Δpp 吗 | 只有瀑布能表达"加法闭合" |
| 类目贡献 | **环形** | 订单在类目间怎么分 | 部分与整体，且只有 4 项 |
| 类目贡献 | **发散条** | 比基准高还是低 | 方向变成位置，不看数字也懂 |
| 原因构成 | **发散条** | 构成变了没 | 同上 |
| 原因构成 | **象限散点** | 先管哪个 | 两个维度 + 规模，合成一句话 |

原表格都保留成"明细"页签 —— 图给方向，表给证据，谁也不替代谁。

### 一、瀑布图暴露了一个之前没被说清的量

表格里 `贡献` 那一列是 4 个独立数字，读者看不出它们**加起来应当等于全店 Δpp**。
一画瀑布就露馅了：第 49 周四个类目合计 `-1.69`，而 `delta_pp` 是 `-1.84`。

差的 `0.15` 不是舍入误差，是**结构效应**：

```
Σ(本周份额 × 类目差距)      = -1.70pp   ← 类目内部变差
Σ(本周份额 × 类目基准率) − 全店基准率 = -0.14pp   ← 订单迁移
                       合计 = -1.84pp ✓
```

订单从退货率高的类目流向了低的类目，所以即使每个类目内部都没变好，
全店退货率也会降。**这个值由后端算好给出来**（`pages.py` 的
`structure_effect_pp`），前端不自己减 —— 否则"这个差是什么"
就变成了一个没人命名的减法。

> 图会逼你把量说清楚。表格里能含糊过去的东西，画成瀑布就是一个对不上的口子。

### 二、环形图踩的两个坑

**坑一：颜色太暗 = 看起来像图缺了一块**

第一版配色最后一个用了 `#56565e` —— 那其实是色板里的 `--fg-5`，
定位是"刻度线/占位"。在 `#151517` 卡片上几乎看不见，
截图里那个扇区像**凭空少了一块**，而不像"第四个类目"。

改成从 `--fg` 往下取四档（`#f2f2f3 / #c6c6cc / #9c9ca4 / #7c7c84`），
最暗的在卡片上仍可辨。

**坑二：颜色跟着数组下标走 = 同一类目换周就变脸**

这一页的类目顺序按"贡献绝对值"排，换一周顺序就变。
按下标配色的话，同一个「服饰」这周白、下周深灰，读者跨周对比会以为看错了图。

改成**对全部类目名排序后取位置**。不用哈希 —— 4 个类目配 4 个色，
哈希撞车概率不低，撞了就变成两个类目同色，比顺序变化更糟。

### 三、象限图：两个维度合成一句话

表格能告诉你「破损损失 16789、可再售 8.5%、份额 +1.56pp」，
但你得自己在脑子里把三列合成一个决定。真实的决策问题只有一个：
**哪个原因既损失大、又基本挽回不了？**

把"损失"和"可再售率"分到两个轴，答案就变成位置：
右下（损失大 + 不可再售）= 真金白银，最该先管；右上 = 能抢回来，优先二次上架。
气泡大小用条数，顺带回答"这类退货多不多"。

分割线用**中位数**不用平均值：平均值会被最大的那个点拽过去，
导致某一象限只剩孤零零一个点，象限就没意义了。

**标签重叠是真问题。** 左下三个点（售后流程问题 51.1% / 功能性能故障 49.3% /
时效慢 46.7%）挤在 4% 的高度里，三个中文标签叠成一团。两条规则一起用：

1. 点在右半边 → 标签挂左侧，左半边 → 挂右侧，总是伸向更空的那边
2. 同侧标签按 y 排序逐个下压，保证最小行距 14px（用 px 算，不用百分比 ——
   4% 在 258px 里是 10px，而"一行小字"要 14px）

**标签还必须脱离气泡的层叠上下文。** 第一版把标签放在气泡按钮内部，
于是它受气泡 `z-index:1` 约束 —— 子元素的 z-index 只在父级上下文内比较，
写多大都压不到旁边那个气泡上面。实测「描述与实物不符」的标签被邻泡盖掉一半。
抽成同级的独立层后才彻底解决。

### 四、四张图里只有一张需要为高对比度特殊处理

瀑布、发散、象限全部靠**位置和长度**编码信息，颜色被 `forced-colors`
抹平也不影响读数 —— `bi-charts` 那段 HC 样式只是"让它们看得见"，不需要换编码通道。

环形图躲不开：扇区天生靠颜色区分，HC 下 `fill` 全被抹成同一个色，
四个扇区合成一个实心圆。用 `opacity`（不受 forced-colors 影响）按序号做成梯度，
配合扇区之间的缝隙，边界仍分得清。

**但真正的保底是图例**：每个图例项都写着自己的百分比和绝对单量，
那是文字，HC 下照样能读。所以即使图和图例对不上号，**数字一个都没丢**。

### 五、验收（check_a11y 新增第 8 节，14 项）

判据不写"图画出来了没"，只写"数字对不对"——四张图各有各的假法：

```
[1] 瀑布    台阶 6 个 · 末柱 is-total · 总柱最高 153px · 柱高随数值单调
[2] 环形    扇区 4 · 环 180x180（相等=不是椭圆）· 最大扇区=最大占比 · 图例同色
[3] 发散    4 行方向全对 · 条长随绝对值递增 [73,149,177,472]
[4] 象限    8 泡 · top∈[12%,88%] · 标签无重叠 · 标签未跑出图外
归因图表问题：0 处
```

写这节时自己先踩了一次：判"图例和扇区同色"时直接比字符串，
但扇区 `fill` 是 `#9c9ca4`、图例读回来是 `rgb(156, 156, 164)`，
`hex in rgb_str` 永远为假 → 4 个类目全报"颜色不一致"。
**断言写错比没断言更难查**：它给红灯，会让人去改一个本来没坏的东西。
改成两边都归一成 `(r,g,b)` 再比。

### 教训（续）

56. **表格回答"是多少"，图表回答"是什么关系"**。分解、构成、方向、取舍都是关系。
57. **图画出来会逼你把量说清楚**。表格里能含糊的差额，瀑布上就是一个对不上的口子。
58. **色板里的弱色不能拿来当分类色**。`--fg-5` 是"刻度线"级别的，当图例色就像缺了一块。
59. **分类颜色按名字固定，不按数组顺序**。排序一变就换色，跨周对比全乱。
60. **百分比图必须有文字图例兜底**，颜色在那个模式下不可靠时，数字还在。
61. **子元素 z-index 压不过父级之外的兄弟**。要压过去只能脱离那个层叠上下文。
62. **4 个项目不要用散点/气泡**。位置比较是四种视觉编码里最不准的一种，
    点少时反而不如"两列排名 + 连线"直白。
63. **`preserveAspectRatio="none"` 会拉伸 `strokeWidth`**。
    坐标要用百分比、线宽要固定像素，只有 `vector-effect: non-scaling-stroke` 能同时满足。
64. **环形/饼图的分母必须是"全部"，不是"Top-N 之和"**。
    两者不等时，环上会留一道没名字的缺口 —— 读者只会认为渲染坏了。
65. **残差不该被藏起来，该被画出来**。补一节「其余未单列」，
    那 1.3% 本身就是一个值得追的事实。

## 四之十六B、第六个视图：这笔钱有多少能拿回来

原因构成这块原先有 5 个视图，各自答一个问题：

| 视图 | 回答 |
|---|---|
| 份额变化 | 构成变没变（是不是换货） |
| 损失×可再售 | 损失大且卖不掉的在哪 |
| 条数×金额 | 按条数排会不会排错 |
| 归属树图 | 该找哪个部门谈 |
| 明细 | 原始数字 |

**没有一个是回答"能救回多少"的。**

数据里明明有 `loss` 和 `resellable`，但一直只被当成散点的纵轴。
而这恰恰是决定动作的那个数：

```
原因 A：亏 10 万，可再售 80%  → 降价清库存，能拿回 8 万
原因 B：亏 10 万，可再售 10%  → 只能报损，别往里投人力
```

两者损失一样，处置方式完全相反。按损失排序它们并列，
按可挽回金额排序差了 8 倍 —— **该按后者排优先级。**

### 为什么是堆叠条，不是饼图

要同时读两件事：每个原因的**总量**（条长）和**可挽回占比**（段内比例）。

饼图只能读其一。8 个原因切成 8 块的饼，既看不清总量也看不清比例，
而且面积角度是人眼最不擅长的比较方式。堆叠条共用一把横轴，两个通道都保住。

（环形图仍然保留，用在类目贡献那块 —— 那里只有 4 个类目，
且问题确实是"部分与整体"。**图表形式跟数据形状走，不跟"丰富度"走。**）

实测第 44 周：

```
可挽回 8.5万 / 损失 34.8%
描述与实物不符   ████████░░░░░░░░  36%   2.1万 / 5.8万
价值感知不符     ██████████████░░  60%   1.7万 / 2.9万
尺码版型不符     ████████████████  81%   1.5万 / 1.8万
```

「尺码版型不符」损失只有 1.5 万，但 81% 能救；
「描述与实物不符」损失 5.8 万，却只有 36% 能救。
按总损失排，前者根本排不上号；按可挽回金额排，它和第一名只差 1.4 倍。

### 三个实现决定

**一、条宽按"占最大值"，不是占 100%**

否则 8 个原因里最小的那条会细成一根线，读者分不清"很小"和"没有"。

**二、百分比定位在轨道右端，不跟在条后面**

第一版写成条后紧跟，条一长就把百分比推到轨道外面 ——
实测 8 行里有 4 行的比例直接看不见。这是截图核对时才发现的：
数字不是没渲染，是被推到了可视区外。

改成绝对定位在轨道右端后，无论条多长数字都在同一列，
竖着扫一列就能比较 —— 这本身也比"跟着条尾巴跑"更好读。

**三、高对比度下靠位置和数字，不靠颜色**

`forced-colors` 会把两段配色都吃掉。但这张图的信息不只在颜色里：

```
左段 = 可挽回   右段 = 净损失    ← 位置
右边直接写 "2.1万 / 5.8万"       ← 数字
```

实测 HC 模式下：可挽回段变成系统 `Highlight` 色、净损失段只剩描边框，
**百分比和金额一个不少**，照样读得出来。

### 验收（check_bi_charts 新增，7 项）

```
[堆叠条] 可挽回 / 净损失 两段相加 = 总量
  OK  行数 8
  OK  可挽回段占比全部在 0–100%
  OK  标注百分比 = 段宽
  OK  百分比全部可见（被裁 0 个）
  OK  8 行全部在卡片内（末行留白 51px）
  OK  表头给出总额 可挽回 8.5万占损失 34.8%
  OK  可聚焦 role=button tabIndex=0
```

第 4、5 项是被上面那两个 bug 逼出来的，不是一开始就想到的：

- **"百分比被推出可视区"**——量的是数字右边界是否越过卡片右边界
- **"最后一行是否被裁"**——卡片是 `overflow: hidden`，8 行的时候
  很容易裁掉底部几条，而裁掉的部分在截图上看起来只是"数据就这么少"

两条都量几何，不量观感。

### 教训（续）

83. **每个视图都该能回答一个别处答不了的问题**，否则它只是同一份数据的另一种画法。
84. **成本相同、处置方式不同时，"可挽回"比"总量"更适合排序**。
85. **百分比的落点要比跟着数据走**。跟着条尾巴跑，条一长就出界；
    固定在轨道右端反而更好扫。
86. **`overflow: hidden` 裁掉的内容，在截图上等于"没有这个数据"**。
    要用几何断言兜住，不能靠看。
87. **取证源取错字段，检查会静默空转，而且看起来一直在运行**。
    `facts = answer.get('facts')` 取了一个不存在的键，得到 `{}`，
    于是数字比对永远在跟空字典比；它不报错、不打日志，
    只是每次都"恰好"列出一堆查无的小数，像在正常工作。
88. **只写进提示、不进失败的检查，等于没有检查**。
    数字溯源原本 `notes.append(...)`，编造 7 个数字 `problems` 仍为空。
    验收项要能变红，否则它只是句装饰性输出。
89. **容差要跟着写法走，不能定死**。固定 0.06 时，facts 里真实存在的
    `18.0` 让 `17.94` 和 `18.04` 都"推导成立"——篡改一位小数照样过。
    改成"写两位小数只容 0.006"之后才分得清近似与篡改。
90. **"数字没编"和"数字用对了"是两件事**。前者查出处，后者查归属。
    把第41周的 13.04% 写成第44周的，出处完全正确，只有归属错了。
    归属要靠"句子里只提一个对象"来判——一句话提两个对象时，
    数字属于谁本来就说不清，这时候宁可跳过，别硬判。
91. **几个数字完全相同，是参数没生效的第一信号**。
    查词云覆盖率时按正负向切片，得到的两组数一模一样
    （评论数、词种数、覆盖率全同），我差点当成"polarity 参数失效"的 bug。
    实际是我传了 `'neg'/'pos'`，而合法值是 `'正向'/'负向'/'中性'`。
    真实数据不可能让两组切片长得一模一样——**先怀疑自己传错，再怀疑代码坏了**。
92. **一条永远变不红的警告，价值是负的**。它每次都亮，看久了就麻木，
    真出事那天反而没人抬头。要么让它能变红，要么把"为什么它不会红"写在输出里。
    `Top40 覆盖率` 那条就是这样：20.6% 是真实语料的正常值（服饰能到 39.9%），
    25% 的下限是拍出来的。**没有为了让测试变绿去改阈值**——
    改的是措辞，让它从"疑似缺陷"变成"已知特征"，并把 15 个切片的实测值写上，
    以后真要调阈值也有依据。

## 四之十七、两个"多一层"的图表：斜率图与双环

四之十六A 里的四张图各自只回答一半问题。看完还想问的那两句，才是决策真正需要的：

| 已有的图 | 回答不了的 |
|---|---|
| 环形（订单占比） | 盘子大的那个，是不是也在出问题 |
| 发散（差距） | 差得多的那个，盘子有多大 |
| 象限（损失 × 可再售） | 按条数排和按钱排，顺序一样吗 |

### 一、斜率图：为什么我把已经写好的气泡图删了

类目只有 4 个。第一版写的是气泡图（x=订单占比、y=差距），
**实测四个点被撑到画面四角、中间全空** —— 中位数分割线 + 16% 留白
在 n=4 时把值域撑得过大。

但更根本的问题不是留白，是：**4 个点用"看位置"来比较，恰恰是最不准的读法**。
人眼比长度比角度准，比"二维位置"最差；点一少，连"谁在谁右上"都要靠想象。

改成斜率图后，两列各自按自己的指标降序，中间连线：

```
第 44 周实际结果 —— 四条线全部交叉
  订单占比降序：生鲜 37.1% → 个护 27.7% → 数码 17.9% → 服饰 17.3%
  差距降序    ：服饰 8.83pp → 数码 3.32pp → 生鲜 2.79pp → 个护 1.37pp
```

**线是平的 = 两个排名一致（按哪个排都一样）；线很陡 = 排名错位。**
四个类目里四个全错位，这件事在气泡图上是看不出来的，
在斜率图上是一眼——因为"交叉"是一个离散、可数的特征。

踩的坑：`viewBox="0 0 100 100"` 配 `preserveAspectRatio="none"` 让
**`strokeWidth` 跟着横向拉伸了几倍**，1.3px 变手指粗的白条，
正好盖住"是否交叉"这个唯一看点。修法是 `vector-effect: non-scaling-stroke`——
SVG 里唯一能同时做到"坐标用百分比"和"线宽固定像素"的东西。

### 二、双环：一张图放两个口径

原因构成那块要回答的是：**按条数算最多的原因，是不是也最费钱？**

```
尺码版型不符   12.5% 的条数 → 只有 7.2% 的钱（可再售 81%，能卖回去）
功能性能故障    4.7% 的条数 → 却有 9.0% 的钱（件少但每件都报废）
```

两个饼图并排也能表达，但读者得逐项对齐 8 行——对齐完早忘了第一项。
同心环把两个口径放在**同一条半径**上，扇区宽度的差就是口径差，错位变成可见的宽度变化。

外环放条数、内环放金额：读者对"条数"的直觉更强（"一半退货是破损"），
先建立基数印象；金额在里圈紧跟，形成"但是……"的转折。
中心写**绝对金额**（24.9万），不写 100%——两环各是 100%，中心再写一遍是废话。

### 三、环上那道缺口：残差要画出来，不能藏

第一版直接拿 `total_loss` 当分母，验收时抓到：

```
★ 条数份额合计 98.2% · 金额份额合计 98.7%（都应为 100）
```

以为是保留小数导致的累积误差，一查数据发现是**真的少了**：

```
items 条数相加  3807  vs  total_returns  3880   （缺 73）
items 损失相加  245327 vs  total_loss  248503  （缺 3176，1.3%）
```

`items` 是数据源返回的 **Top-N**（第 44 周只给 8 类），`total` 是全部。
直接拿 total 当分母，环就只画到 98.7% —— **缺的那块没有名字，读者只会认为渲染坏了**。

修法不是"改成按 items 求和当分母"（那等于假装 Top-N 就是全部，
把"有 1.3% 的损失归不到任何原因"这个事实抹掉），而是补一节
**「其余未单列」**，用最弱的一档灰、排在最后。

> 残差不是误差，是信息。藏起来会让人误判"数据是干净的"；
> 画出来，它自己就成了一个待查的问题。

### 验收（check_bi_charts 新增第 5、6 节）

```
[5] 斜率图  左4/右4/线4（类目 4 个）· 线宽 1.3px（>3.5px 说明被拉伸）
[6] 双环    扇区 18（9 项 × 2 环）· 条数合计 100.1% · 金额合计 100.0%
            口径差与两列相符 · 中心写绝对值 24.9万
归因图表问题：0 处
```

两条判据值得单独说：

- **线宽 ≤ 3.5px**：这不是审美标准，是"`strokeWidth` 有没有被 viewBox 拉伸"的探针。
- **两环合计必须 ≈100%**：容差 1.0pp（9 项各保留 1 位小数，最多累积 ~0.45pp）。
  这条测的不是"好不好看"，是**分母取对了没有** —— 而分母错的图，
  每一段比例都是错的，却渲染得完全正常。

## 四之十八、被压平的那一层，才是结论

归因页的「原因构成」原来有四个视图：份额变化、损失×可再售、条数×金额、明细。
看起来已经"够 BI"了 —— 有发散条、象限散点、双环、表格。

但四个**全部把两级归属压平到二级**：

```
数据本来长这样              图里看到的
一级归属 → 二级原因        只有二级原因
履约物流 → 破损/变质/污损     破损/变质/污损
       → 时效慢/错发漏发     时效慢/错发漏发
产品本体 → 材质做工问题       材质做工问题   ← 和上面两行并列了
       → 尺码版型不符         尺码版型不符
       → 功能性能故障         功能性能故障
```

压平之后，第 44 周的数据给出一个**相反的结论**：

| 一级归属 | 损失 | 占比 | 其下最大单条 | 单条名次 |
|---|---|---|---|---|
| 履约物流 | 74,847 | 30.5% | 60,303 | **第 1** |
| 产品本体 | 73,582 | 30.0% | 33,168 | 第 4 |
| 信息承诺 | 57,853 | 23.6% | 57,853 | 第 2 |

产品本体的三条原因（材质做工 33,168 / 功能故障 22,467 / 尺码版型 17,947）
**单看分别排第 4、5、6，一条都进不了前二**。
但按归属加总，它是第二大类，**离第一名只差 1,265 元**。

> 按二级排序的图，永远看不到"这一整类是最大的问题"。
> 而"该找哪个归属谈"恰恰是按一级问的。

### 为什么是矩形树图

不是"因为用户提到饼图所以加个图"，是数据形状决定的：

- **两层** → 需要嵌套，饼图只能表达一层
- **8 个二级项** → 饼图 8 个扇区的角度差肉眼分不出来（这也是项目里
  环形图只用在 4 个类目上的原因）
- **面积可比** → 树图的本职就是"用面积编码可加量"
- **要能看名单** → 每个格子能放标签，比散点好

用了 squarify（Bruls/Huizing/van Wijk 2000）而不是"按顺序切竖条"。
朴素切条出来又长又窄，标签放不进去、面积也读不准；
squarify 每行贪心地塞到"最差长宽比"开始变差为止，格子尽量接近正方形。

### 三个必须处理的对账问题

**一、"未归因"这块不能省**

`items` 是 Top-N，`total_loss` 是全部。实测差 **3,176（1.3%）**。
不补这块，树图面积只画到 98.7%，而格子上写着"占总损失 x%"，
加起来不到 100% —— 读者会以为哪里算错了。

补成一块之后，这个残差本身变成一个可读的事实：
**有 1.3% 的钱没被任何原因覆盖，那件事值得追。**

（双环图当初就为同一个原因加了「其余未单列」，这次是同一课第二遍。）

**二、同一张图不能有两个分母**

第一版浮层写「占 24.3%」（分母 `lossTotal` 248,503），
aria-label 写「占总损失 24.6%」（分母各格之和 245,327）。
同一屏两个百分比差 0.3pp，读者会怀疑哪个对。统一后都是 24.3%。

验收里直接对账：

```
[6] 浮层与 aria 的百分比口径一致
    OK   浮层 ['24.3'] vs aria ['24.3']
```

**三、`min-width` 必须有配对的滚动容器**

写了 `min-width: 420px` 却没给 `overflow-x: auto`，
容器一窄，撑出去的部分会被父级**直接裁掉** ——
右侧整列格子消失，而且不会有滚动条提示"还有内容"。
静默裁掉比出现滚动条糟糕得多：读者不知道少了东西。

### 顺手修的一处旧问题

截图核对时发现瀑布图的**总计柱是一整块纯白**（`--accent` = #f2f2f3），
153px 高、115px 宽，在 `#151517` 的卡片上第一眼看起来像"这里没渲染出来"。

改成空心框（淡底 + 1.5px 描边）。这不是审美问题：
**总计柱是前面所有节的结果，不是"又一节增量"**，实心白把它说成了后者。
而且 HC 模式下的处理本来就是 `border: 2px solid CanvasText; background: Canvas` ——
两个模式现在表达同一件事，切换模式时图不会"变样"。

### 验收（check_a11y 新增第 8 节，验几何而不是"画出来没有"）

```
[1] 结构        6 个归属 / 9 个格子（画布 1110x300）
[2] 不重叠      重叠 0 对
[3] 面积同序    面积排序与金额排序最大位次差 0 · 面积占比与金额占比最大偏差 1.67pp
[4] 归属汇总    6 个归属都带合计 · 组合计 ≈ 格子合计
[5] 键盘        格子可聚焦 · aria-label 带金额和占比
[6] 口径一致    浮层 ['24.3'] vs aria ['24.3']
树图问题：0 处
```

窄屏四档（1366 / 1100 / 900 / 760）**零溢出、零裁切**。

判据不写"图有没有画出来"，因为树图的两个失败模式都看起来正常：
格子重叠时文字还在、颜色还在，只是少了几块；
面积和金额脱钩后图还在，但它说的已经不是数据了。后者最危险 ——
读者会按面积判断"哪个最贵"，而那是错的。

### 教训（续）

68. **层级数据被压平，结论会反过来**。单条排名和归属排名可以是两个答案，
    而"找谁谈"是按归属问的。
69. **Top-N 的图必须显式画残差**。否则百分比加不到 100%，读者会以为算错了；
    画出来之后，覆盖率本身就成了一个可追的指标。
70. **同一张图不能有两个分母**。差 0.3pp 就足以让人怀疑整套数字。
71. **`min-width` 要配 `overflow-x`**。否则溢出部分被静默裁掉，

72. **"总计"用框、"增量"用填充**。两者语义不同，不能用同一种实心块表达。

## 四之十九、"代码明明改了，界面纹丝不动"

这一轮用户第三次贴来截图问"这两个模块能不能做成可交互看板"。
而这两张卡片在当前代码里各有 **5 个视图**，环形图、瀑布、象限、树图、双环全都在。

查 zip 原件确认他看的是最初版本（`Donut`/`Waterfall`/`Segmented` 一个都没有）。
**但连贴三次就不是"看错文件"能解释的了。** 根因在服务端：

```
$ curl -sI http://127.0.0.1:8848/
last-modified: Mon, 02 Nov 2026 10:37:15 GMT
etag: "8642f5c1f123581b059ac61a9b882952"
                                      ← 没有 cache-control
```

Vite 的产物文件名带 hash（`index-t9UcBUyj.js`），内容一变名字就变，
所以 **JS 本身不会被旧缓存命中**。但 `index.html` 名字是固定的 ——
它一旦进了浏览器缓存，就永远指向上一版那个**已经被删掉**的 bundle。

后果是所有检查都是绿的，唯独人眼看到的东西不对：

```
✓ 源码改了      ✓ dist 重新 build 了
✓ curl 服务端返回的是新 bundle    ✗ 浏览器打开还是旧界面
```

这类假失败的排查成本远高于它本身的复杂度 ——
因为它不报错，只是"看起来没生效"。

### 修法：两类文件用相反的策略

```python
class _NoCacheHtmlStatic(StaticFiles):
    async def get_response(self, path, scope):
        resp = await super().get_response(path, scope)
        if path.endswith('.html') or path in ('', '.'):
            resp.headers['Cache-Control'] = 'no-store, must-revalidate'
            resp.headers['Pragma'] = 'no-cache'
            if 'etag' in resp.headers:
                del resp.headers['etag']
        return resp

app.mount('/', _NoCacheHtmlStatic(directory=str(_DIST), html=True), name='static')
```

```
index.html   → no-store, must-revalidate · pragma: no-cache · 无 etag
assets/*.js  → etag 保留（文件名带 hash，可以长缓存）
```

**为什么用子类而不是 `@app.middleware('http')`**：中间件会给包括 `/api`
在内的每一个请求都套一层，而这里只需要改一类静态文件的响应头。

**踩到的坑：`MutableHeaders` 没有 `pop()`。**

```python
resp.headers.pop('etag', None)     # AttributeError → 整页 500
```

Starlette 的 `MutableHeaders` 是大小写不敏感的映射，但没有 dict 的 `pop`。
删头只能 `del`（或用 `in` 判断后再删）。我第一版就是这么写的，
服务一重启**整个首页 500** —— 修一个"看不到新版"的问题，
顺手把页面搞挂了，这比原问题严重得多。

## 四之二十、看板里"选中"必须是全局概念

两个模块当时各有一个缺口：

| 位置 | 问题 |
|---|---|
| 卡①「明细」 | 完全忽略 `catPick` —— 图上点了类目，表格不响应 |
| 卡② 四张图 | **没有任何 `onPick`** —— 切视图选中全丢 |

切到「明细」想看它的具体数字 —— 选中没了，得在 8 行里重新找一遍。
**刚才那次点击等于白费。**

### 做法

```tsx
const [stPick, setStPick] = useState<string | null>(null)
const pickSt = (k: string) => setStPick(stPick === k ? null : k)
```

4 张图共用这一个状态，明细表的行也读写它。

`Quadrant` 组件原来不支持选中，补上 `onPick` / `activeKey` ——
它本来就是 `<button>`，所以键盘可达是天然的，不用再补 tabIndex。

### hover 和选中必须是两种视觉

```
hover  → 只改填充（我在看它）
pin    → 额外加一圈外环（我选中了它）
```

用同一种高亮的话，鼠标一移开就分不清"刚才选的是谁"。

外环用 `--accent-line` 而不是 `--bad`：`--bad` 是"这个数据有问题"的语义，
这里表达的是操作状态，不是数据状态。

表格行的选中用 `inset box-shadow` 画左竖条，**不用 `border-left`** ——
后者会挤动单元格宽度，切换选中时整张表横向抖一下。

## 四之二十二、条形元素的两种"看起来没做完"

用户截了归因页两张图，一句"这些条条柱柱的也不圆润呀"。查下来是两个独立的问题，
共同点是：**都不会报错，只会让人皱眉**。

### 一、圆角早就统一过，但这两张图漏了

`app.css` 3403 行有一段现成的记录：

```
/* 条形图：圆角提到 6px。原来 3px 在高 20px 的轨道上显得很"方" */
.bar-track    { border-radius: 6px; }
.bar-fill     { border-radius: 6px; }
.stack-bar, .stack-seg { border-radius: 6px; }
```

但归因页这几个图是独立实现的，柱子还是 `2px`（瀑布）和 `1px`（双向条）。
1px 在 100px 宽的柱子上就是直角 —— 截图里看着像"这图没做样式"。

修法：

| 元素 | 改前 | 改后 |
|---|---|---|
| `.bi-wa-bar`（瀑布柱） | 2px | 6px，四角 |
| `.bi-dv-bar.pos`（右伸） | 1px | `0 6px 6px 0` |
| `.bi-dv-bar.neg`（左伸） | 1px | `6px 0 0 6px` |
| `.bi-ss-bar`（堆叠份额） | 2px | 6px |

双向条**只圆远端**，零点那一端保持齐平。如果把靠零轴的一端也倒圆，
每根条的根部都会出现一个半圆缺口，看起来像"条没贴住轴" —— 那比直角更糟。

修完顺手把根因也处理了：加一个 `--r-bar: 6px`，上面这些和主条形图
全部改引用它。**光改数值不改出处，第三次还会漏。**

### 二、总计柱是个空心框，读起来像"没渲染"

上一版是 `rgba(242,242,243,.13)` 淡底 + 1.5px 近白描边，起因是**纯白填充太刺眼**。
这个理由没错，但结论错了：在 1280 宽的窗口里这根柱子是 **99 × 153px**，
描边比旁边任何一根数据柱都亮，而中间是空的。读者的第一反应不是"这是合计"，
而是"这块图没出来"。

改成实心中性灰 `var(--fg-4)`（#86868f）：

- 红/绿只留给有方向的数据，灰色天然表示"汇总，没有方向"
- 亮度低于描边、高于背景，既不刺眼也不会被当成占位
- 读它的方式和读别的柱子一致：看高度

HC（强制色）模式下仍然是空心 + 2px 描边 —— 那里没有颜色可用，
只有描边能把"总计"和"数据"分开。

### 三、顺手把 12 个页签全过了一遍

改两处是"照着用户指的改"，但同一个卡片还有 5 个页签没看。所以写了个审计脚本，
把两张卡所有页签里"比高度长、且有填充或描边"的元素全列出来，量它们的圆角：

```
卡① 类目贡献
  贡献瀑布    bi-wa-bar        2px → 6px ✔
  本周vs基准  纯表格            —
  订单占比    环形 path          —（圆弧，不适用）
  差距        bi-dv-bar        1px → 远端 6px ✔
  规模×差距   象限散点            —（圆点）
  明细        迷你条 pg-bar-f   已是 999px 药丸

卡② 原因构成
  份额变化    bi-dv-bar        ✔
  挽回潜力    bi-ss-bar        2px → 6px ✔
  损失×可再售  象限散点            —
  条数×金额   气泡               —
  归属树图    bi-tree-c        3px → 4px（见下）
  明细        迷你条            已是药丸
```

结论：真正的"条"只有 4 处，都在上次漏掉的那批里。其余是圆弧、圆点、药丸，
本来就没有直角问题 —— **按形状分类看，比按"是不是图"看更准**。

### 四、树图的两个问题：一个是圆角，一个是半行字

树图格子是**块**不是条，直接套 6px 会过头：

- 最矮的格子只有 19px 高，6px 会把它做成胶囊
- 相邻格子之间只有 1px 缝，半径越大"掐腰"越明显

所以取 4px。但放大截图时发现了更严重的一条：**那两个 19px 格子里的原因名被压扁了**。

```
19px 高的格子：上下内边距 10px + 一行文字 13.75px = 需要 24px
实际只有 19px → flex 默认 flex-shrink:1 把文字框压成 7px 高
```

屏幕上是半行字，而这正是代码里自己写过的那句"半行字比没有更糟"。

麻烦的地方在于**它测不出来**：`scrollHeight == clientHeight`，任何"内容溢出"检测
都看不到 —— 文字不是溢出去了，是被布局压扁了。所以：

```css
.bi-tree-cl, .bi-tree-cv, .bi-tree-cs { flex: none; }  /* 文字不许被压扁 */
@container (max-height: 25px) { .bi-tree-cl { display: none; } }  /* 塞不下一行就不写 */
```

现在小格子退化成一块纯色方块（全称在 aria-label 和浮层里），
其余格子的文字都是完整的 14px 行盒。

### 五、范围再扩到整个应用：又找到三处

归因页修完，同一套审计脚本扫了全部 7 个页面（dashboard / attribution / reasons /
reviews / competitors / eval / chat），按类名聚合每个"条状元素"的圆角：

| 类名 | 位置 | 改前 | 改后 |
|---|---|---|---|
| `.bi-bar-track` / `.bi-bar-f` / `.bi-bar-f.is-ghost` | 仪表盘横向条（15px） | 2px | `var(--r-bar)` |
| `.bi-mini-f` | 表格里的迷你条（5px） | 2px | `border-radius: inherit`（=轨道 999px） |
| `.pg-heat-fill` | 原因页热力格（24px 色块） | 3px | 4px（和树图同档） |

迷你条那条还有个隐藏问题：**轨道是药丸、填充是 2px**，两个圆角不一致，
条短的时候右端会从圆头里露出一块直角。改成 `inherit` 之后两者永远一致。

审计同时排除了几个"看着方、其实不能改"的：

```
pg-decomp-seg     中间的分段，必须方 —— 它是一根条被切开，圆角只该出现在整根条两端
pg-hit            评论命中高亮，2px 是"记号"不是数据条
< th > / tr       表格行（宽高比 >3 才被误判成条）
sw.good / sw.gray 9×3 的图例色块
bi-dv-bar         最小圆角 0 是我故意留的（零点端齐平）
```

**为什么最后没用"启发式自动找方条"做断言**：一次扫下来误报 20 多个，
真条只有 3 个。所以断言改成**按类名清单钉住**，扫全站只用来"发现"，
不用来"判定"。启发式适合找线索，不适合当门禁。

### 六、审计脚本自己有个盲点：SVG 里的柱

第一版审计按 HTML 的 className 聚合，**SVG 图形全被折叠成 `[object SVGAnimatedString]`
一个键**，我当时把它当误报放过去了 —— 那等于没看。

单独扫一遍 `<rect>` 才找到：评论页「分周走势」底部的 **样本量柱 52 根**，
10px 宽、直角。这是全站唯一用 SVG `<rect>` 画柱的地方，所以 CSS 里的 `--r-bar`
永远管不到它。

```jsx
<rect rx={Math.min(2.5, barW / 3)} ... />
```

不能照搬 6px：CSS 那边的 6px 是给 100px 宽、15px 高的柱准备的比例，
这儿的柱只有 10px 宽，6px 会做成药丸。而且这张 svg 是
`preserveAspectRatio="none"`，`rx` 会跟着横向拉伸，上限还得再保守一点。

断言：`check_reviews_chart [6]` —— 53 根柱 rx ≥ 1.5。`rx` 写在 viewBox 坐标里、
又被拉伸，换算成像素没有意义，所以只要证明"不是直角"。

### 七、加了 8 项断言，量的是可证伪的性质

新增 `check_a11y.py::check_bar_shape`：

```
✓ 瀑布柱四角 [6,6,6,6]（应都 ≥5，2px 在 100px 宽的柱上等于直角）
✓ 右伸柱 [TL,TR,BR,BL]=[0,6,6,0]（远端圆、零点端 0）
✓ 左伸柱 [TL,TR,BR,BL]=[6,0,0,6]
✓ 总计柱底色 alpha=1（rgb(134,134,143)，99×153px）
✓ 堆叠份额条圆角 [6,6,6,6]
✓ 仪表盘横条 f=6 / track=6
✓ 迷你条 填充 999 = 轨道 999（必须相等，否则短条右端露直角）
✓ 原因页热力格 4（色块不是条）
```

总计柱那条特意看 **alpha** 而不是"有没有背景色"：空心框的 `backgroundColor`
也是设过的（`rgba(242,242,243,.13)`），只判"存在背景色"会漏判。
按旧值 0.13 算，这条会红。

后三条是跨页面跳转量的（`location.hash` 切到 dashboard / reasons），
不依赖归因页的上下文 —— 因为这类"同一组件在别处又实现一遍"的问题，
只在**那个页面**才复现。

### 教训（续）

93. **同一个视觉元素在第二处实现时，第一次修好不等于第二次也对**。
    圆角、间距这类"约定"没有共享变量就一定会分叉 —— 上一轮把主条形图
    从 3px 提到 6px 时，归因页的柱子谁也没想起来。修完数值要顺手修出处。
94. **用"有底 / 无底"表达身份，在有背景的深色面板上会被读成"内容没加载出来"**。
    区分身份要用颜色类别（有方向 / 无方向），不要用填充的有无。
95. **文字被压扁不会触发任何溢出检测**。flex 子项默认 `flex-shrink: 1`，
    空间不够时它先压文字框（19px 的格子把 14px 的行盒压成 7px），
    而 `scrollHeight` 仍等于 `clientHeight` —— 溢出断言全绿，屏幕上是半行字。
    要么给 `flex: none`，要么明确不显示；两者都比"让它挤一挤"强。
96. **启发式适合找线索，不适合当门禁**。扫全站"方条"时误报 20 多个、
    真条只有 3 个。所以流程是：启发式扫一遍**发现**，人挑出真问题，
    最后用**类名清单**写成断言。反过来直接拿启发式当测试，只会制造假红灯。
97. **审计脚本的盲区会伪装成"没问题"**。按 HTML className 聚合时，
    SVG 图形全被折叠成一个键 `[object SVGAnimatedString]`，看上去"只有一个类"，
    实际是 52 根没被检查的方柱。**扫不到的东西不会报不存在，它会被算成 0 个问题。**

### 八、把圆角收成变量，再给"漏改"装一道源码门禁

上一轮修完 8 项断言还是绿的，但把同一批元素在别处又实现了一遍的版本捞出来看，
躺着的还有三处：

| 元素 | 页面 / 组件 | 原来 | 现在 | 为什么之前没发现 |
|---|---|---|---|---|
| `.wc-track` / `.wc-fill` | 对话页 词云条（13px） | 2px | `--r-bar` | 只出现在对话答案的某个 block 里 |
| `.ps-bar` / `.ct-bar` | 对话页 人物画像 / 对比条（4px） | 2px | `--r-pill` | 同上 |
| `.bi-mini` | 仪表盘表格迷你条（5px） | **两遍**：2px + pill | `--r-pill` | 后一条盖前一条，读哪一遍都像没问题 |

第三行才是最危险的一类：**同一条规则写了两遍、取值还不一样**。
改动代码的人如果只 grep 到第一处，会以为"已经是 2px 了，改过了"。

所以做两件事：

1. **两个设计变量 + 明确的适用边界**
   ```css
   --r-bar: 6px;    /* 条：10–16px 高，6px 即半个圆头 */
   --r-cell: 4px;   /* 块：19–24px、里面要文字，6px 会变胶囊且在 1px 缝上掐腰 */
   ```
   边界写进注释：`--r-cell` 只管**要塞文字**的块（树图格 / 带字热力格）；
   纯色无字的色格（`.bi-heat-c` 22px、图例 swatch）保持 2px —— 那是"刻度"，
   放大就变成装饰了。**不写这条边界，下一次"统一圆角"就会把它们改成胶囊。**

2. **`check_radius_tokens()`：不开浏览器，直接读 app.css 源码**
   ```
   ✓ 变量 --r-bar / --r-cell / --r-pill 有定义（var() 失效会静默变 0）
   ✓ 条/块类选择器无写死小圆角（<4px）
   ✓ 条/块类选择器圆角取值一致（同一 selector 不许两遍不同值）
   ```
   为什么查源码而不是查渲染：渲染只能证明"我打开的这一页是对的"，
   而这个 bug 的形态就是**散在不同页面、分几次写**。
   豁免必须写明理由（键帽 `<kbd>` 名字里有 bar，图例色块是刻度），
   否则下次有人"统一"时会连豁免一起改掉。

**验证这道门禁真的会响**：注入一行 `.wc-track { border-radius: 2px }`，
两条断言同时变红（`[('.wc-track','2px')]` / `('2px' → 'var(--r-bar)')`），
撤回后回到 0 处。不这么做就无法区分"检查通过"和"检查没执行"。

98. **"改过了"要能证明改的是生效的那一条**。CSS 后写的规则覆盖前面的，
    同一个 selector 出现两次不同值时，`grep` 到的那一行未必是浏览器用的那一行。
    要么删掉被覆盖的死代码，要么让两处取值相同 —— 留着一个"看起来已经改好"的旧值，
    比留着明显的错值更费时间。
99. **渲染断言证明不了"全站都对"，只能证明"这一页对"**。同一类元素每多一处
    独立实现，就多一处只在特定数据/特定路由下才出现的漏改（词云条要等某条回答
    里恰好有 WordCloud block）。这类问题该用**源码级门禁**兜底：
    它不关心数据走到哪个分支，只关心"还有没有人写死那个数字"。
100. **门禁要配一次"注入 - 变红 - 撤回"的验证**。新增断言后立刻说"全部通过"，
     等于假设检查本身是对的。改一行、看它红、改回来，三步成本极低，
     却能把"检查没执行/没匹配上"这种假绿挡住。
101. **修 bugs 时只改了"当时正在跑的那个入口"**。数字溯源要从 `tool_result` 取证这件事，
     2026-11-02 改在了 `run_all.py` 里，而 `check_chat.py` 的命令行入口
     还留着 `answer.get('facts')`（恒为 `{}`）—— 于是同一个检查：
     跑批时"派生小数已核对"，手工单问时"无工具返回，N 个小数未核对"。
     **同一个判断散在两处就会出现这种"半修好"**：抽成 `check_chat.facts_from(events)`，
     两个入口都调它。判据：改完后手工跑一次单问，提示行里必须出现"已核对"，
     而不是"未核对"。
102. **截图空白不是"没渲染"，是 clip 落在视口外**。对话页回答会累积到几千 px 高，
     词云/画像/对比这些块几乎必然在视口下方，`Page.captureScreenshot` 的 `clip`
     一旦越界就给你一张纯色图 —— 不报错。判据：量 `getBoundingClientRect().y`
     与视口高比一比，先 `scrollIntoView({block:'center'})` 再截，
     并且 clip 的 `y+height` 要夹在视口内。
103. **门禁查源码 ≠ 门禁查产物，中间隔着一个 `npm run build`**。
     源码门禁全绿、服务端发的还是旧 CSS —— 这种假成功有绿勾作证，比"没改"更危险。
     判据：`dist/index.html` 引用的那个 CSS，mtime 不得早于 `src/styles/app.css`，
     且要用**同一套** `_radius_scan()` 扫一遍（两套各写一遍就又是"修一份忘一份"）。

### 九、对话页三个块：源码门禁之外，补一次像素确认

`.wc-track` / `.ps-bar` / `.ct-bar` 这三个不存在于任何独立页面，
只在"某条回答里恰好有这个块"时才渲染 —— 渲染断言没法稳定覆盖，
所以它们由源码门禁（`check_radius_tokens`）守着。为了确认门禁说的和屏幕一致，
真的去问了三个问题，实测：

| 块 | 触发问法 | 实例数 | 高度 | 轨道圆角 | 填充圆角 |
|---|---|---|---|---|---|
| 词云条 `.wc-track` | 差评都在说什么 | 24 | 13px | 6px | 6px |
| 画像条 `.ps-bar` | 买我们东西的都是什么样的人 | 16 | 4px | 999px | 999px |
| 对比条 `.ct-bar` | 竞品表现怎么样 | 20 | 4px | 999px | 999px |

三个数都对上了变量定义：13px 走 `--r-bar`，4px 走 `--r-pill`，
而且**轨道和填充必须同值**（否则短条右端会露出一块直角）。

这三个不写成常规断言，理由要写清楚：它们依赖 LLM 回答里恰好出现某个块，
一旦模型换措辞/换工具，断言就会随机变红 —— 假红灯比没断言更糟。
分工是：**源码门禁守回归（确定性），像素确认只做一次存证。**

### 十、再补一道：产物一致性（`check_dist_fresh`）

前面所有圆角断言都读 `frontend/src/styles/app.css`，但后端挂的是 `frontend/dist/`。
两者之间隔着一个 `npm run build`，而这一步没人会记得每次都做 ——
于是最容易出现的假成功是「源码改对了、门禁全绿、屏幕上是旧的」。

新检查四条，都不开浏览器：

```
✓ dist/index.html 引用的 CSS 与 JS 都真实存在（不是上一次的哈希）
✓ 它们都不早于 src/ 下任何源文件的最新 mtime（改了没打包 → 报警并指出是哪个文件）
✓ 里面确实有 --r-bar / --r-cell / --r-pill
✓ 用同一个 _radius_scan() 扫产物，无写死小圆角 / 同名取值冲突
```

第二条是核心：它不是"格式检查"，是**时间先后**检查 ——
`stat().st_mtime` 一比就知道有没有打包。实测 `touch app.css` 之后
它立刻报「源码比产物新 41.1 分钟，去跑 npm run build」，重新 build 后回 0。

**第一版这条只比 `app.css` 与产物 CSS，留了个洞**：改 `.tsx` 完全不报警。
而「Reviews.tsx 的柱子加 `rx`」就是纯 tsx 改动、CSS 一个字节没动 ——
旧版门禁照样全绿，浏览器里是旧柱子。所以基准改成 **`src/` 下所有文件的最新
mtime**（实测 20 个：16 个 tsx / 3 个 ts / 1 个 css），产物也 CSS + JS 一起比。
再 `touch src/components/BiKit.tsx`，它现在会指名道姓：
「BiKit.tsx 比产物新 3.9 分钟，去跑 npm run build」。

顺手做的一件事：把圆角扫描抽成 `_radius_scan(css)`，源码和产物共用。
这条判断现在只有一份实现 —— 否则下次改了其中一份，
又是 `.bi-mini` 那种"读哪遍都像没问题"。

### 十一、运行时：整页抛错时所有检查都会变绿

之前所有检查看的都是"某几个元素对不对"。但一个页面渲染时抛错，
结果是**整块卡片空白** —— 颜色、圆角、对比度全都"没东西可测"，
于是照样全绿。`check_console_clean` 补上这个盲区，并且**自己验证自己**：

```
✓ 监听器自检：先故意 throw 一个异常，确认被捕获
✓ 页面清单以后端 /api/pages/nav 为准，侧边栏项数必须相等
✓ 每页 main 可见文字 ≥ 80 字
✓ 每页路由必须真的生效：切过去后侧边栏第 i 项要有 on
✓ 每页 0 条未捕获异常 / 0 条 console.error（warning 只统计，不判失败）
```

**这条检查是被自己坑出来的，两次：**

第一次，我手写了 12 个 tab 名去扫，实际路由只有 7 个
（`dashboard/attribution/reasons/reviews/competitors/eval/chat`），
另外 5 个（overview / kb / actions / code / ops）是我编的。

第二次更值得记：**未知 hash 不会渲染空白，它会停在上一个页面**。
实测 `#/overview`、`#/kb`、`#/ops` 全都显示 dashboard 的 1132 字。
所以"内容 1132 字、0 报错"这种绿灯，很可能只是六次测了同一页 ——
光看字数是发现不了的。必须问"当前选中的导航项是不是我要求的那一项"：

```
hash=#/attribution  期望第 1 项选中 → {'on': True}  → 通过
hash=#/overview     期望第 1 项选中 → {'on': False} → ★ 会报红
hash=#/kb           期望第 3 项选中 → {'on': False} → ★ 会报红
```

顺带把 `check_a11y.Ctl` 改成继承 `check_contrast.Ctl`，只保留差异
（`Page.enable` + 键盘注入）。两份逐字重复的 CDP 客户端，在给父类加
"事件缓冲"时正是"又得改两处"的典型现场。

104. **"页面加载成功"不等于"我要的那一页加载成功"**。SPA 的 hash 路由
     对未知值常常静默忽略，于是审计脚本反复测量同一页而不自知。
     判据不是"有内容"，而是"当前选中项 == 我指定的那个"。
105. **监听型检查必须先证明监听器活着**。不做自检，"0 个错误"分不清
     是页面干净还是根本没收事件 —— 与"检查没执行"的假绿同源。
106. **别手写清单，去问下发源**。导航页清单由 `/api/pages/nav` 给，
     手写一份必然漂移；漂移之后不会报错，只会让你测错对象。
107. **加覆盖之前先确认"是不是已经有了"**。核对路由时发现 chat 页
     不在 `PAGES` 里，我以为漏了，加进去——结果它本来就有专门两节
     （欢迎态 / 真实回答后），因为推理链、结论卡要等一条回答回来才存在。
     这次加法有三个副作用：同一页被审两遍、多花 4 秒、
     表头那句"6 个功能页"变成假话。已撤回。
     **覆盖率这种事，先搜再加**：搜不到不等于不存在（可能换了形式，
     比如 chat 是单列一节而不是塞进 PAGES）。

### 十二、覆盖矩阵：窄屏原来只测了 1/7 的页面

把"每个检查函数访问了哪些路由"抽出来一张表，才看见两个洞：

```
check_focus            dashboard, chat
check_reduced_motion   dashboard
check_narrow           dashboard          ← 只有 dashboard
check_interactive      dashboard, attribution
check_semantics        dashboard, chat
check_forced_colors    dashboard
check_bar_shape        attribution, dashboard, reasons
```

**窄屏只测 dashboard 是最没道理的**：横向溢出是逐页布局问题，
卡片栅格、表格列宽、图例换行都写在各自页面里，没有任何理由假设另外 6 页不撑破。
已改为 7 页 × 2 档 = 14 个组合，实测全部 `scrollWidth == viewport`。

改的过程中又发现判据本身不够：**注入一个 3000px 宽的块后，
`overflowX` 仍然是 false** —— 它被祖先 `overflow:hidden` 裁掉了，
页面不横滚、滚动条也没有，可那块内容就是看不见了。
所以判失败不能只看滚动条，必须看"有没有越界元素"。

同时要避免误伤：页面里确实有几处**设计上就该横向滚动**的容器
（`.tbl-wrap` / `.pg-heat-wrap` / `.bi-heat-wrap`），它们内部超宽是故意的。
所以判据加了一层"向上找有没有 `overflow-x: auto|scroll` 的祖先"，有就豁免。

三个情形都验过：

```
① 基线                                    offenders: 0
② 裸超宽块（该报）                        offenders: 1  ['probe-naked']
③ 放进 .bi-heat-wrap（合法滚动容器）      offenders: 0  豁免生效
```

108. **"这两种失效长得很不一样，判据却只能看见一种"**。横向溢出有两种形态：
     出现滚动条，或被祖先裁掉。前者显眼，后者安静 —— 而安静的那种
     恰好是用户投诉"这块字被切了"的来源。判据要覆盖两种，
     再对"故意的滚动容器"给豁免，别一刀切成假红灯。
109. **只在一个页面上验"全局类"性质，等于没验**。窄屏、减动效、
     高对比度这三项当时都只在 dashboard 上跑。减动效/高对比度或许可以由
     一条全局规则代表（也确实写在一处），但**布局不是**——
     布局是每页各写一遍的。分清"全局规则"与"逐页实现"，后者必须逐页验。
110. **"写在一处 CSS 里"不等于"只影响一个页面"**。我原以为高对比度那 28 条规则
     是全局的、dashboard 代表得够；把选择器列出来后发现有 `.pg-chart-svg` /
     `.pg-cross` / `.pg-sel-box` 这一组，**Dashboard.tsx 与 Reviews.tsx 各画一张图**。
     规则只有一份，命中的元素却有两套 —— 而 svg 的 stroke/fill 是各自 inline 写上去的，
     规则是否生效取决于元素结构，不取决于规则本身。已把 reviews 页纳入。
111. **断言量错维度，比漏测更费时间**。给 reviews 样本柱加断言时量了宽度，
     12 根全是 11px → 报假红。而那张图的宽度是常量、数值编码在高度上。
     写断言前先问一句"这一维承载数据吗"，否则会把人引去改一个没坏的东西。
112. **同一个缺口，我一天里"补"了三次重复的**。chat 对比度、其余页窄屏、
     其余页 th 语义——每次都是"发现没覆盖 → 加一段"，然后发现原处已经有、
     或已经有另一节在做（`[1b] 六页 th scope 覆盖`）。
     第三次才定下规矩：**加覆盖前先搜一遍已有输出里有没有同名的节**，
     有就扩展那一节，别再开一节。判据是"跑一遍看输出里是不是出现了两个 [1b]"。
113. **用类名当判据，等于给断言装了一个静音开关**。`_TABLE_PROBE` 统计
     "可排序表头"用的是 `className.includes('bi-th-sort')`，而原因治理页那套
     表头写的是 `class="r sortable"`——两套实现、两个类名。于是 `sortable` 恒为 0，
     调用处写的是 `if sortable and focusable != sortable`，0 直接短路成通过。
     **61 个表头检查里，reason 页那 3 个从来没被看过一眼，却一直是 OK。**
     类名会漂移、会分叉（本项目已经有两套表头），**光标不会**：
     设计上"点得动"统一用 `cursor:pointer` 表达，两套实现都遵守。
     判据要锚行为，不要锚标识符。
114. **凡是 `if X 非空 and ...` 形状的断言，都在等一个静默的永真**。
     这种断言不会报错、不会变红，只会让人以为测过了。两个修法任选：
     要么把"X 必须 > 0"也断言掉（空集就是失败），要么换一个不会为空的判据。
     本期这条属于后者：换成光标后 `sortable` 从 0 变成 3，缺陷立刻显形。
115. **`<tr>` 从来不在浏览器的默认可聚焦列表里**。挂 `onClick` 加 `cursor:pointer`
     得到的是一行"鼠标能点、键盘够不着"的内容——不报错、不变形、不遮挡，
     鼠标用户一辈子碰不到。补的方式是 `tabIndex={0}` + `Enter`/空格 keydown，
     **不要加 `role="button"`**：那会让读屏丢掉 `tr` 的行语义，
     `th` 与 `td` 的对应关系随之断裂。补可达性不该以毁语义为代价。
116. **判断"能不能聚焦"要看 `el.tabIndex`，不看 `getAttribute('tabindex')`**。
     `<summary>` 原生可聚焦，但属性是 `null`——第一版探测器因此把 reviews 页
     那个"展开全部 12 个词的原话"报成了缺陷。同时 `disabled` 的按钮本就不该可聚焦，
     也不能算缺陷（chat 的 send-btn 就是被这么误报的）。
     **一个探测器要同时防假阳和假阴，唯一办法是换判据重算一遍再对账**：
     光标法 288 个（把可点祖先的后代全算进来了）→ React `onClick` 法 215 个
     （把 disabled 按钮算进来了）→ 第三次"光标 + 真有 onClick + 非 disabled"
     才收敛到 2 个真缺陷。第一次的结果如果直接拿去改，会白改 200 个地方。
117. **键盘可达 ≠ 键盘可用，得按下那个键才算验完**。属性到位之后再发一次真事件：
     原因治理页 Enter 后"条数"前三从 `18,243/16,172/10,646` 变成
     `18,243/16,172/12,820`（真的重排了），`aria-sort` 从
     `none/descending/none` 变成 `descending/none/none`；
     总览页 Enter 后正文从 1621 字涨到 2101 字（明细真的展开了）。
     两处焦点环实测对比度都是 **11.92:1**——因为全局 `:focus-visible` 是通配的，
     `tr`/`th` 一旦变可聚焦就直接继承，不需要新写样式。
     **这条顺带回答了"要不要为它加 CSS"：先测，别先写。**
118. **一屏 208 个格子，不能有 208 个 Tab 停靠点**。热力矩阵每格都挂着
     `onPick`（tooltip 上明写着"点击进归因 ›"），但 `<div>` 不在默认可聚焦列表里，
     所以整块下钻入口是鼠标专享的。给每格加 `tabIndex=0` 是错的解法：
     Tab 序列变成 208 次停顿，可达性没解决、可用性反而更差。
     正解是 **roving tabindex** —— 整块只留一个 `tabIndex=0`，进入后用方向键
     在同一平面内移动。实测：208 格只有 1 个停靠点，方向键
     `0,0→0,1→0,2→1,2→1,1→0,1`，按 Enter 真的跳到 `#/attribution/48`。
     另外每格必须有 `aria-label` 写**结论**（"个护，第 1 周，退货率 6.68%，
     比基线 -0.50pp，正常波动"）：视觉上这三行信息折叠在 tooltip 里，
     而键盘和读屏没有 tooltip。
119. **当两个语义抢同一个通道时，把其中一个挪到另一个通道，而不是二选一**。
     热力格的 `outline` 平时被两条语义占着：红框=异常周、黄虚线=统计显著但幅度不够
     （代码里 `.is-link` 当初改用 `box-shadow` 就是为了这个）。焦点环如果也走
     `outline`，一聚焦就把"这格异常"涂掉了。解法是：焦点环走 `outline`（外圈白），
     `.is-anom:focus-visible` 把红色迁到 `inset box-shadow`（内圈红）。
     聚焦的异常格同时看到"白圈在外、红圈在内"，两条信息都不丢。
     黄虚线那一档让位（三档里最弱，且 aria-label 里有结论）。
120. **新门禁要先证明"它会红"，否则只是又一条永真**。`check_keyboard_reachable`
     写完后连跑两轮注入验证：
     （a）把热力格的 `onKeyDown` 短路掉 → 报"只 1 个停靠点但方向键无效"；
     （b）把 `tabIndex` 全改成 -1 → 报"整类不可聚焦"。
     两个分支都变红、且诊断指向真实原因，才算这道门能用。
     **一条从没红过的断言，和一条被注释掉的断言，价值相同。**
121. **门禁的判据要跟着"合法的设计"升级，不能因为它误报就把判据放宽到抓不到真问题**。
     `check_keyboard_reachable` 第 3 版逐个判 `tabIndex >= 0`，把 207 个
     roving 格子报成缺陷 —— 这不能靠"加白名单"糊过去，因为白名单会让
     真正的"只留一个停靠点却没做方向键"漏掉。改成"按同类控件成组 + 方向键实测"，
     两个方向都保住了。分组键还踩了一个坑：不能拿完整类名当键
     （`bi-heat-c` / `bi-heat-c is-anom` / `bi-heat-c is-link` 会被拆成三组，
     其中异常格那组一个 `tabIndex=0` 都没有 → 误报"整类不可达"），
     要取块名（第一个 class token）。
122. **"猜一个够用的步数"是最危险的一类检查设计**。`check_focus` 前后三个版本：
     第 1 版只测总览/问答两页；第 2 版给每页配固定步数
     （总览 16 / 问答 40 / 其余 10）—— 看起来覆盖了 7 页，但实测每页的
     Tab 停靠点是 **52 / 41 / 16 / 22 / 13 / 9 / 23**，而前 7 步永远是同一组侧边栏。
     也就是说 quiet 页真正被验到的页面元素只有 3 个，
     attribution 那 41 个停靠点里 **38 个从没被看过**，却一路全绿。
     步数一旦失准，表现是"更少的检查 + 依然全绿"，比报错难发现得多。
     改成**走到回到第一个元素为止（序列闭合）**，把每个停靠点都验一遍；
     闭合与否也打印出来，没闭合说明有元素被跳过或焦点逃逸。
123. **判"闭合"的身份键不能只用 tag + class + 文本**。SVG 元素的 `className`
     是 `SVGAnimatedString`，`toString()` 之后全是 `[object SVGAnimatedString]`，
     `innerText` 又为空 —— 5 个 `<g>` 会互相认成同一个，第二格就误判成"已闭合"，
     整圈提前结束（而且看起来一切正常）。键里必须带坐标。
124. **证明"扩了覆盖"要用旧预算外的元素做注入**。给 `.bi-wa-bar` 抹掉焦点环
     （它在 attribution 的第 22–27 步，旧的 10 步预算永远够不到）→
     新检查报"第 22–27 步不可见 6 处"，`最低环对比 11.92` 同时说明
     其余 35 个停靠点是好的。**如果注入点落在旧的覆盖范围内，
     这次验证就等于没做** —— 它只能证明"原来就会红"。
125. **会改真实数据的测试，必须校验"改回来了"，而且要放在最前面校验**。
     `check_kb_fail` 靠把 `reason_kb.json` 改名、写坏来模拟工具故障，
     但它的恢复段落只有一个 `except OSError: pass`：恢复失败被静默吞掉，
     然后脚本继续去评判措辞 —— **它可能一边把线上在用的知识库弄坏、一边报 PASS**。
     现在恢复完必须逐字节比对（文件在？内容与开工前一致？），不一致直接 `return 3`，
     和"措辞不合格"（`return 1`）分开报 —— 数据被弄坏比措辞不对严重得多，
     混在同一个退出码里会被当成同一类问题去看。
126. **测试别往业务数据目录里写临时文件**。`check_kb_fail` 原来 `copy2` 出一个
     `data/reason_kb.json.bak_check`，用完再 `os.remove`。两个后果：
     ① `data/` 里留下垃圾（一次被拦就一直躺在那儿）；
     ② 删除要经过环境的 safe-delete 钩子，钩子一拦**进程直接被中断** ——
     表现为退出码 1、没有 `FAIL` 行、`PASS` 永远打不出来，
     看起来像"断言失败"，实际是清理动作被杀。
     改成读进内存当备份、恢复时 `write_bytes` 回去，删除操作彻底消失。
     **凡是"为了能回滚而创建的文件"，先想想能不能只存在内存里。**

127. **乘 100 必须在四舍五入之前**。`plan()` 里 `_f(share, 2)` 先把 0.2186
     舍成 0.22，再乘 100 得到 22.00% —— 真值 21.86% 的两位有效数字被永久吃掉，
     而且**错误的方向是"看起来更整"**，最不容易被怀疑。
     换算链路上任何一步先降精度，后面的放大都只是把误差放大。

128. **同一个字段名在不同接口里语义必须一致，否则前端一定会按旧语义去拼字符串**。
     `share` 在 `reasons` / `dashboard` 里是百分数（21.86），
     在 `plan` 里一度是小数（0.22），前端照旧拼 `%`，屏幕上印出「占 0.22%」。
     这类错排版检不出来（没溢出）、对比度检不出来（颜色正常）、
     键盘可达也检不出来（它不该被点）—— 它长得完全像一条正常结论。
     只能靠"同一份数据内部自洽"来抓：`check_plan_numbers` 用
     `count / 退货量 × 100` 反算占比，差 100 倍立刻红。

129. **能用可验算的关系时，不要留启发式判据**。`check_plan_numbers` 里
     本来有一条"值落在 0–1 之间就当小数没 ×100"，写完发现它会误报：
     一个真正稀有的原因（占损失 0.8%）合法地就落在 0–1 之间。
     删掉它——"占比之和 = 100%"已经精确覆盖同一件事，且不会误伤。

130. **两块并排的内容不等高，会被读成"这里没画完"**。
     `.pg-2col` 是 `align-items: start`，左栏四个条形 168px、
     右栏四条判定 318px，左下就空出一块 L 形缺口。
     光改等高只是把缺口挪进卡片里，真正的修法是**给那块空间一件该做的事**：
     补上"四项合计 3.53pp + 未分配 0.11pp = 3.64pp"——
     读者本来就要问"加起来为什么对不上总量"，正好用这块地方回答。

131. **对不上的数字要给它一个名字，不要留着让人猜**。4 个类目贡献相加
     3.53pp、总量 3.64pp，差额 0.11pp 是类目占比本身在变（结构变化）。
     不解释的话，读者第一反应是"算错了"，而这一页后面所有数字的可信度
     都会跟着打折。差额小于 0.05pp 就不提 —— 那是四舍五入的尾巴，
     专门标一句反而像在解释一个不存在的问题。

132. **注入故障后必须当场还原，不能"等一会再说"**。给 `Plan.tsx` 注入
     "选中的周不绑定范围"这个 bug 去证明探针会红，中途被别的事打断，
     注入版就留在了工作区 —— 下一条需求改完、跑 `npm run build`，
     构建出来的 dist 里**带着那个假 bug**，而且所有门禁都是绿的
     （那个 bug 只有交互探针能抓，而它不在默认六套里）。
     以后：注入和大卡/截图之间必须紧挨着；开始新任务前先 `grep` 一眼
     有没有 `_tmp/*.bak` 对应的源文件还没还原。

133. **断言里不要用"第 N 张卡"这种下标**。归因页删掉一张卡后，
     `check_bar_shape` 里 `.pg-card`[3] 整体前移一格，指到了另一张卡上：
     找不到「挽回潜力」分段控件 → 没点 → 目标元素不存在 → 量出圆角 `[0]`。
     报错信息是"圆角 0"，看着像样式退化，实际是**选择器指错了元素**。
     改成按卡片标题文字定位，增减卡片都不会再误伤。

134. **"没找到元素"和"属性值是 0"必须分开报**。两者都判失败，但
     `堆叠份额条圆角 [0]` 会把人引去改 CSS，而真正的问题是元素没渲染。
     `ss = js(...) or [0]` 这种写法把两种失败折叠成了一种，
     等于把排查方向也一起折叠掉了。

135. **页面就绪判据不能引用"马上要删掉的元素"**。`check_contrast` 等归因页
     时盯的是 `.pg-gate-item`（判定卡），卡一删就永远等不到，
     90s 后超时 —— 表现出来不是"检查失败"，而是"像后端挂了"。
     删 UI 时必须全局搜一遍选择器，包括就绪判据和悬停态清单。

136. **卡片"页脚"样式不能当独立块用**。`.pg-note-inline` 带 `border-top`
     和底色，塞在卡片底部是页脚；一旦被当成 `.pg` 的直接子元素，
     就变成一条上边有横线、左右无边界的带子，看起来像渲染了一半。
     独立成行的说明另给一个 `.pg-note-line`（无容器痕迹，靠栅格间距对齐）。

137. **交互类断言要进"常跑的门禁"，别只留在 `_*.py` 探针里**。
     预警策划页的选周交互（点击 / 切类目 / 回车）最初只写在临时探针里，
     而临时脚本的结局是被清理 —— 那一刻断言就消失了，但页面还在，
     下次谁动这一页都没有任何东西兜着。现在并进 `check_a11y`
     的 `check_plan_interact`（6 步、含一次真实 Enter 键）。

138. **"选中的东西"要和"选了它的范围"绑在一起**。只存一个裸周号，
     切类目后仍拿旧周号去取数：个护只有第 48 周异常，页面却按第 44 周取，
     清单里没有 44 那一行、下面却写着"第 44 周的策划方案"。
     存 `{值, 范围}`、取值时校验范围，跨范围自动退回默认值。
     **注入证明**：改回裸周号后门禁报 4 条 ★（无高亮行 / KPI 与高亮不符 /
     方案标题与高亮不符 / 高亮周不在清单），还原后回到 0。

139. **每一步都要重新验一遍不变量，不要只在最初验一次**。
     上面那条注入之所以能被抓住，是因为"点击后、切类目后、回车后"
     各验了一次"KPI 周号 = 高亮行 = 方案标题"。
     只在页面打开时验一次的话，第一次交互之后的错就全都漏掉了。

140. **值为 0 不要渲染成空白 —— 它会和"缺数"长成同一个样子**。
     原因页的 `类目 × 原因` 矩阵原来写 `v > 0 ? v.toFixed(1) : ''`，
     屏幕上有 5 个洞（个护/数码的「尺码版型不符」、服饰/生鲜的「功能性能故障」、
     生鲜的「未归类」）。读者看到洞只能猜：是这类目真没有这种退货，
     还是系统没算出来？0 是一次真实测量，印成 `0` 才是准确的说法，
     用 `.is-zero` 压到最低一档灰，不跟真有大值的格子抢注意力。
     门禁：`原因矩阵 N 格全部有数字`（空白格数必须为 0，且内容全是数字）。
     **注入证明**：改回 `: ''` 后报"空白 5 格"，还原后回到 0。

141. **堆叠条不是"好看的条形图"，它是一条加法断言**。
     归因页促销卡原来把「结构效应 0.04」和「机制效应 3.98」画成一条堆叠条，
     旁边标「合计 3.28pp」。但机制项是 151 个 SKU 配对差的**等权平均**
     （每个 SKU 一样重），合计是**按订单加权**的总体差 —— 两个口径，
     0.04 + 3.98 = 4.02 ≠ 3.28。堆叠条的几何语义正是"两段相加等于全长"，
     所以它在用图形宣称一个不成立的加法。改成三格并列的账目，
     每格自带口径说明，读者不会去做那个加法。
     **判断标准**：只有两段确实能相加时才画堆叠；口径不同就并列。

142. **「其中」这个词自带加法语义，别乱用**。
     同一处原来写「其中：结构效应 +0.04pp」——一个"其中"就在说它属于第一格。
     改成并列的「结构效应」才配得上"不能相加"那句话。
     措辞和图形是两个独立通道，**两个通道都得跟数据一致**，
     改了一个不改另一个，等于换个方式说错话。

143. **差额必须由后端命名并给数，前端不自己减**。
     4.02 与 3.28 差 0.74pp，这个差是什么？原来没人说，读者自己一减就得出
     "这页算错了"。改成后端下发 `residual_pp`，页面写一句
     "实际涨幅与「结构 + 自身」相差 0.74pp，差额来自权重口径，不是算错"。
     **对不上的数字，要么闭上，要么命名** —— 留给读者猜就是让评审去猜。
     注意：命名之后还得防止它变成大头，所以门禁另加一条
     "差额 ≤ 实际涨幅的一半"，真变大了说明分解口径要重做，不是加句话能圆的。

144. **一个数据块的计算范围（周/类目）必须显式下发，不能让前端自己推**。
     `promo_mechanism()` 不接 week，算的是"促销周 vs 非促销周"的整体对照。
     归因页的标题是「这一周为什么涨了」，第 52 周不是促销周、退货率还在降
     （−0.98pp），页面照样显示「促销周退货率上升 +3.98pp」。
     修法是后端下发 `is_promo_week`（`w in promo_weeks`），前端据此决定展不展示。
     **不要用 `promo_weeks.includes(d.week)` 让前端自己判** —— 那两个字段的
     类型一旦变（数组换字符串），判断会静默失效，而页面看起来完全正常。
     非促销周也不能让这块凭空消失：用一行 `.pg-note-line` 说
     "第 N 周不是促销周，这条排除项不适用"，否则论证链看起来缺一环。

145. **结论块里的 evidence 往往就是上面数字的文字复述**。
     促销卡的 `verdict.evidence` 三条（构成没变 / 同批 SKU 变差 / 没降价没换低质）
     与三格账目 + 四格排他性检验一一对应。同一张卡里，同一件事说三遍，
     读者只会去比对两处措辞是否一致。收敛成「数字一次 + 结论一次」：
     账目格给数，排他性检验给反证，结论块只留 headline 和治理方向
     —— **这两句是数字推不出来的，才值得占版面**。

146. **底部两张"小表"通常是上半页图表的降级副本**。
     归因页底部曾有「本周退货原因构成」（原因/条数/占比/损失）和
     「同周类目对比」（类目/退货率/订单/退货）。前者是 `structure.items`
     明细视图的弱化版（少了基准份额、份额变化、可再售率），
     后者是 `category_contribution` 的弱化版（少了基线、偏离、贡献）。
     最有力的证据是：那张表自己的说明写着"要看变化，用上面那张构成对比表"
     —— **一个模块在给自己的读者指路，就是它在说自己多余**。
     删的时候连带把后端只为它生成的三个字段也删掉，不留死字段。

147. **中文表格在窄屏会被压成一字一行，因为 `table-layout: auto` 的下限是"一个字"**。
     504px 视口下，原因页那张 18 列的表有 9 个格子的文字竖着排下来，
     看起来像渲染坏了，其实每一列都在，只是每列只剩 40px。
     修法照抄热力矩阵早就用过的那套：容器 `overflow-x: auto` +
     表 `white-space: nowrap` + `min-width: 100%`（宽屏仍铺满，不缩成一条）。
     **不要靠"让它自己折行"解决** —— 折两行是能读，但列宽仍由浏览器平摊，
     该被看见的列还是会被挤成缝；而数据表横向滚动对 WCAG 1.4.10 是豁免的。

148. **溢出一丁点就冒滚动条，比稍微挤一点更难看**。
     仪表盘那张表只溢出 14px，于是整张表底下挂着一根滚动条，
     最右的「归因」列被切掉半个字 —— 读者看到的是"样式坏了"，不是"可以往右拖"。
     根因是 `.pg-table td { padding: 7px 10px }` 的左右留白：
     7 列 × 20px = 140px 全花在空白上。窄屏（≤900px）收到 7px 省出 42px，
     这张表正好回到屏内，其余表的溢出量也各小一截（185→131、52→10）。
     **先量溢出多少再决定改不改**，别一上来就加提示条。

149. **"能横向滚" ≠ "看得出能横向滚"**。
     滚动条有两种：经典型占布局高度（`offsetHeight - clientHeight ≥ 10px`），
     overlay 型不占位、悬停才浮出来。后者等于没有提示，
     用户看到的仍是"右边被切了"。判定就一行：
     `el.offsetHeight - el.clientHeight`。本项目实测 10px（经典）。
     **这条要单独量**：`overflow-x: auto` 和 `scrollWidth > clientWidth`
     只能证明"滚得动"，证明不了"看得出来滚得动"。

150. **数"文字占了几行"不能用 `Range.getClientRects().length`**。
     同一行里的多个 inline 元素各返回一个 rect，把「基准」两个字
     包在 `<span>` 里就会报成 2 行 —— 探针于是把好好的格子判成竖排。
     真实行数要按 rect 的 `top` 去重（`new Set(rects.map(r => Math.round(r.top)))`）。
     同理，"竖排"不能用 `高 ÷ 宽 ≥ 1.6` 判：旁边有 90px 高的格子时，
     43px 宽的普通格也会满足。判据应是**行数 ≥ 字数**（且字数 ≥ 2）。

## 四之二十三、把"看着像图"的两块表，做成真的能问问题的看板

原因治理页原来有上下两块：一张 9 行的原因表、一张 4×9 的热力矩阵。
两块都在**陈述**，没有一块能**回答下一句**：
"破损占 24.11% 损失，那是多少钱？多少条？点进去都是些什么货？"
读者只能把问题咽回去，或者自己在那张表里找。

用户连着提了两次要把这两块做成可交互看板。第二次我没有直接动手，
先问了一句"你是想要 BI 那种联动，还是只想要好看"——
因为这一页的**问题不是样式**，是"表格和矩阵各说各话"：

| 原来 | 现在 |
|---|---|
| 矩阵 36 格只印一个百分比 | 每格带条数 + 损失额，浮层里给全 |
| 只有"占条数"一种口径 | 「占条数 / 占损失」可切，两套列最大值分别归一 |
| 格子怎么点都没反应 | 点一格：整页范围切到那个类目，表格那一行跟着亮 |
| 表格行只按损失排 | 八列都能点，再点一次反向；`aria-sort` 三态 |
| 键盘：36 格要按 36 次 Tab | 整块 1 个停靠点 + 方向键 |

### 一个必须承认的取舍：矩阵不跟着范围筛选变

页顶选「数码」之后，矩阵**仍然是四行**。这不是漏了联动 ——
矩阵唯一的用途就是横向比类目，跟着筛就只剩一行，表就拆了。

麻烦的是它的**外观**：页顶写着"范围：数码"、底下一张表还是四行，
读者第一反应是"筛选没生效"。屏幕上没有任何东西会提示他不是。
所以卡片说明里明说了这件事，并用一条断言守住：

```python
# 下钻之后矩阵不塌成一行
nrow = br.ctl.js("document.querySelectorAll('.pg-heat tbody tr').length")
ok = nrow == len(cats)
```

注入（`categories.filter(c => !category || c === category)`）之后这行报
「现在 1 行」，**并且连带把锁定定位和 roving 一起打歪**——
`data-r` 索引错位，点的格子锁到了 `0,5`，Tab 停靠点掉到 0 个。
一个"少了个筛选"的动作，能顺着索引把三个不变量一起破坏，这是原来没想到的。

### 踩得最深的一个：锁定态不能用压暗

第一版把锁定做成了"其余格子 `opacity: .38`"。看截图才发现问题：

> 颜色深浅本来就在编码数值大小。
> 一个被压暗的 27%，和一个正常的 8%，**长得一模一样**。

于是读者看的是"这块数值小"，而事实是"这块被压暗了"。
两个通道（颜色 = 数值、明度 = 状态）打架，输的永远是数值那条。

改法是**只允许不改颜色的信号**：

```
列头点亮（颜色变，但那是文字不是格子）
行标签左侧竖条
选中格描边
```

压暗只留给 hover 那一瞬间 —— 因为 hover 是暂时的，读者不会把它当数值读。
断言直接钉死这一点：`is-dim` 计数必须为 0（锁定态）/ 24（悬停态，4+9−1=12 格在十字线上）。

### 门禁做了两层，因为这两块错起来没有形状

```
check_bi_board(port)      18 项 · 交互：真的点、真的按、真的数
check_reasons_recon()     22 项 · 纯接口：行合计 / 格合计 / 乘法关系
```

交互层守的是三件"点了也不会报错"的事：切了口径但数字没变、
有描边但范围没跟着切、36 格全给了 `tabIndex=0`。

对账层守的是另一种：**页面两套切法，任何一处漏行都对不上，但渲染完全正常**。
R1–R3 验行合计 = KPI，R4 验 `可挽回 = 损失 × 可再售率`（脚注里写的那句话），
R5–R6 验矩阵格合计 = 总量。

### 三个自己给自己挖的坑

**① R1 一直是真的，因为两边同源。**

```python
recoverable_total = sum(float(x['recoverable']) for x in rows)
```

KPI 就是从行推出来的。把某一行乘 1.1，**R4 五条全红、R1 一条不红** ——
被篡改的行同时也进了合计，比值不变。这不是白测（R1 守的是"哪天 KPI
改成从别处取"），但**真正抓单行算错的是 R4**。
注释里把这句话写明了，免得以后有人以为有 R1 就安全。

**② 注入 G 第一版删到的是 0 格。**

`cells.pop()` 删掉的是「生鲜 × 未归因」，而它是 0 条 0 元（后端把
不存在的组合补成真实的 0）。删掉它合计纹丝不动，注入白做。
换成 `[x for x in cells if not (x['category']=='生鲜' and x['n']>0)]`，
R5/R6 立刻报「少 1,707,256 元 / 28,724 条」。

**教训是通用的：注入一个"删除"类故障，必须确认被删的东西不是空值。**
否则你验证的是"删除空值没影响"，不是"门禁能抓到丢数据"。

**③ 探针点了屏幕外面。**

矩阵第 2 行的坐标算出来 `y = 872`，而视口只有 805 高。
点击被浏览器直接丢掉，报出来像"事件没绑上"。
修法是先 `scrollIntoView({block:'center'})` 再量 `getBoundingClientRect()`。

同类的还有一个舍入误报：接口给 27.25、界面显示 27.3，
而 Python 的 `f"{27.25:.1f}"` 给 27.2（银行家舍入）——
两边都对，比字符串却失败。判据改成"离真值不超过半个末位"。

### 顺手修掉的一个：可点 `<tr>` 又漏了键盘

归因页「类目贡献」那几行点得到、没有光标、进不了 Tab、回车没反应。
这已经是这个项目第四次踩同一个坑了（可排序表头、热力格、策划页行都踩过）。
修法固定：`clickable` 类 + `tabIndex={0}` + `Enter/Space` + `aria-current`，
**不挂 `role="button"`** —— 那会让读屏丢掉行语义，表头和单元格的对应关系跟着断。

### 教训

151. **锁定态不能改颜色**。颜色通道已经在编码数值了，再加一个
     "压暗 = 未选中"的通道，一个被压暗的 27% 就和一个正常的 8% 同形。
     状态只能用**不改格子填充**的信号：列头文字、行标签竖条、格内描边。
     压暗只留给 hover 这种**瞬时**状态。

152. **一页有两种切法（按原因 / 按类目）时，必须明说哪一块不跟着筛选变**。
     矩阵跟着筛只剩一行就没法横向比，所以它固定是全类目视角 ——
     但页顶写着"范围：数码"、底下还是四行，外观上就是"筛选没生效"。
     说明写在卡片里，断言守住"下钻后行数不变"。

153. **"两边同源所以恒等"的断言会自我安慰**。KPI 由行合计推出来时，
     `Σ行 = KPI` 恒真，改任何一行都不会红。这类断言要标明它守的是
     "哪天数据源分家"，并另外补一条**不依赖合计的单行验算**（R4）。

154. **删空值不算注入**。`pop()` 删掉的格子恰好是 0 条 0 元，
     合计不变、门禁不红 —— 验证的是"删空值没影响"，不是"能抓到丢数据"。
     注入前先确认目标的值不是 0 / 空 / 默认值。

155. **率与额并排时，换算关系要写在同一处**。`可再售率 5.8%` 和
     `可挽回 7.4万` 是同一件事的两种表达，但读者看到会先问"这是两个指标吗"。
     脚注里补一句 `可挽回 = 损失 × 可再售率`，并说明"各行加起来 = 页顶那笔"，
     读者才能当场验算 —— 一个能当场验算的数字，比一个说得漂亮的数字可信。

156. **矩阵格的可访问名要写结论，不是写形状**。
     `aria-label` 里必须是「数码，材质做工问题：占本类目退货 9.65%，
     1,222 条，损失 19.2 万，占本类目损失 11.29%。回车把整页范围切到数码」——
     读屏没有浮层，浮层里折叠的绝对量必须同时进名字。

157. **"这行是什么"和"这行的数是多少"是两个断言，前一个更容易漏**。
     「未归类」1,647 条、占 1.97%、可再售率 72.4%（**全表最高**）——
     每个数字都对，但它不是第 9 个原因，是"我们没归上原因"。
     读者横向扫可再售率那一列，最大的数落在一个根本不能派活的行上，
     自然读成"未归类最值得先管"，而事实是这一类连为什么被退都不知道。
     **数字全对的页面，结论可以是反的。**
     修法是把身份写进数据而不是塞进渲染：后端给 `is_void` + 层级写
     「数据缺口」（不是并列的「其他」），前端只用一条虚线把它和上面隔开。
     不降透明度（会让 72.4% 看着像弱数据）、不换底色（会和 hover / 钉住打架）。
     断言只看接口下发的身份位：恰好 1 行 `is_void`、层级是「数据缺口」、
     且**没有别的行冒用这个层级** —— 最后这条防的是"改成给所有异常行都标数据缺口"。

158. **同一张表里的行可以不等价，但视觉必须告诉读者**。
     如果两行的"下一步动作"根本不同（一行派活、一行派归因），
     它们就不能用同一套排版并排到底。最省事的信号是**一条虚线分界**：
     比加徽标省地方，比换底色安全（底色已经被 hover / 钉住占了两套）。

## 七、两种运行模式

| 模式 | 触发条件 | 谁决定"下一步查什么" | 谁写结论文字 |
|---|---|---|---|
| 确定性推理引擎 | 无 API Key（默认） | 规则引擎（`_react` 里的 if-else） | 模板拼接 |
| LLM 推理 | 设置 `CANYU_LLM_KEY` | 仍然是规则引擎 | **模型改写**（只改文字，不改数字） |

**两种模式下，工具调用都真实执行 pandas，数字来源完全一致。**

这里有个必须说清楚的设计取舍：**模型不参与"查什么"，只参与"怎么说"。**
原因不是技术上做不到（让模型选工具很容易），而是可靠性：
工具选择一旦交给模型，它就可能漏查关键表——比如促销周不调 `promo_mechanism`，
结论就会退化成"破损变多了"这种错误归因。
现在由规则引擎保证"该查的一定查"，模型的表达优势用在它真正擅长的地方。

### LLM 接入的几个实测结论

1. **Key 是阿里云百炼（DashScope）的**，`sk-ws-` 前缀。默认端点
   `https://dashscope.aliyuncs.com/compatible-mode/v1`，模型 `qwen-plus`。
   （试过 DeepSeek / Moonshot / OpenAI 官方端点，全部 401 或不通。）
2. **零依赖**：本机没有 `requests` / `httpx` / `openai`，pip 索引又不通，
   所以直接用标准库 `urllib.request` 手写 OpenAI 兼容调用（见 `llm_client.py`）。
3. **同步 HTTP 必须丢线程池**：`await asyncio.to_thread(...)`。
   否则会阻塞事件循环，SSE 卡在最后一步，前端看起来像死机。
4. **失败会自动重写一次**：校验不过时把"哪里不合格"回灌给模型再问。
   实测同一道题单次通过率只有 50%–70%（模型措辞有随机性），
   加一次重试后稳定到 5/5。多花一次调用的时间，比整段回退模板划算得多。

### 五道输出校验（任何一道不过就重写，两次不过才回退模板）

| # | 防什么 | 判据 |
|---|---|---|
| 1 | 编数字 | 正文每个数字必须能在事实包里找到（容差 0.06；量词数字如 95% 置信水平放行） |
| 2 | 跑题 | 3 段、40–110 字/段、标题 ≤46 字 |
| 3 | 硬编因果 | 低样本/无异常/显著改善场景不许出现"导致/造成了"（否定式除外） |
| 4 | 编动作 | 正文动作词必须出自 playbook；无 playbook 时不许给动作（"不建议做"除外；复盘/回顾类自省动作放行） |
| 5 | 泄露内部结构 | 不许出现 snake_case、`中文名 = 数值`、`true/false` |
| 6 | 悬空指代 | 出现"该原因/这个动作"但事实包里没有对应结构 → 判失败 |

**这六道校验都拦下过真问题**，不是摆设：
`机制占比 107%`（模型自己做了除法）、
`供应链、物流、客服三方协同排查`（库里没这条动作）、
`quality_promo=-0.0704 > base=-0.0898`（把字段名抄进正文）、
`¥50 档挽单率 68.4%`（**其他档位的数据全是编的**，因为当时只给了最优档）、
`这一周不建议针对该原因开整改动作`（**"该原因"指代空气**，因为这一周连原因结构都没算过）。

**校验也会误伤，误伤同样要修**——这是本项目踩得最深的一类坑：

| 误伤现象 | 根因 | 修法 |
|---|---|---|
| `t = 17.72` 被判成编程表达式 | 正则 `[=<>]=?\s*-?\d` 太宽，匹配到 `= 17` | 等号左侧限定为 ≥2 字符标识符：`t`/`z` 放过，`base`/`promo` 拦住 |
| `2,057 单` 被拆成 `057` 判成编数 | 千分位逗号未剥离 | 抽数字前先 `re.sub(r'(?<=\d),(?=\d{3}\b)', '', body)` |
| `不建议做 X` 被当成给建议 | 否定式未剥离 | 先剥掉"不建议…"分句（范围收窄到 30 字且止于标点） |
| 改善场景出现"复盘"被判成动作 | 白名单缺失 | 开白名单：复盘 / 回顾 / 沿用 / 保持 / 沉淀 |
| `95% 置信区间` 里 95 被判成编数 | 白名单只有序数，没有量词数字 | 白名单补置信水平（95/99/90/80）与时间口径（12/30/60） |

### 一条被反复验证的原则：换算值必须由后端预支

模型天然会做三类换算，而且**逻辑通常是对的**，只是那个数不在事实包里：

| 模型想写的 | 它自己怎么算的 | 正确做法 |
|---|---|---|
| 机制占比 107% | 3.93 ÷ 3.68 | 后端给出 `mechanism_share_pct` |
| 每 100 单多退 3.7 单 | pp × 100 | 后端给出"每 100 单多退几单" |
| 比不补偿每单多赚 ¥5.95 | 22.41 − 16.46 | 后端给出最优档与零补偿档之差 |
| ¥50 档比最优档低 ¥9.69 | 22.41 − 12.72 | 后端给出**每一档**与最优档之差 |
| 样本量小、"天然抖动 ±6.4pp" | 1.96 × √(p(1−p)/n) | 后端给出 `噪声幅度_pp` **和** `波动区间95_pp` |
| "多少单才算够"写成 600 | 猜的 | 后端给出 `判定门槛_单数` |

**不要靠"放宽校验"来解决，那会把真编造也放过去。**
正确做法是把这个派生值按统一定义算好、喂进去——
这也正是"数字归 pandas，文字归模型"的实际含义：
凡是能用加减乘除得到的，都不该让模型做。

最后一行尤其典型：我给了一个标准误 ±3.91pp，模型仍不满足，
自己乘 1.645 得到 ±6.46pp 写成"90% 置信区间"——数学完全正确，
但 6.46 不在事实里，被校验拦掉。**它不是不听话，是我的预支不完整。**

### 提示词里最危险的一句话：给示例措辞

写"必须明确说明「这一周不建议针对该原因开整改动作」"，
本意是约束写法，结果是**替模型写好了稿**——它原封不动抄了这句，
正文里就出现了凭空指向空气的"该原因"。

正确做法是只约束"必须满足什么"，措辞交给模型：

> 用上面「理由」里的具体事实说明这一期为什么不派动作，
> 把理由写进正文，不要只写一句"不建议"就完事。
> **但不要写"该原因"这种空指代**：如果你手上没有具体的原因名，
> 就直说"这一周"。

同一类坑还有一个更隐蔽的版本：在提示词里列"不许写 `low_sample`"，
反而教会了模型抄这个字段名。**根治办法是把事实包的键名换成中文**，
让它根本看不到可抄的东西。校验该保留，但正确做法是别给它抄的机会。

### 从"布尔值直接拼成中文"看模型的偷懒方式

实测截图里出现过这样一句：

> 不显著、**不业务显著**、无异常

"不业务显著"不是中文。根因很清楚：事实包里给了两个字段
`统计显著=否`、`业务显著=否`，模型各加一个"不"再连起来念。

要注意它**不是幻觉、也不是算错**——三个判断的意思全都对。
问题在于模型找到了一条捷径：把内部变量逐个取反、拼成一句话，
比"想清楚这三种情况分别意味着什么、再用一句话说出来"省力得多。
只要事实包里还是布尔值，它就会走这条捷径。

改法分两层，缺一不可：

1. **提示词**：明确禁止拼词，并给出三种情况各自的人话说法：

   | 内部状态 | 该怎么写 |
   |---|---|
   | 统计不显著 | "这点波动在正常范围内"（它就是噪声） |
   | 统计显著但幅度不值一提 | "确实是变了，但幅度小到不值得动手" |
   | 统计显著且幅度够大 | 这才叫异常，才值得归因 |

2. **出口校验**：`不业务显著`、`未异常`、`非异常`、`不统计显著`
   这类生造组合直接判废、触发重写。

提示词只是引导，模型换一种形式照样会犯（这轮从"未异常"变成"不业务显著"
就是换了个形式）。**真正的保险在出口**。

顺带还抓到一个更隐蔽的：**元话语**。

> 报告"没有异常"就是核心结论。

这句话没有任何事实错误，但它把正文变成了一份"关于这份正文的说明"。
读者想知道"然后我该干嘛"，不是"作者认为他的报告写对了"。
这类句子同样加了出口校验（`本报告`/`本文认为`/`核心结论就是`/`我判定为`）。

再往下一层，是**同一件事说三遍**：

```
第一段：低于基线 0.55pp，落在正常噪声范围内
第二段：z 未达 2，业务上也不显著，不是真实异动
第三段：这一周本来就不是异常周，不存在需要归因的问题
```

三段都是"没事"，只是换了三种说法。字数凑够了，信息量是零。
现在第三段被明确要求只回答一件事：**读者接下来把注意力放哪**
（"这一周不用管，真正要盯的是第 44 周"）。

## 八、已知局限（写在代码里，也写在这里）

1. 结构效应与机制效应之和（−0.31 + 3.93 = 3.62pp）与实际涨幅（3.54pp）有差额，来自 shift-share 分解的交叉项，未单独拆解。
2. 机制效应用 SKU 配对差分，控制了 SKU 固定效应，但未控制"同一用户跨周行为变化"——数据里没有用户 ID。
3. GMV 换算依赖已估计的传导弹性 λ₁ = 1.303、ω₁ = 0.639，若平台流量结构变化需重新估计。
4. 补偿曲线是相关关系下的期望利润最大化，未做随机化实验，最优档存在选择偏误风险。
5. 商品主数据与经营面板为模拟生成（文本语料为真实公开数据集 online_shopping_10_cats），参数真值已在数据报告中公开以便复核。
6. **措辞层面存在偶发波动**：模型每次输出的说法不完全一样，`run_all.py` 有 8 条、`check_complaints.py` 有 12 条，
   单轮跑下来偶尔会有 1 条被出口校验拦下、回退模板。被拦下的都是真问题（比如那条答案里自己加了
   一句"立即处理"，而对比类问题本来不该给动作建议），不是误伤；回退模板后结论和数字依然正确。
   项目用"失败原因回灌再问一次"的重试把这个概率压下来，但**做不到 100%**——这是 LLM 参与的固有成本，
   不是可以修完的 bug。评审现场演示建议同一问题准备两次，或在演示前先跑一遍 `run_all.py`。
   **2026-11-02 抽查复核**：E4/E1/E5 各跑 3 次共 9 次，0 次被拦；此前抓到的一例是
   第 49 周答案里写了 `1.69`，拿去跟事实包逐项比对——不在任何字段、不等于任何两数之差、
   任何换算都不成立（最接近的猜测 `13.41 − 11.72`，但 13.41 根本不在那次的事实包里），
   确认是模型自己造的。**这条拦截是对的。** 也就是说，偶发回退不是校验器过敏，
   而是模型确实会偶尔写一个查无出处的数；拦下来回退模板，比放出去编一个像样的数字要好。
7. **数字溯源检查曾长期空转，2026-11-02 已修，但它的保证仍有边界。**
   修之前有两个叠加的缺陷：`run_all.py` 从 `answer['facts']` 取数，而 `answer` 顶层
   根本没有这个字段（只有 headline/badge/summary/blocks/caveats/week/llm_note/by_llm），
   取到的是 `{}`；退一步说，就算取到了，那段代码也只把"查无的小数"写进 `notes`，
   不进 `problems`。两条叠加的结果是：编造 7 个与工具返回毫无关系的小数，
   验收依然返回空的问题列表。现在取证源改成 `tool_result` 的 `data`/`evidence`，
   判定改成"能推导才放行"（原值 / 百分比换算 / 万元换算 / 两数之差），
   容差按正文小数位数给（写两位就只容 0.006）。
   实测：8 条真实回答 0 误伤，编造、篡改一位、撞已有阈值四类共 6 个对照全部拦住。
   **第一层（数值溯源）的边界**：它只能证明"这个数确实来自工具返回"，
   不能证明"这个数被安在了正确的对象上"—— 把第 41 周的 13.04% 写成第 44 周的，
   数值仍能通过溯源。这一层由下面的周次绑定补上。
   **周次绑定（2026-11-02 同日补）**：从 facts 里收出所有带 `week` 的记录，
   建成「周次 → 该周全部数值」的索引；正文按 `。；` 分句，只处理
   **主体唯一**（整句只提一个周）且该周确实在索引里的句子；
   句中某个小数若不属于这个周、却明确属于另一个周，判为张冠李戴。
   一句话提两个周时（"第44周比第41周高 3.63pp"）数字归属本来就说不清，直接跳过 ——
   宁可漏，不可误报。实测：8 条真实回答 0 误伤；5 个对照
   （正确引用 ×2、周次写错 ×2、一句双周 ×1）全部符合预期。
   **仍存在的边界**：只覆盖周次，没覆盖类目和原因维度；
   且"第 44 周的订单量写成第 41 周的"这类只在整数上体现的错误不在小数检查范围内
   （整数一律不查，避免把"3 个动作""2 类原因"这类量词当数据）。
   **为什么没继续做到类目和原因**（2026-11-02 量过，不是没想过）：
   facts 里这两个维度是齐的 —— `category` 键出现 12 次、`reason` 6 次，
   每个类目名下挂 16–17 个数值，做绑定的原料完全够。
   但 8 条用例跑下来，正文里**几乎不提**它们：
   类目只在 E4 出现过 1 次，而且是"服饰、数码、生鲜、个护"四个并列一句，
   没法归属到单一类目；原因只在 E1/E2 出现过（"破损/变质/污损"）。
   做出来基本不触发，是死代码；原因名还带斜杠变体（正文可能只写"破损"），
   匹配不准反而制造误报。**原料够、场景不够，就先不做。**
   另有一处要留意：`trend` 工具返回的趋势序列，每个周在索引里只挂一个退货率
   （E3/E4 有 15 个这样的"单值周"）。如果正文提到某个单值周的**其它指标**
   （趋势里没有的，比如该周 GMV），而这个数恰好等于另一个周的字段值，
   会被误判成错配。压力测试 E3/E4 各 4 次、共 8 次，实际误报 0 次，
   说明模型目前不会这么写；但换问题类型时要重新看这一条。

### 怎么自己验收（不用点点点）

```bash
cd agent/backend

# 单题：打印结论 + 机器检查（字段名泄露 / 编数字 / 是否走 LLM）
python check_chat.py "第44周退货率为什么涨了"

# 八场景批量：一行一个用例，看 PASS/FAIL 与徽章是否匹配预期
python run_all.py

# 也可以只跑其中几个
python run_all.py E1 E3

# 界面文字对比度（需要服务在跑）：6 页 + 问答页 + 14 种交互态

# 键盘焦点 / 降动效 / 窄屏（同样需要服务在跑）
python check_a11y.py
```

> `check_contrast.py` 和 `check_a11y.py` 是仅有的两个需要
> **服务正在运行 + 装了 Edge/Chrome** 的验收脚本。
> 它们靠真实浏览器读计算样式，所以也顺带验证了"前端产物确实构建并挂上了"——
> 如果 dist 是旧的，它们报的是旧界面的结果。

8 个用例里有 3 个是**对抗测试挖出来的真实缺陷**，固化下来防回归：

| 用例 | 问题 | 防什么 |
|---|---|---|
| E1 | 第44周退货率为什么涨了 | 促销周必须识别机制，且不针对破损开动作 |
| E2 | 最新一周差评有异常吗 | 最新周正常 → 自动重定向到异常的第 44 周 |
| E3 | 第3周为什么异常 | 10,274 单但 z=+0.66 不显著，必须直说"不是异常周"、不许改题 |
| E4 | 第49周怎么回事 | z=−5.10 显著下降，不是问题，不该套归因模板 |
| E5 | 客服补偿补多少最划算 | 先求最优档，再换算价值 |
| **E6** | 第60周退货率为什么涨了 | **数据边界：必须明说没有这一周，不许拿别周顶替**（徽章「超出范围」） |
| **E7** | 帮我写一首诗 | **能力边界：必须拒绝，但要说清自己能做什么**（徽章「超出能力」） |
| **E8** | 第44周和第41周哪个更严重 | **对比题：必须两个周都答，并说清排序依据** |

> E6 和 E7 原来共用「超出范围」一个徽章。用户投诉的正是这件事：
> 问个不在业务范围内的问题，收到的红牌子和"数据没有这一周"一模一样，
> 会以为这个产品只认一种问法。现在两者分开——
> **数据边界**（我这份数据没覆盖到）和**能力边界**（这不是我的活）
> 是完全不同的两件事，徽章、正文、caveat 全都不一样。

`check_chat.py` 里的检查项是**已知会犯的错**的固化清单，不是泛泛的格式检查：
snake_case 泄露、`中文名 = 数值`、`t = 17.72` 被误判成编程表达式（这条曾经反向误伤过模型）。
加了这个脚本之后，"改一处、坏一处"的问题才暴露出来——
之前手动跑一个场景看一眼，很容易漏掉交叉回归。

### 另一套验收：测"说了什么"

`run_all.py` 测的是行为——走没走对工具、徽章对不对、数字有没有编。
但用户投诉过的两件事**一件都测不出来**：

| 用户投诉 | 行为对吗 | run_all 能测吗 |
|---|---|---|
| "样本量不足以下判断" | 对：确实不该归因 | **不能**，那是措辞问题 |
| "你好你是谁"收到拒绝卡片 | 对：确实不在业务范围 | **不能**，同上 |

所以另写了 `check_complaints.py`：把用户投诉过的原话逐条重放，
在最终 answer 的全文里搜禁用语，搜到就 FAIL。
它搜的是**所有会显示给用户的字符串**——`headline`、`summary`、
`caveats`、`badge.label`，以及每个 block 的 `note`。

```bash
python check_complaints.py
```

这一步不是多此一举。第一次跑它就抓到 3 处漏改：

```
FAIL  数码类目第52周为什么退货率高
      !! 命中禁用语：['样本不足']
      上下文：…本周被判定为样本不足或非异常，因此只列原始差异…
```

那是表格底下的注释。我前面改了正文、改了 caveats，唯独漏了 block 的 note。

### 第三套验收：注入故障，测"工具坏了会说什么"

`check_complaints.py` 测的是正常路径——方案库真的查过、真的没有。
还有一条更尴尬的路径：方案库压根没查成。这两件事在界面上长得很像，
说出来的话却是相反的（见第 12 节）。

正常路径无论跑多少遍都测不到它，因为故障不会自己发生。所以
`check_kb_fail.py` 主动制造故障：

```bash
python check_kb_fail.py
```

它做两件事：把 `reason_kb.json` 改名（模拟文件缺失）、
往里写 `{ this is not json`（模拟文件损坏），然后在真实链路上跑三条问题，
断言三件事：

1. 不出现「知识库里也没有」「暂时没有整理好的动作」这类**断言**（那是假话）
2. 必须出现「没读到 / 读取失败 / 没取到」中的至少一个（承认状态）
3. 标题不能说"也没有近似条目"——因为它明明给了替代口径数字

跑完会自动把文件恢复原样。

### 第四套验收：评论分析（31 条断言）

```bash
python check_review_analytics.py
```

七节，测七件不同的事：

| 节 | 测什么 | 关键断言 |
|---|---|---|
| 1 | 数据隔离 | corpus 里**物理上**没有 label/cause/truth 列 |
| 2 | 情感判定 | 22 条踩过坑的句子逐条判对；全量准确率 ≥94%；负评召回 ≥80% |
| 3 | 词云 | 40 个词全部可回溯到原句；有极性时 `rank_by='lift'`；差评 Top10 无商品名 |
| 4 | 用户画像 | 每条结论带原话；原话必须命中它挂靠的信号词；否定句不算复购 |

反向验证过：把 `collector_status` 返回的 `ok` 去掉再跑，第 7 节立刻红。

### 一句话给评审：这套东西的可信度是怎么来的

七套验收测七件不同的事，缺一不可：

| 脚本 | 测什么 | 测不出什么 |
|---|---|---|
| `run_all.py` | **行为**：走对工具了吗、徽章对吗、数字编了吗 | 措辞（"样本不足"时行为完全正常） |
| `check_complaints.py` | **措辞**：用户投诉过的那几句话回来了吗 | 工具失败时的表现（故障不会自己发生） |
| `check_kb_fail.py` | **故障**：文件坏了会不会说假话 | 分析结果对不对 |
| `check_review_analytics.py` | **分析正确性 + 出口契约 + 看板联动** | 界面渲染 |
| `shoot_cdp.py` / `shoot_page.py` | **屏幕上到底长什么样** | 任何不能从像素上判断的东西 |
| `check_contrast.py` | **文字看不看得清**（WCAG AA 对比度，含交互态） | 布局、间距、语义是否合理 |
| `check_a11y.py` | **键盘能不能用**、**降动效**、**窄屏**、**SVG 过渡是否真在插值**、**读屏能不能听懂**（scope / aria-live / label / 触控尺寸）、**高对比度下图表是否还在**、**走势图是否每周都可读可点** | 实际语音合成效果、真机读屏软件兼容性、其他浏览器 |

**最后一格是必需的。** v4.0 到 v3.3 之间挖出的 bug 里，绝大多数任何断言都测不到：
重定向静默失效、`NaN 步`、截图脚本截错页、热力图上色键错、
联动时其他类目变 0%、看板状态不可寻址 ——
它们不产生错误数字，只是让用户看到一张"没在回答他的问题"的页面。
断言只能守住你已经想到的事，**没想到的那些必须先看图**。

而 `check_contrast.py` 是唯一一条不靠眼睛的：灰阶化把 74 处文字
压到 WCAG 线下，截图里完全看不出来——它测的是"看得清"，
不是"好看"。这两件事在视觉重构里经常同时出问题，但只有后者
会被人当场发现。
## 四之二十四、竞品雷达页的三块 BI 看板（选图比加图重要）

三块模块各选了**数据形状适配**的图，而不是统一上条形：

- **负评率横向对比 → 点级图 + 本店基准虚线**。5 个对象各一个比率：
  没有份额语义（饼图会诱导读者去加总）、每家只有一个数（箱型图没有分布可画）。
  这一页真正要回答的是"谁离本店多远、够不够显著"——点的位置给距离，
  实心/空心给显著性（p<0.05），基准虚线给参照。点击竞品行 → 表格行
  aria-current 同步 + 维度分布条里该竞品 6 个点点亮、其余 18 点压暗。
- **维度差距 → 每维度五点分布条**（范围线 = 最好到最差，本店实心圈）。
  不用雷达图：四条线叠一个多边形只能看出"谁包住谁"，看不出差几个点。
- **用词差异 → 蝴蝶图**。log₂ 比天然双向（正=偏本店、负=偏对标），
  左右镜像让方向变成位置而不是需要记忆的符号；浮层把 log₂比翻译成
  "偏向约 N 倍"（2^lr）。

### 本轮踩坑（两次白屏都自己抓住了）

1. **React #310**：把 `useTip()` / `useState` 放在 `if (err) return` /
   `if (!d) return` 之后 —— 加载态渲染 3 个 hook、加载完 6 个，当场白屏。
   规则：**hooks 全部置顶，派生计算留在出口之后**。
2. **roving 停靠点落在"不可操作"的点上**：维度分布条默认游标取
   `by_entity[0]`，恰好是本店（不可点、无 role=button）—— 24 个竞品点
   全是 tabIndex=-1，键盘可达探针判"整类 0/24 可达"。
   home 必须取**第一个可操作**的点，不是第一个点。
3. **roving 只挪样式游标不算键盘可达**：探针验的是方向键之后
   `document.activeElement` 有没有变。moveStrip 里必须真的
   `getElementById(...).focus()`。
4. 圆角写死 `2px` 被圆角 token 门禁抓 → `var(--r-bar, 2px)`。

门禁：`check_comp_interact`（10 项）——结构计数、三处选中联动同步、
取消可逆、roving 焦点跟随、两个浮层内容（p 值 / 偏向 N 倍）。
注入「压暗逻辑置 false」→ 精准红 1 处 → 还原 → 产物哈希一致。

### 教训

- 159. 选图的第一问是"数据是什么形状"：N 个对象各一个数 → 点级图+基准线；
  一维跨组分布 → 分布条；有符号的量 → 对冲图。饼图要"部分占整体"的语义，
  箱型图要分布，两者都没有时硬上就是装饰。
- 160. hooks 纪律是硬约束：提前 return 的组件里，任何 hook 都必须在出口之前。
  白屏不会告诉你 hook 数量不一致，要靠注入异常钩子抓 stack。
- 161. roving tabindex 的"停靠点"必须落在可操作元素上；落到只读元素上
  （基准点、空格子），整类可操作元素在探针眼里就是"整类不可达"。
